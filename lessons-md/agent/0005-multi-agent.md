## 开场（页首框｜先别急着学，聊两句）

一个 agent 干不完的活，叫一群来干，是不是就更快、更好？不一定：**多 agent 烧的 token 是单 agent 的好几倍**，活太小，叫帮手纯属亏本。

真叫了帮手，问题才开始：活怎么拆？谁汇总？有人干砸了谁兜底？**分工写不好，一群帮手比一个人更乱。**

**学完这课，你能**：判断什么时候该上多 agent；说清多 agent 有哪几种连法、什么时候用哪种；说清怎么派活、失败了谁兜底；知道审计为什么适合派给子代理，以及 TeleAgent / OpenCode 各自怎么派。

【选读框｜记住一条主线，后面就不会晕】

**多 agent 是用分工换上下文**——每个 worker 只看自己那一摊，干完只回结论。这一课讲的，就是怎么把这句话兑现、什么时候不值得兑现。

## 1. 什么时候该上（不是默认）

先说反面：**大多数活不该上多 agent**。Anthropic 在自己的多 agent 调研系统里给过量级（他们自报的口径）：

- **简单查证**：1 个 agent、3～10 次工具调用就干完了——叫帮手纯属亏本；
- **直接对比**：2～4 个 worker、每人 10～15 次调用，才开始划算；
- **复杂调研**：10 个以上 worker、分工明确，才拉开差距。

该上的信号就三种：**能并行的独立分身活**（各查一个方向）、**需要多个视角的活**（正反两方、多个候选）、**单个上下文根本装不下的活**（一个 worker 啃一块，别硬塞一个脑子）。三种信号有一个共同点：活本身够大，而且拆得开。

决定要上，下一个问题就来了：一群 agent 怎么连起来干活？先看最常见的形状。

## 2. 怎么分工：编排者-工作者

这种形状叫**编排者-工作者**：一个 **lead（编排者）**加一群 **worker（工作者）**。

【三柱框】

**lead：拆活、派单、汇总**

自己几乎不动手，只做三件事：把大任务拆成边界清楚的子任务、派出去、收结论合成答案。

**worker：啃一块、回一句**

领到一个边界清楚的小目标，自己转自己的循环；干完**只交结论**，流水留在自己那儿。

**接口：派单四件**

每个 worker 必须拿到：**目标**（干什么）、**输出格式**（交什么）、**用什么工具和来源**（去哪找）、**边界**（别管什么）。

**派单写糊了会怎样？**Anthropic 的教训（大意）：让 worker"调研一下半导体短缺"这种含糊指令，会让他们**重复劳动、互相抄、留缺口**；写成"列出 2024–2026 年关于 X 的 5 篇论文，每篇一句话摘要加链接"才跑得齐。**只回结论不回流水**同样关键——worker 的十万字流水全塞回 lead 的上下文，lead 第一个被撑死。

**失败重派也是 lead 的活**：worker 会失败（工具超时、模型跑偏），重派、换工具、降级都发生在编排层；别让每个 worker 自己写重试，重复建设还容易各错各的。

图注：**一个来回走五步**：任务进来 → lead 拆活派单 → 各 worker 自己转循环 → 只回结论 → lead 汇总交卷。分工换的是上下文：每个 worker 一整个干净的上下文啃自己那块，lead 只装得下结论。

真要做多 agent，优先用成熟框架或产品，别自己手搓调度；这课只讲形状，不写编排脚本。

## 3. 连法不止一种：多 agent 的拓扑谱系

编排者-工作者是最常见的形状，但不是唯一的连法。对照 workflow 的骨架就清楚了：Anthropic 的工程文章（文末一手资料）列过链式、分流、并行、编排者-工作者、评估-优化五种，其中链式、并行、编排者-工作者是**步骤写死的流程**，每一步是一次模型调用；多 agent 做的事，是把那些步骤换成**一个个自己转循环的 agent**。节点变重了，连法就从那几种骨架长成一个谱系：

| 连法 | 长什么样 | 什么时候用 |
|---|---|---|
| **并行分身** | 拆法事先想得清楚，几路同时开、互不相认，结果由人或固定代码收尾 | 子任务能预先写下来——Anthropic Cookbook 的说法：这种用简单的并行就够，别上编排者 |
| **编排者-工作者**（星型） | lead 现场拆活、派单、汇总，子任务**不是预先定的** | 最优的拆法取决于任务本身——本课讲的就是它 |
| **收尾接力** | 干活的和收尾的分开：大家干完，把材料交给一个专职收尾的 agent | 最后一步是补引用、出格式这类固定工序——Anthropic 调研系统末尾就挂着一个补引用的 CitationAgent |
| **层层扩编** | worker 干着干着，再开自己的子代理 | 现在还很少真用：Anthropic 的生产系统是同步执行（一批干完再下一批），他们把异步扩编写在未来方向里，因为协调、状态、错误传播都更难 |

这张表的用法就两问：**拆法能不能预先定**？能就并行分身，不能才上编排者-工作者。**有没有固定的收尾工序**？有就再挂一段收尾接力。层层扩编先别急着上——协调成本比它省的还多。连法还能组合：Anthropic 的实际形状就是「编排者-工作者 + 收尾接力」，lead 派几路 worker 并行，最后交给 CitationAgent。

说回本课讲的这种形状。连法定了，还有更细的问题：活拆好了，哪些值得派给一个真正独立的 agent？

## 4. 什么时候该派：审计是最好的例子

真正难的是判断**哪一块该派**。一个很实用的判据：这块活是不是需要**一个不被当前上下文带偏的独立视角**。

**代码审计为什么特别适合派子代理？**主代理刚写完代码，让它审自己，容易顺着自己的实现找理由——"这里我知道为什么这么写"。子代理从干净上下文进来，只看需求、diff、测试，角色是**只读审计**：找风险、给文件/行号、说理由，**不给它改代码的权限**。修不修、怎么修，回到主流程决定。

这条判据怎么用？把常见的活分成两堆过一遍：哪些值得派，哪些别派。先看值得派的这几类。

| 适合派 | 为什么 |
|---|---|
| **代码审计 / 安全 review** | 写代码的人审自己容易有确认偏差；独立上下文只看证据，更适合挑错 |
| **多来源调研 / 事实核查** | 各查一路、互不干扰；最后只回结论和来源 |
| **方案对比 / 反方视角** | 需要多个独立判断，而不是一个脑子顺着第一条路走到底 |
| **大材料 / 长任务** | 一块料塞进一个上下文会互相干扰；分开啃，各自只回结论 |

**不该派：**

- **三五个工具调用的小活**：拆活、派单、汇总的成本比活本身还贵。
- **强顺序依赖**：下一步必须等上一步结果，派了也要排队。
- **要共享同一份状态、频繁互改的活**：子代理各拿一份上下文，反而容易改冲突。
- **最终责任 / 高风险决策**：可以派去收集证据、提反方意见，但拍板还是人。

两堆分完，"哪块该派"就有答案了：能换出独立视角的派出去，其余留在主流程。

**派单怎么写？**还是四件，再加两条纪律：

```
目标：只读审计这次改动，找最可能出问题的 3 个点。
输出：每条给 文件:行号 / 风险 / 触发条件 / 建议，按严重程度排序。
工具与来源：只看 @src 下这次 diff 涉及的文件和测试，不参考主代理的自我解释。
边界：不要改代码；不确定就标"需人工确认"。
纪律：只回结论，不回流水；失败或超时就重派一次。
```

**不同 harness 的派法不一样。**同样是"派个子代理"，TeleAgent 和 OpenCode 的操作入口、可控程度都不同：

| 问题 | TeleAgent | OpenCode |
|---|---|---|
| **谁决定派** | 主 agent 自动委派 | 主 agent 自动调用，或用户 `@` 点名 |
| **用户能点名吗** | 这版手册没看到"选某个子代理"的入口 | 能：`@general` / `@explore` / `@scout`；自定义 agent 后 `@name` |
| **在哪看** | 任务监控里的「任务委派」 | 子会话 / 输出 |
| **适合** | 办公任务自动拆、少手动配置 | 代码探索/审计/调研，想明确控制谁去干 |

**TeleAgent 怎么操作**（按 2026-10-18 的手册）：把任务描述成"可拆的几路独立活"，发出去后展开任务监控里的 **「任务委派」**，看它有没有真的开子智能体。例如：

```
把这个任务拆成三路并行，分别做、各自只回结论：
1) 审计 @src 下这次改动，找 3 个风险，给文件:行号；
2) 查这次改动涉及的测试缺口；
3) 查这个依赖的最新 breaking changes。
最后按严重程度汇总；不要互相参考，也不要改代码。
```

别写成"@某个子代理"；它没派，可能是任务太小、模型判断不需要。你可以明确要求拆成几路，但**不能保证**一定派。

**OpenCode 怎么操作**（[官方 Agents 文档](https://opencode.ai/docs/agents/)）：它内置 `general`、`explore`、`scout` 等子代理，可以由主 agent 按 description 自动调用，也可以手动 `@` 点名。想稳定让"审计"去干，`@` 更可靠。要固定一个审计角色：在 `.opencode/agents/` 写一个 `review.md`（description 写清"什么时候用它"），之后 `@review` 调用；具体配置看文档，这课不展开。

**TeleAgent 是"把任务写得值得拆"，OpenCode 是"可以直接点名"**；共同点是派单四件、只回结论，以及**审计只读、修不修回主流程**。

## 5. 这笔账：收益和代价

- **代价**：同样复杂任务，token 消耗单 agent 约是简单任务的 4 倍，多 agent 约 **15 倍**——全出自 Anthropic 自报口径。
- **收益**：同一个来源里，复杂调研任务上"强模型编排＋够用的 worker"比单个强模型**好 90.2%**（同为自报）。为什么？分工换来的**上下文隔离**，第 2 节的图里画了。
- **怎么用这两个数**：按第 1 节那三档对号——第一档（几个工具调用）连算都不用算，别上；第二、三档再拿自己任务试一把，比投入的 token 和产出质量。

账算明白，剩下的就是别把这笔账亏掉：下面四条翻车，每一条都是账面上的一个窟窿。

## 6. 常见翻车

- **小题大做**：一个小问题 spawn 十几个 worker——烧钱且更乱。
- **汇总变拼接**：lead 把几份报告原文堆一起就交卷——读者要的是结论，不是汇编。
- **同步等待**：一个 worker 卡住，全体干等——最慢的那个 worker 决定总时长。
- **编排者一错全错**：拆活拆歪了，每个 worker 都在错方向上使劲——lead 是最该测的那一个。

这一课只回答了怎么把活分出去。但每个 worker 都要替你读外面的东西、替你动手——**帮手越多，能读的东西、能动手的东西也越多**。网页里一行小字，就可能让它替别人干活。下一课看这件事怎么发生、怎么堵。

## 7. 检查一下你懂了没

**Q1　一个任务三五个工具调用就能干完，该不该上多 agent？**

- 该，多几个人分工干更快
- 看模型有多大，再决定要不要上
- 该，多 agent 质量一定更高
- ✅ 不该，拆活派单汇总本身就有成本

答对时：对。量级参考：简单查证 1 个 agent、3～10 次调用就够。
答错时：多 agent 是放大器：活不够大，放大掉的是钱。

**Q2　lead 派单时，每个 worker 必须拿到什么？**

- ✅ 目标、输出格式、工具与来源、边界
- 额度、重试次数、超时时间的设定
- lead 的完整历史和全员中间结果
- 其他 worker 的中间结果和缓存

答对时：对。这四件少一件就出事：写糊了重复劳动、留缺口，交回流水 lead 第一个被撑死。
答错时：额度和重试是编排层的事；给历史反而把 lead 撑爆，worker 之间互看会互相带偏。

**Q3　worker 干完活，往回交什么？**

- 全部过程流水，方便 lead 检查
- ✅ 一句话结论——流水留在自己那
- 原始数据，lead 自己挑
- 什么都不交，直接把结果发给用户

答对时：对。这就是「分工换上下文」的兑现点：lead 只装得下结论。
答错时：流水全塞回来，lead 第一个被撑死；原始数据同理。

**Q4　worker 第一次跑失败了，该谁兜底？**

- worker 自己必须写好重试和兜底
- 用户自己把任务重新发一遍就可以了
- ✅ lead——重派、换工具、降级都是编排层的活
- 不用管，多 agent 天然有冗余

答对时：对。兜底写在编排层，别让每个 worker 各写一套重试。
答错时：把兜底塞给每个 worker 是重复建设；编排层统一管。

**Q5　拆法事先写得清楚、几路活互相独立，该用哪种连法？**

- 编排者-工作者，lead 现场拆活派单
- ✅ 并行分身，结果由人或固定代码收尾
- 层层扩编，让 worker 自己再开子代理
- 收尾接力，最后交给专职收尾的 agent

答对时：对。子任务能预先定就用简单的并行，动态拆活是编排者-工作者的活。
答错时：动态拆活是给「拆法取决于任务本身」的活准备的；层层扩编的协调成本更不划算。

**Q6　多 agent 为什么反而常常更快？**

- 模型本身算得比以前快很多，所以自然就快
- 多 agent 不消耗 token，所以更快
- ✅ 能并行，且每个 worker 上下文干净互不挤占
- 网络请求变多了，所以速度反而更快了不少

答对时：对。并行省时间，上下文隔离省干扰——但代价是 token 成倍涨。
答错时：它并不省钱也不省 token；快来自并行和干净的上下文。

**Q7　代码审计为什么适合派给子代理？**

- 子代理写代码的速度比主代理快得多
- 审计这种活必须人多，大家分头查才全
- 子代理做审计根本不需要任何工具帮忙
- ✅ 主代理容易偏向自己写的代码，独立上下文更客观

答对时：对。审计要的是独立视角；让写代码的人审自己，容易顺着自己的实现找理由。
答错时：快慢不是关键；关键是主代理的确认偏差，独立上下文更适合挑错。

**Q8　按这版 TeleAgent 手册，用户怎么派子代理？**

- ✅ 把任务写成可拆的几路，它自动委派
- 输入 `@general` 直接点名子代理
- 必须手写一份 JSON 配置才能派
- 只能自己开发一个子代理才能用

答对时：对。TeleAgent 这版是自动委派，没有点名入口；你能做的是把任务写得值得拆，并观察任务委派。
答错时：这版手册没有「选某个子代理」的入口；@点名是 OpenCode 的做法。
