## 开场：同一段要求，为什么每周都要重说一遍

周一上午十点，周会还有半小时。你打开一个新会话，把上周用过的周报要求又粘了一遍：先汇总完成项，按项目分组；问题单列；下周计划按优先级排；缺数据先问，不要编。粘完你想起，这已经是第六周了。

Skill 就是把重复的要求写成一个文件，放在 agent 能找到的地方。每次遇到写周报，agent 按文件里的说明做。

学完这课，你应能说清 Skill 是什么、正文为什么按需加载；能在 TeleAgent 里创建、测试、修改技能；也能分清 MCP 和 Skill 各管哪层，知道什么时候用哪个。

> **MCP 给能力，Skill 给做法。**

MCP 上一课讲过：它把外部动作包装成模型可调用的工具，比如查日历、读数据库、发消息。Skill 不提供新动作，它告诉模型在什么情况下、按什么顺序、用哪些动作，最后交什么格式的结果。下面从周报开始拆。

## 1. 工具是厨具，技能是菜谱

用agent写周报不难，但是每次新起会话都要重复相同的要求很麻烦。新会话没有上一轮的聊天记录，这是设计使然：上下文越长，成本和干扰越大，所以软件不会把历史对话无限带进新任务。

也有人把要求写进 `AGENTS.md` 或 `CLAUDE.md`，这也行，因为agent每次请求都会把这两个markdown文件的内容塞进上下文，不过，周报的要求越多，占用的上下文就越多。而技能和MCP工具一样，平时只留一行技能文件的说明，相关任务来了才读正文。

如果说MCP工具是厨具，那么技能就是菜谱，agent是厨师。厨师拿着厨具，照着菜谱，开始干活，agent也是读取技能，调用工具，帮你完成任务。

既然技能是菜谱，下一步就看这个文件夹在磁盘上长什么样。

## 2. 一个技能在磁盘上长什么样

一个技能至少是一个目录，目录的根上放一个 `SKILL.md`。这个文件是入口，也是唯一的必需文件。做法复杂时，再往目录里加脚本、参考资料和模板。

```text
weekly-report/
├── SKILL.md
├── references/
│   └── report-template.md
└── scripts/
    └── check_report.py
```

`SKILL.md` 是模型要读的正文；`references/` 放长说明，比如团队模板、字段定义；`scripts/` 放可以直接运行的脚本；`assets/` 放图片、表格模板这类静态文件。

opencode 会去几个固定位置找技能。harness 指的是承载 agent 的软件，opencode 和 TeleAgent 都是。

| 范围     | opencode 查找的位置                    |
| -------- | -------------------------------------- |
| 全局     | `~/.config/opencode/skills`            |
| 全局兼容 | `~/.claude/skills`、`~/.agents/skills` |
| 项目     | `.opencode/skills`                     |
| 项目兼容 | `.claude/skills`、`.agents/skills`     |

项目技能放在仓库里，提交 git，同事拉下来就能用；全局技能放在用户目录，换项目还能用，但不进仓库，分享要单独打包。opencode 还会读 `.claude/skills` 和 `.agents/skills`，这是为了兼容其他工具。有人以为写进 `CLAUDE.md` 就会被发现，其实 opencode 读的是 `.claude/skills` 目录；`CLAUDE.md` 是常驻指令，不是技能发现入口。

两个地方有同一个技能怎么办？opencode 按来源顺序注册，后注册的覆盖先注册的；项目 `.opencode/skills` 排在全局之后，所以同一个 ID 的项目版本会盖掉全局版本。技能的身份由路径推导出的 ID 决定，不由 frontmatter 的 `name` 决定：`weekly-report/SKILL.md` 的 ID 是 `weekly-report`，`name: Weekly Report` 只是显示名。搞不清时先找重复 ID，删掉不需要的那份。

TeleAgent 走另一条路：技能跟着账号和运行端走，从技能广场添加，或导入 `.zip`、`.skill` 包；本地和云电脑技能不互通。你在 opencode 项目里放文件夹，TeleAgent 不会自动看到。

目录和查找规则清楚了，接下来拆开 `SKILL.md`，看模型到底先读到什么。

## 3. 模型先读哪一句

`SKILL.md` 看起来像普通的 Markdown，只是开头多了一段 YAML。YAML 是一种一行一条「键: 值」的配置文本，用两行 `---` 包起来，这段叫 frontmatter。

```markdown
---
name: weekly-report
description: 当用户说「写周报」「汇总本周工作」「生成周报」时，按团队模板整理本周完成项、问题和下周计划。
---

# 周报

## 什么时候用
用户要写周报、汇总本周工作，或让你根据任务记录生成周报时使用。

## 怎么做
1. 读 `references/report-template.md`，确认栏目顺序。
2. 完成项按项目分组，每条写清做了什么、结果是什么。
3. 问题单列，写明影响和当前状态；下周计划按优先级排序，标出负责人。
4. 缺哪一项就先问，不要补写；运行 `python scripts/check_report.py` 检查栏目和字数。

## 输出格式
按模板输出 Markdown，标题用「本周完成」「问题与风险」「下周计划」。

## 失败怎么救
材料不足时，只输出已确认的部分，并在末尾列出缺口；脚本报错时，把错误原样贴给用户。
```

`name` 是技能名，1 到 64 个字符，只能用小写字母、数字和连字符，并与目录名一致。`description` 写清「做什么 + 什么时候用」，上限 1024 个字符，最好带上触发词。opencode 运行时对字段比较宽松，但没有 `description` 的技能不会出现在模型可用的列表里，所以两个都写。

description 的第一职责是让模型判断该不该用。「帮助处理周报」太模糊；「当用户说写周报、汇总本周工作、生成周报时，按团队模板整理完成项、问题和下周计划」就具体得多。模型平时只看到这一行，写含糊了，技能等于不存在。

正文是你真正要它照做的部分：开头写「什么时候用」，中间写步骤和判断，结尾写输出格式和失败处理。规范建议正文控制在 500 行以内，超出的细节放到 `references/`。

图注：**一个目录 + 三层加载**：平时只有 `name`／`description` 进模型能看到的技能目录；模型决定用，才读 `SKILL.md` 正文；正文提到别的文件，再按需打开。

技能不是一次性全部读进来的，加载分三层。会话开始时，harness 只把 `name` 和 `description` 放进模型能看到的技能目录，opencode 还会带上技能 ID，正文不在上下文里。

模型判断匹配后调用 `skill` 工具，opencode 才把正文去掉 frontmatter 加进对话，并告诉它技能目录和最多十个附带文件路径。正文提到 `references/report-template.md` 或 `scripts/check_report.py` 时，模型再按需去读、去运行。

这样设计是因为上下文稀缺。粗略估算，一个技能正文 2000 token，装 50 个就是 10 万 token；还没开始干活，上下文先被说明书占满。按需加载把常驻成本压到几十到几百 token 的说明上，模型只在相关任务里付正文的钱；无关步骤混进来，还会让模型抓错重点。

渐进式加载解释了为什么正文可以短。但技能里还可以放脚本，这又和第一课把 Skill 算进「工具」的说法看起来冲突。下一节把这笔账算清。

## 4. 技能里的脚本，和 MCP 工具差在哪

第一课把工具分成函数、MCP 和 Skill 三档，都归进「模型可以调用」；这一课又说 Skill 是菜谱。两种说法讲的是不同层面：入口上，Skill 是一个可以被模型调用的包；内容上，包里装的主要是做法，必要时才装脚本。

周报技能里有一个 `scripts/collect_tasks.py`，读取 `tasks.csv`，按项目统计完成项，输出 `summary.json`。脚本负责确定性计算；`SKILL.md` 告诉模型什么时候运行、传什么参数、出错怎么办。

```markdown
## 收集数据
运行 `python scripts/collect_tasks.py --input tasks.csv`。
如果退出码不是 0，把 stderr 原样贴给用户，不要继续编造数据。
```

这里的路径相对技能目录。opencode 加载技能时会把技能目录告诉模型，所以模型知道去哪里找；引用附带文件都按这个相对路径写，别写死绝对路径。

脚本和 MCP 工具的区别在复用范围。脚本是技能目录里的一个文件，跟着技能走，不需要服务和协议，适合本地小计算、格式转换、文件检查；MCP server 是独立服务，通过协议把一组工具暴露给多个客户端，适合多产品复用，或统一处理认证、网络和共享状态。只有一个产品用、只跑本地脚本的小工具，Skill + 脚本更轻；等它要被多个客户端调用，再抽成 MCP server。

技能也可以调用 MCP 工具。比如周报技能先用日历 MCP 工具拉本周会议，再用本地脚本统计任务，最后按模板排版。Skill 负责编排，MCP 负责动作。

脚本在你的环境里跑，能碰到你的文件和网络；装陌生技能等于装一段程序，装前至少读一遍 `SKILL.md` 和 `scripts/`。

脚本和工具的账算清了，还剩一个更根本的问题：技能写了步骤，模型一定会照做吗？

## 5. 写步骤的是你，做决定的是模型

答案是不一定。技能是文本，不是工作流引擎。

在 Dify 这类工作流产品里，节点和连线是你画好的，运行时沿着连线走；条件为真走这条，为假走那条，模型只在节点里完成它那一段。技能没有运行时来强制路径：模型读到「缺数据先问」，多数时候会问，但也可能直接编一个数，或者把「先问」理解成「最后提一句」。

技能的约束力来自文字和模型的理解，不来自代码，所以写法会影响它照做的概率。想让模型更愿意按步骤走，可以把下面几件事写进技能。

- 把硬约束放在最前面，用短句写；常见分支也各写一句条件。比如「缺数据先问，不要编」，以及材料缺失、脚本报错、要求含糊时怎么处理，都写在格式说明之前。
- 在结尾放一个检查清单，让它交稿前逐条核对；计数、排序、格式转换、字段校验这类确定性工作交给脚本。
- 用真实任务测试，别只用顺利的样例。拿一份缺数据、格式乱的材料让它跑，观察它在哪一步跑偏；改技能，不要在对话里反复补丁。
- 不可逆的操作不要只靠「请勿」。部署、删除、发送邮件这类动作，用权限系统挡住，或者把技能设为只能手动调用。

还有一个办法：让模型动手前先复述步骤和缺口。理解变成可见文字，跑偏时你能马上发现。这些做法提高的是概率，不是保证；真正不能出错的步骤，应该放到脚本、权限规则或人工确认里。

知道了怎么让模型更愿意照做，接下来把它装进 opencode 和 TeleAgent，实际跑一遍。

## 6. 装一个技能，再让它在该出现的时候出现

先看 TeleAgent，因为它最像应用商店。在 TeleAgent 里装一个现成技能，路径是：

1. 打开左侧栏的「技能·专家·应用连接」，切到「技能」标签，进入技能广场。
2. 在榜单、分类或搜索框里找到技能，点「立即添加」；它出现在「我的技能」，默认是启用状态。
3. 回到输入框输入 `@`，用上下键选中技能，或点 `+` 选「技能」；选中后指令插入输入框，再补具体任务。
4. 有自己的包，点右上角「导入技能」，上传 `.zip` 或 `.skill`。根目录必须有 `SKILL.md`，头部 YAML 写 name 和 description；包不超过 10MB，单文件不超过 1MB，文件总数不超过 300 个。系统会自动做安全审查，发现风险会弹窗，确认后仍可导入。
5. 在「我的技能」里按来源和状态筛选；停用后不能 `@`，同时启用的技能上限是 100 个。本地和云电脑技能不互通，云电脑任务只能用云端技能。

`@` 列表里找不到，先看技能是否停用、任务在本地还是云电脑；导入失败，先查根目录 `SKILL.md`、YAML 和大小限制。

opencode 没有内置技能广场，安装更像放文件。项目技能放 `.opencode/skills/weekly-report/`，全局放 `~/.config/opencode/skills/weekly-report/`，目录名就是 ID。技能来自压缩包或网址时，可以让 agent 下载、解压、放到目录，再检查 `SKILL.md` 和 frontmatter；opencode 没有内置的一键安装按钮，这一步由 agent 完成。

放完文件后重开会话最稳。opencode 把可用技能列在 `skill` 工具的说明里；也可以问 agent「你现在有哪些技能」，或 `@weekly-report` 试一次。没出现时先查文件名、路径、ID、description、权限和同名覆盖。

装好后，它什么时候自己出现？TeleAgent 手册说，不指定技能时会按任务描述自动选，但可能不如手动指定准确；`@` 一次既能提高触发率，也能确认选中的是哪个。opencode 用 `@技能 ID`，Claude Code 用 `/技能名`。三家软件的调用方式可以放在一张表里对照。

| 软件        | 自动触发              | 手动调用          | 只许手动调用的写法                                                        |
| ----------- | --------------------- | ----------------- | ------------------------------------------------------------------------- |
| opencode    | 模型按 description 选 | `@技能 ID`        | `metadata.opencode/autoinvoke: false` 或 `disable-model-invocation: true` |
| TeleAgent   | 按任务描述匹配        | `@` 或 `+` → 技能 | 手册没有写单个技能的开关；可以停用技能                                    |
| Claude Code | 模型按 description 选 | `/技能名`         | `disable-model-invocation: true`                                          |

opencode 和 Claude Code 都能用 `disable-model-invocation: true` 阻止模型自动调用；opencode 里这个技能仍能用 ID 显式加载。TeleAgent 手册没有写这个开关，只能停用。需要绝对不自动执行的操作，放到需要授权的工具或人工步骤里。

技能里的指令和脚本会以你的权限运行；TeleAgent 的审查不等于内容安全。装前读 `SKILL.md` 和脚本；opencode 可以用 `skill` 权限规则设为 `ask` 或 `deny`。

装别人的技能解决的是「有没有」；要把你自己的周报做法变成技能，还得自己写一个。

## 7. 从一次成功的周报开始，做一个自己的技能

最快的起点不是从空白文件开始，而是拿一次刚做成功的任务，把有效步骤和踩过的坑写下来。Anthropic 的创建建议也是这个顺序：先看 agent 在哪些真实任务上卡住，再针对缺口写技能，写完拿同类任务验证。

在 TeleAgent 里，点技能广场右上角的「创建技能」，描述名称、使用场景、执行流程和输出格式，它会生成技能并放进「我的技能」。第一次做也可以 `@技能孵化器`，它会问你要做什么、什么时候用、怎么判断做完，再帮你生成或迭代。

创建完不要只看「已完成」，要开新任务测。`@weekly-report`，给它一份乱材料：完成项只写一半、问题没影响、下周计划空着。看它会不会先问缺的部分，有没有按「完成项 / 问题 / 输出格式」的顺序来，有没有在脚本报错时停下。不对就回孵化器说清偏差，比如「缺下周计划时它自己编了三条，应该先问我」。

TeleAgent 手册没有写技能文件存在本地哪个目录，所以迭代靠对话和孵化器，不是找文件手改。从本地包导入的，改源文件再导一次；在 TeleAgent 里创建的，就用孵化器改。

opencode 里可以直接让 agent 写文件。给它一个明确的目录和结构要求，比如：

```text
在 .opencode/skills/weekly-report/ 下创建一个技能：
- SKILL.md 的 description 要包含「写周报」「汇总本周工作」
- 正文按「什么时候用 / 怎么做 / 输出格式 / 失败怎么救」组织
- 附一个 references/report-template.md 和一个 scripts/check_report.py
```

opencode 里可以装 `skill-creator`，让它按规范带你建；没装也能直接让 agent 写，因为技能本质上就是几个文件。写完打开 `SKILL.md` 改一遍：description 能不能一眼看出什么时候用，正文有没有废话，脚本路径是不是相对技能目录，失败处理有没有写。

测试分两步：先开新会话，不说技能名，只说「帮我写本周周报」，看它会不会自己触发；再用 `@weekly-report` 显式调用，确认能跑通。乱触发就收窄 description，不触发就补用户常说的说法。

技能没反应，按这个顺序查：

- 文件名和路径：必须是 `SKILL.md`，放在技能目录根部。
- 调用 ID：用路径推导出的 ID，不是 frontmatter 里的显示名。
- description：不能为空，要包含用户会说的触发词。
- 权限和重复：没有被 `deny`，没有同名技能被后注册的来源覆盖；改完重开会话。

技能里要放脚本时，下面几条能让它更稳。

- 脚本放 `scripts/`，在 `SKILL.md` 里用相对技能目录的路径引用；脚本自己处理输入输出路径，别写死绝对路径，依赖在文件开头或 `references/` 写清。
- 出错时打印清楚的错误信息，并用非 0 退出码结束；`SKILL.md` 里明确写「把 stderr 原样贴给用户，不要继续编数据」。
- 先在终端里跑通脚本，再把它接进技能；计数、排序、格式转换、字段校验交给脚本，需要判断的留给模型。
- 不可逆的动作加确认，或者放到权限系统后面；不要只在 `SKILL.md` 里写「请谨慎」。

做完这些，你手里就有一个能触发、能跑、能改的周报技能。剩下的七道题，用来检查你有没有把机制和操作混在一起。

## 8. 检查一下你懂了没

Q1　每次都把同一段「周报格式」粘给它，最该做的改造是什么？

- 换一个更聪明的模型
- 把这段话写得更长更详细
- ✅ 做成 Skill，让 agent 自己记住做法
- 把周报格式写进 MCP 工具的名字里

答对时：对。反复教还教不稳，就说明这套做法不该只留在对话里；写成文件，agent 每次按文件做。

答错时：换模型或写长提示词都解决不了重复交代；把固定做法放进文件，才是 Skill 要解决的事。

Q2　装完之后，agent 多了「按格式写周报」的本事，它多出来的是什么？

- 一段网络连接
- 一个新动作
- ✅ 一套做法
- 一个新模型

答对时：对。装完看它多了什么：多出动作的是 MCP，多出步骤、格式和判断的是 Skill。

答错时：网络连接和新动作属于 MCP；「按格式写」是一套做法，属于 Skill。

Q3　模型决定「要不要用某个 Skill」，第一依据是什么？

- SKILL.md 的正文写得够不够长
- Skill 文件夹的命名顺序
- ✅ description 写得清不清楚
- 上一次用它的时候有没有成功

答对时：对。平时只有 `name` 和 `description` 进技能列表；description 含糊，模型不会打开正文。

答错时：正文要等模型决定用之后才读；目录顺序只影响同名覆盖。

Q4　为什么 Skill 要做「渐进式加载」？

- ✅ 上下文是稀缺的，塞多了又贵又乱
- 模型一次读不了太长的文件
- 文件太大，下载会比较慢
- 技能多了以后会互相冲突

答对时：对。上下文按 token 计费，塞得越多越贵，也越容易分散注意力。

答错时：根因是成本和干扰，不是下载慢，也不是模型读不了长文件。

Q5　导入一个别人做的 Skill，哪条要求是对的？

- 随便什么压缩包，解压到目录就能直接用
- ✅ 根目录放 SKILL.md，头部写名字和描述
- 只要脚本能跑，说明文件可以完全不管
- 必须做成 exe 安装包，双击才能装

答对时：对。根目录要有 `SKILL.md`，头部 YAML 写 name 和 description；导入前还要看来源和脚本。

答错时：它不是 exe，也不是随便的压缩包；根目录必须有 `SKILL.md`。

Q6　只有一个产品用、只跑本地脚本的小工具，最省事的做法是？

- 先搭一个本地 MCP server
- ✅ 写一个 Skill，配一个脚本
- 两个都搭上，图个双保险
- 把模型换成更大一号的试试

答对时：对。单产品、本地脚本，Skill + 脚本更轻；多客户端复用再抽 MCP server。

答错时：单产品不必先上协议；Skill + 脚本跑通后，有复用需求再抽 MCP。

Q7　朋友发来一个别人做的技能包，功能正是你需要的。装之前该做什么？

- 直接导入，能用就行
- ✅ 先读一遍 SKILL.md 和脚本，确认来源可信
- 看文件大小没超过 10MB 就装
- 改个名字再导入，免得跟别的技能冲突

答对时：对。技能里的指令和脚本会以你的权限运行，只装可信来源，装前读一遍。

答错时：大小和名字都不是安全关；10MB 只是 TeleAgent 的导入上限，装前先读 `SKILL.md` 和脚本。

## 收尾

能力接上了，做法也装进来了。但还有一类活，一个 agent 干不完：什么时候叫帮手、怎么分工、交接什么，下一课讲。你会遇到需要同时查资料、写代码、做验证的任务；一个 agent 串行做，时间和上下文都不够。
