## 开场（页首框）

你是否经常这样做：让agent写周报时，详细列了好多条要求；下周写周报，这些要求又罗列一遍，你有没有想过：agent能不能记住我每次的要求，只要我说写周报，它就能按照我的要求帮我写周报？

能。把做法放进一个文件夹，agent 用的时候自己翻开照做，这就是 **Skill（技能）**。

**学完这课，你能**：说清什么是skill技能、为什么正文要按需加载；用 TeleAgent 创建一个技能、测它、改它；分清 MCP 和 Skill 各管哪层、什么时候该用哪个。

## 主线（记住这一句的框）

**MCP 给能力，Skill 给做法**。

## 1. 工具是厨具，技能是菜谱

「先汇总完成项，再列问题，最后写下周计划；缺数据就先问，不要编。」每次让 agent 写周报时，都得提醒它按上面的要求来做。写周报的要求其实是固定不变的，但每次写周报都会新开一个会话，新会话里之前聊过的内容就没了，所以每次都要把同样的要求再重复一遍。

Skill 就是把这些重复的要求写成文件：只需要写一次，agent 每次都会读取这个文件，发现当前任务是写周报时，就按文件写好的要求来执行。

打个比方，工具好比厨具，Skill 就好比菜谱。你可以用厨具切菜炒菜，也可以照着菜谱先切菜、再翻炒。但不管是直接使用厨具，还是照着菜谱做菜，动手的始终是 agent。。 

## 3. 技能就是文件夹

所以，一个Skill，本质上就是一个文件夹，里面包含一些 Markdown 格式的文本文件，这些文件就是所谓的“菜谱”，外加可选的脚本和资料。每次harness软件启动的时候，都会去固定的位置扫描这些技能文件夹，读取每个文件夹里面的技能文件。

## 4. 其它需要知道的

大部分harness软件都会读取当前目录下的agents.md文件，为了兼容claude，也可能读取claude.md文件。





做法能装进 agent，是因为它先变成了文件。文件才可装、可改、可传、可以按版本管理。一个 Skill 就是一个目录：

```
weekly-report/
  SKILL.md            ← 入口：frontmatter + 正文
  reference.md        ← 补充资料，用到才读
  scripts/
    collect.py        ← 可选：确定性步骤交给脚本
```

`SKILL.md` 自己长这样：

```
---
name: weekly-report
description: 当用户说「写周报」「汇总本周工作」时，按团队模板生成周报。
---

# 周报

## 什么时候用
...

## 怎么做
1. ...

## 输出格式
...

## 失败怎么救
...
```

`SKILL.md` 头部的 YAML（一种一行一条「名字: 值」的配置文本）叫 **frontmatter**，`name` 和 `description` 是必填。`description` 写的是「做什么 + 什么时候用」，它是模型认出这个技能的第一关。正文是第二层：什么时候用、怎么做、输出什么、失败怎么救。

## 3. 看起来一样，多出来的东西不一样

在技能广场里，两样东西长得一样：下载、装上、agent 变能干。上一课装天气工具时你已经见过：连上之前问，它只会说查不了；连上再问，就能查出来。分辨装进去的是什么，也用这个土办法——装完看它多了什么。装了周报 Skill，agent 多的是「按你们的格式写周报」这个做法；装了天气 MCP，多的是「查天气」这个动作。

「装上」的动作像，里面装的东西不一样。MCP 装的是一个 server 的配置：连上后 server 报一份带参数的工具清单，模型照着清单挑动作。Skill 装的是一个文件包：会话开始时产品扫到它，只把 name 和 description 放进模型能看到的技能目录，正文等模型决定用了才读。

一个是能调用的动作，一个是要不要翻开的手册。所以严格说，Skill 本身不是一个可调用的工具：它是被加载的说明书，真正执行动作的才是工具。

用同一个任务检验最清楚。你说「写周报」，Skill 决定先汇总什么、再列什么、输出长什么样、缺数据怎么办；周报里要「拉出本周的提交记录」，那一步是工具的事，工具可以在 Skill 的流程里被调用。做法里可以调用能力，但两者不是一回事。

为什么容易混？产品把入口做成了同一个样子，把「装的其实不一样」这条线索盖住了。真正的分层是：MCP 站在「怎么接」那一层，它是对外的标准接口，谁来都能接；Skill 站在「怎么做」那一层，它是给某个 agent 的说明书，换个产品不一定认得。接下来只看做法这一层。



## 4. 它怎么被发现：目录常驻，正文按需

Skill 不是 MCP 那种「连接时由 server 报一份工具清单」。它的发现走另一条路：会话开始时，产品扫一遍已安装的 Skill，只读每个 `SKILL.md` 头部的 `name` 和 `description`，把这一条放进模型能看到的技能目录。正文不在里面。

这份目录放在哪，各家产品不一样。Anthropic 的 Agent Skills 把它放在系统提示里；OpenCode 有一个专门加载 Skill 的 `skill` 工具，可用 Skill 的 name 和 description 就写在这个工具的说明里；TeleAgent 的手册只写到添加、启用和 `@`，没写内部放在哪。位置不同，做法是同一个：先给模型一份薄薄的目录，正文按需读。

模型觉得某个 description 和当前任务对得上，才去读 `SKILL.md` 正文。模型只决定用不用；真去读，在 OpenCode 里是调那个 `skill` 工具，由工具把正文装进上下文。正文进来之后，才轮到它提到的 `reference.md` 或脚本。这就是渐进式加载的三层：

1. **平时**：每个已安装 Skill 的 `name`＋`description` 进技能目录，只有名字和说明这两条。
2. **模型觉得用得上**，才打开 `SKILL.md` 正文。
3. **正文提到某个文件**：再按需打开那个文件，或运行里面的脚本。

为什么非要这样？因为上下文是稀缺资源：进上下文的东西都要花钱、占位置，还会互相干扰（[LLM 底层第 3 课](../../lessons/llm/0003-kv-cache-and-prompt-caching.html)讲过）。渐进式加载就是「不看不用的，连打开都不打开」，和 [RAG](../../lessons/rag/0001-why-retrieval.html) 是同一个思想：按需取资料，而不是把整份文档塞进去。这也说明 `description` 为什么是第一关：平时它只有这一句话的机会。

## 5. 在 TeleAgent 里做一个

TeleAgent 把创建技能做成了两个入口：技能广场右上角的「创建技能」按钮，或者直接 `@` 技能孵化器（手把手引导你从零创建、迭代技能）。入口名各家产品可能不同，产物都是 `SKILL.md`。这一节按 TeleAgent 2026-10-18 的手册来。

动手前先想清两件事：这个技能只干什么？用户说什么话时该用它？别一上来就要「万能助手」。

然后点「创建技能」，用自然语言把需求说全。可以照这个模板：

```
帮我创建一个技能：
- 名字：weekly-report
- 什么时候用：用户说「写周报」「汇总本周工作」时
- 输入：本周的日报/任务记录/提交记录
- 步骤：先汇总完成项，再列风险，最后写下周计划
- 输出格式：Markdown，三段：本周完成 / 风险 / 下周计划
- 边界：缺数据就先问，不要编；不写与工作无关的内容
```

等它生成，去「我的技能」里启用。只有启用的技能才能被 `@` 引用；启用上限是 50 个，别把不用的都开着。

第一次测试，先手动 `@` 它，别靠自动匹配：在输入框点技能按钮，或者直接打 `@` 从列表里选。例如：

```
使用 @weekly-report，把这周的日报汇总成周报。
```

TeleAgent 的手册明确说：不指定技能时系统会自动选，但匹配不如手动指定准。第一次测试、以及技能很多时，先手动 `@`。

最后看它怎么用，再改。用 3 个真实任务测：两个「该触发」的、一个「不该触发」的。看它哪一步跑偏，回去改 `description` 或正文；也可以让 `@技能孵化器` 帮你迭代。TeleAgent 里还能看技能详情、评分；同一技能用满 20 次会触发「技能自进化」（手册提了这个机制，没细说它改什么）；做好的技能可以上架到广场。

另一种是导入现成的 Skill。技能广场 → 导入技能，支持 `.zip`／`.skill`；根目录必须有 `SKILL.md`，头部 YAML 写 `name` 和 `description`，文件不超过 10MB。导入时会过安全审查，有风险会提示；通过后出现在「我的技能」。

自己做的也好，导入的也好，走到这里，你手里就有一个能反复用的技能。接下来是怎么让它被用对。

## 6. 建好只是开始

技能建好了，能不能被用上、用得对不对，头一道关是 description，后面几条决定它用起来稳不稳。

- **`description` 是第一关**：写「做什么 + 什么时候用」，最好带上用户真会说的词（「写周报」「汇总本周工作」）。只写「一个周报工具」等于没写。
- **一个 Skill 只干一件事**：既写周报又审合同，触发词会打架，正文也会互相干扰。拆成两个。
- **正文写成操作手册**：输入、步骤、输出格式、失败怎么救。模型不是同事，不会自己补你们团队的默认规矩。
- **长内容往外挪**：模板、长表格、参考资料放 `reference.md`；照固定规则就能跑、不用模型判断的步骤（拉数据、拼格式这类）放脚本。正文保持短，才省上下文。
- **给例子**：一段「输入 → 期望输出」的样例，比十句形容词管用。
- **用真实任务迭代**：先跑几个真实任务，再改；不要凭想象一次写完。Anthropic 的建议也是「从评估开始，观察它在哪卡住，再补 Skill」。
- **安全**：导入的技能可以带指令和脚本，等于别人给你装了一段程序。只装可信来源，装前读一遍 `SKILL.md` 和脚本。

这些功夫，都是为了让技能被反复用。只用一次的事，不值得建 Skill，直接把要求对它说清就行。

### 用起来出毛病，先从最常见的地方查

- **技能不被触发**：先看 `description` 有没有写「什么时候用」；再试手动 `@`；最后看它是不是被停用了、启用数是不是到顶。
- **不该用的时候硬用**：`description` 写太宽（「处理文档」），把范围收窄，或拆成多个技能。
- **输出格式不对**：正文里没写清模板/例子；补「输出格式」一节，给一段样例。
- **导入失败**：对着导入的四个条件逐条查——格式、根目录 `SKILL.md`、YAML、文件大小。
- **改了没生效**：改完要保存/更新；旧任务可能还引用旧版本，新开一个任务再测。
- **脚本跑不起来**：依赖没装、路径写死、工作目录不对；先在本机手动跑通脚本，再放进 Skill。
- **技能太多互相抢**：只启用常用的；触发词重叠的合并或拆清。

先查 description、启用状态和手动 `@` 这三处；都没问题，再看正文和脚本。

## 7. 去哪找现成的

Skill 不用都自己写。国内常用的入口有三个（2026-10-18 看，产品会变）。先看格式和权限，再安装。

- **TeleAgent 技能广场**（软件内）：TeleAgent 自己的和社区的技能，创建、导入、管理都在这里。
- **ModelScope Skills 技能中心**（[modelscope.cn/skills](https://modelscope.cn/skills)）：浏览技能，下载后按你的产品要求导入。
- **阿里云百炼 Skill 管理**（[文档](https://help.aliyun.com/zh/model-studio/introduction-to-skill)）：阿里云百炼自己的 Skill 添加即用，自定义 Skill 传 ZIP，自动审查。

三个入口都能拿到现成的包，差别在格式和审核方式；装之前先确认你的产品认哪种格式。安装前还要问清楚：格式对得上吗（ZIP + `SKILL.md`？还是某个平台自己的插件？）· 要什么权限（API key、本地文件、云账号？）· 来源可信吗（技能里的指令和脚本会以你的权限跑）。

## 8. 要动作，还是要做法

MCP 和 Skill 都见过了，回到开头那个混淆：它们在技能广场里长得一样，装完多出来的东西不一样。判断只需要一问：我要的是一个新动作，还是一个做法？

| 场景                                                                         | 更合适                             |
| ---------------------------------------------------------------------------- | ---------------------------------- |
| 要教 agent「什么时候用、按什么步骤做、输出什么格式」                         | **Skill**（流程里可以调 MCP 工具） |
| 要模型直接看到一个可调用函数（名字/说明/参数）                               | **MCP 工具**（或产品内置工具）     |
| 只有一个产品、一个团队，工具只跑本地脚本                                     | **Skill + 脚本**（更轻）           |
| 同一能力要给多个产品、多人用，或要让不同产品都能发现它、照同一份参数说明来调 | **MCP**                            |
| 数据在远程，要验身份、限用量，key 这类凭据不想进模型上下文                   | **MCP**（凭据握在 server 手里）    |
| 一次性小工具，只有你一个人用                                                 | **直接写函数**，别上 MCP/Skill     |

本地的 MCP 和带脚本的 Skill，功能上确实有重合。一个本地 MCP server 是「跑在本机、把能力暴露出来的程序」；一个 Skill 也能带脚本在本机跑。只服务一个产品、一个团队，很多本地 MCP 确实可以用 Skill + 脚本替掉。

但「重合」不等于「一样」：Skill 管「这件事怎么做」，MCP 管「这个能力怎么被接上」。两者常常配合：Skill 写流程，流程里调 MCP 工具；或者先用 Skill 脚本跑通，等要被多个客户端复用时再抽成 MCP server。

## 9. 检查一下你懂了没

**Q1　每次都把同一段「周报格式」粘给它，最该做的改造是什么？**

- 换一个更聪明的模型
- 把这段话写得更长更详细
- ✅ 做成 Skill，让 agent 自己记住做法
- 把周报格式写进 MCP 工具的名字里

答对时：对。做法反复教、还教不稳，就该变成文件——这正是 Skill 装的东西。
答错时：做法不该散在对话里；工具的名字也装不下一套流程。

**Q2　装完之后 agent 多了「按格式写周报」的本事，它多出来的是什么？**

- 一段网络连接
- 一个新动作
- ✅ 一套做法
- 一个新模型

答对时：对。土办法：装完看多了什么——多做法的是 Skill，多动作的是 MCP。
答错时：动作是 MCP 给的；「按格式写」是步骤和判断，是做法。

**Q3　模型决定「要不要用某个 Skill」，第一依据是什么？**

- SKILL.md 的正文写得够不够长
- Skill 文件夹的命名顺序
- ✅ description 写得清不清楚
- 上一次用它的时候有没有成功

答对时：对。平时只有 name 和 description 进技能目录——description 写得含糊，Skill 就等于不存在。
答错时：正文要等模型决定用之后才打开；第一关是 description。

**Q4　为什么 Skill 要做「渐进式加载」？**

- ✅ 上下文是稀缺的，塞多了又贵又乱
- 模型一次读不了太长的文件
- 文件太大，下载会比较慢
- 技能多了以后会互相冲突

答对时：对。不看不用的，连打开都不打开——这就是省 token 的核心手段。
答错时：根因在成本和干扰：进上下文的东西都要买单，还容易跑偏。

**Q5　导入一个别人做的 Skill，哪条要求是对的？**

- 随便什么压缩包，解压到目录就能直接用
- ✅ 根目录放 SKILL.md，头部写名字和描述
- 只要脚本能跑，说明文件可以完全不管
- 必须做成 exe 安装包，双击才能装

答对时：对。技能就是文件包：根目录 SKILL.md + YAML frontmatter；还要过安全审查。
答错时：它不是 exe，也不是随便的压缩包：根目录必须有 SKILL.md，头部 YAML 写清名字和描述。

**Q6　只有一个产品用、只跑本地脚本的小工具，最省事的做法是？**

- 先搭一个本地 MCP server
- ✅ 写一个 Skill，配一个脚本
- 两个都搭上，图个双保险
- 把模型换成更大一号的试试

答对时：对。单产品、本地脚本，Skill 更轻；等要被多个客户端复用，再抽成 MCP server。
答错时：单产品不需要先上插口标准；Skill + 脚本跑通后，需要复用再抽 MCP。

**Q7　朋友发来一个别人做的技能包，功能正是你需要的。装之前该做什么？**

- 直接导入，能用就行
- ✅ 先读一遍 SKILL.md 和脚本，确认来源可信
- 看文件大小没超过 10MB 就装
- 改个名字再导入，免得跟别的技能冲突

答对时：对。技能里的指令和脚本会以你的权限跑，等于别人给你装了一段程序——只装可信来源。
答错时：大小和名字都不是安全关：技能会以你的权限跑它的指令和脚本，装前先读内容、确认来源。

## 收尾段（小测后面）

能力接上了，做法也装进来了。不过还有一类活，一个 agent 干不完：什么时候该叫帮手、怎么分工，下一课讲。

## 一手资料（页脚框，一般不动）
