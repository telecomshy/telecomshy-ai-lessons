## Q1 · 本地部署时偶尔 JSON 解析失败，是引擎没有这个功能吗？

你在本地跑一个模型，让它输出 JSON 供工具解析，结果**偶尔**解析失败。**答案：不是引擎没有这个功能，是这个功能没打开。**

约束解码是**请求级的开关**：请求里没带 schema 或「必须是 JSON」，引擎就当普通生成处理，一个字也不替你挡。它也不是"新版本才有"。这功能好几年了，XGrammar 那套后端 2024 年就有技术报告，现在是 vLLM、SGLang、TensorRT-LLM 结构化输出的默认后端。

那没开的时候，格式靠谁？**靠模型自己写。**写出合法 JSON 靠的是它训练里练出来的格式习惯（第 0 课讲过：语法、习惯都压在那些数字里）。**习惯不是保证**，所以偶尔崩完全正常：初学版演示一里，不加闸那组约三成是废的（玩具分表，量级别当真）。

本地部署还常有第二层：**整条链路没人带这个开关**：客户端或框架发的是普通对话请求。工具调用的 JSON 也是模型自己写、你的代码去解析，解析器只负责"读"、不负责"防"。（学习者本地实测到的"偶尔解析失败"，就是这一层。）

## Q2 · 结构化输出的开关在哪？怎么确认它真开着？

**答案分两层：能力在引擎侧、常备；开不开在请求侧、默认关。**引擎装好就有约束解码的本事（vLLM 文档原话：结构化输出「默认就支持」），可「输出必须长什么样」只有调用方知道。所以开关只能由请求带进来：**请求里带了 schema（「必须长什么样」的说明书）或一个「必须是 JSON」，约束才开**。

「默认是关的」说的就是**请求侧的默认状态**：默认情况下请求都不带约束。引擎侧能配的是「怎么干活」，不是「这条请求要不要约束」。本地跑 vLLM，服务端可选「用哪个约束后端」（`vllm serve --structured-outputs-config.backend`，默认 `auto`）、思考模型里要不要也约束（`--structured-outputs-config.enable_in_reasoning=True`）。托管 API 那头连后端都不用你挑，你能动的就是请求里那块。各家参数名不一样，同一个引擎还会改名。

两个场景各一个最小例子。**场景一：托管 API**（Anthropic 那边，那块配置叫 `output_config.format`）：

```python
import anthropic
client = anthropic.Anthropic()

response = client.messages.create(
    model="…",                                  # 你的模型名
    max_tokens=256,
    messages=[{"role": "user", "content": "把城市提出来：『北京明天下雨』"}],
    output_config={                             # ← 多带的就是这一块
        "format": {
            "type": "json_schema",              # 开关：按说明书出 JSON
            "schema": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            },
        }
    },
)
print(response.content[0].text)                 # {"city": "北京"}——形状被钉住
```

拆开就三件事：**消息照旧发**；**说明书里只要一个 `city` 字段**；**`output_config.format` 就是那个开关**。

**场景二：自己部署的开源引擎**（vLLM，服务起在你自己的机器上）：同一件事、另一套拼写：

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="-")   # 你自己的 vLLM

response = client.chat.completions.create(
    model="…",                                  # vLLM 上挂的模型名
    messages=[{"role": "user", "content": "把城市提出来：『北京明天下雨』"}],
    response_format={                           # ← 同一个开关，换了个名字
        "type": "json_schema",
        "json_schema": {
            "name": "city",
            "schema": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            },
        }
    },
)
print(response.choices[0].message.content)      # {"city": "北京"}
```

vLLM 还有第二种拼写：把说明书塞进 `extra_body={"structured_outputs": {"json": …}}`（约束形态另有固定选项／正则／文法几种，背后跑的是 xgrammar 或 guidance）。⚠ **别照抄旧教程**：vLLM 旧的 `guided_json` 那一族参数在 v0.12.0 已经移除，新写法是 `structured_outputs`。拿旧写法跑新版本，可能"写了不生效"，甚至直接报错。**照当前版本的文档写。**

还有个能让效果更好的做法：**在提示词里也把 schema 写清楚**：vLLM 官方说这样通常会明显变好。

**配完怎么知道它真开着？亲手造一个「不约束必翻车」的场景，看它翻不翻：**

- **盯字段**：把说明书定成必须有某个字段（比如 `city`），连发几十次，看是不是永远带着——漏一次就是没生效。
- **故意诱导**：让它多写个字段、少个引号，看会不会被挡回去。没约束的模型迟早写出来；约束开着，就永远见不到。

另外两件事约束不管，别误会：**内容对不对**（它只管形状）；**拒答**（拒答优先于格式，初学版讲过）。

## Q3 · 「这招不是免费的」——代价具体有哪些？

**代价有三笔：第一次用要等编译、说明书改了要重编、说明书太复杂会被直接拒掉。**

语法得先**「编译」成机器能跑的规则**。**同一份说明书第一次用会多花一点时间**。编译结果按 **24 小时**缓存（Anthropic 的口径，从最后一次用起算）。**改了说明书就得重编**，还会让这一轮对话的缓存作废（同[第 3 课进阶 Q1](../../lessons/llm/0003-kv-cache-and-prompt-caching-deep.html#q1-thinking)；只改说明书的 `name`/`description` 不作废）。

第三笔：**说明书太复杂会被直接拒掉**：Anthropic 的说法是"编译不出来"，返回 **400**，另有 **180 秒**兜底超时。所以参数别一口气堆满：**可选参数越多、编译越贵**（Anthropic 文档原话是"指数级编译代价"），上限 **24 个可选参数**（严格工具调用上限 20 个），超了就吃那个 400。

## Q4 · 约束解码和投机解码能同时开吗？两个承诺矛盾吗？

**答案：不矛盾，能同时开。**两个承诺不在一个层面上：**约束解码改的是"抽样池"**：把非法字从候选里划掉，定义"合法答案是哪些"。**投机解码改的是"怎么抽"**，小模型打草稿只是**提案**，大模型验收时按定死的规则**拒收**不合格的（这一步叫**拒绝采样**）。草稿要是提议了非法字，验收那关过不去。

所以两个都开时，输出应当跟「只开约束、不开草稿」那次**一模一样**：**既合法**（约束的承诺），**又跟不开草稿时一致**（投机的承诺）。vLLM 文档有两处佐证：「Lossless guarantees」一节明说它的拒绝采样器**跟目标分布一致**、贪心采样开不开草稿结果相等。「已知不兼容」清单里**没有结构化输出**（列的只有流水线并行和旧版本的 draft model 限制）。

边界照实说：所谓"无损"是**在硬件数值精度范围内**：浮点细微差异仍可能有，和初学版演示三同一个来源。

## Q5 · 为什么分四层，不分成「模型＋外壳」两块？

**答案：因为「外壳」这个词装不下网关和引擎。**它们都在服务端那头。出了事，既不是模型的锅，也不是你代码的锅，**两分法里根本没有它们的位置**。分四层，才能把「格式坏、限流、变慢、停在哪」逐个落到具体某一层、某一家。

「Agent ＝ 模型 ＋ 外壳」把世界切成「模型」和「其余一切」两半（模型是发动机、周边程序是车壳），可「其余一切」里至少有三种命运完全不同的东西：

- **你的程序**：归你管，改代码行为就变；
- **API 网关**：服务商门口的「前台」，验身份、管配额、计费；
- **推理引擎**：服务商的「车间」，排队、挑字、划掉非法字都在这层。

排查问题时区别就来了。拿两件事对号：

- **429 和 529 的修法相反**：429 是网关在管你的配额（撞到月度花费上限的那种，重试没有意义），529 是引擎忙不过来（等一会儿再试）。两分法下这两个都会被记进「模型/服务不行」的糊涂账。
- **「同一个模型换一家部署，同样的参数不保证挑出一模一样的字」**。换掉的正是引擎这一层：权重文件一个字节没动，动的是挑字的默认值、计算精度、执行顺序。两分法里这个变量无处安放，你会误以为「模型变了」。

所以这四层是给排查用的地图，问法固定两步：**这个行为是哪一层干的 → 那层归谁管、谁能改**。「模型＋外壳」讲故事够用，修问题不够用。

## 检查一下你懂了没

**Q1　本地跑模型输出 JSON，偶尔解析失败，最可能的原因是？**

- ✅ 这个开关是请求级的，整条链路根本没人打开它
- 模型参数太少，写 JSON 的能力还不够
- 引擎版本太老，根本没有结构化输出这个功能
- 显存不够用，生成到一半掉了链子

答对时：对。这是请求级的开关：没带 schema，引擎就当普通生成处理。
答错时：不是功能缺失：这功能好几年了，是开关没打开——没开就靠模型自己的格式习惯，偶尔崩很正常。

**Q2　想让输出稳定符合 schema，这份额外的配置应该加在哪里？**

- 写进提示词里，用更严格的措辞反复要求它
- ✅ 加在请求里，带 schema 或 JSON 开关
- 装到服务器上，部署时给引擎传一个启动参数
- 放进权重里，换一个专门练过输出格式的模型

答对时：对。「配置」就是请求里多带一样东西：一个 schema，或者一个「必须是 JSON」的开关。
答错时：开关在请求里，不在提示词、不在权重——服务端只有「用哪个后端」这类配置，没有替你约束的总开关。

**Q3　怎么确认约束解码真的开着？**

- 看服务端日志里有没有 constrained
- 直接问模型「你现在是不是带着约束」
- ✅ 亲手造一个「不约束必翻车」的场景，看它翻不翻
- 连发两次，看两回的字数是不是完全相同

答对时：对。约束的本事是「让错的路不存在」——造一个不堵必翻车的场景，看它还翻不翻。
答错时：日志、问模型、比字数都不作数；盯一个「不约束必翻车」的场景，漏一次就是没生效。

**Q4　结构化输出「不是免费的」，代价是哪几笔？**

- 每个字都要多算一遍，生成速度明显变慢
- 回答内容更容易错，因为候选被划掉了太多
- 按 schema 的字段数量收费，字段越多越贵
- ✅ 首次编译要等、说明书改了要重编、太复杂会被拒

答对时：对。三笔都在「编译」这件事上：第一次用要等、改说明书要重编、太复杂直接拒（400）。
答错时：代价是编译那三笔——不是变慢、不是掉准确率、不是按字段收费。

**Q5　约束解码和投机解码同时开着，输出会怎样？**

- ✅ 又合法、又跟不开草稿时一模一样
- 草稿那招自动关掉，只剩约束还在起作用
- 会打架，这两个开关本来就不能同时开
- 约束那招自动关掉，非法字又会漏出来

答对时：对。约束定义「合法答案是哪些」，草稿改「怎么抽」——验收那关会拒收非法草稿，两个承诺不打架。
答错时：不矛盾：草稿只是提案，大模型验收时拒收不合格的；输出既合法，又和不开草稿时一致。

**Q6　排查问题时，为什么「Agent ＝ 模型＋外壳」两分法不够用？**

- 因为外壳的代码量加起来比模型本身还要大
- ✅ 因为网关和引擎都在服务端那头，两分法没它们的位置
- 因为模型有时候也会自己伸手去调用工具
- 因为外壳一般不和模型部署在同一台机器上

答对时：对。出事的常常是网关和引擎——既不是模型的锅，也不是你代码的锅，两分法里没它们的位置。
答错时：跟代码量、部署位置都无关：网关和引擎这两层在两分法里无处安放，分层才找得到修法。

## 一手资料（页脚框，一般不动）

- [Anthropic — Structured outputs（官方文档）](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)：结构化输出是请求里的 `output_config.format`；改它会让这一轮对话的前缀缓存作废。**Q2 最小例子的请求形状照这页抄**（2026-10-13 当场抓：`output_config={"format": {"type": "json_schema", "schema": …}}`）。Q3 的三笔代价全出自这页：**编译结果按 24 小时缓存**（从最后一次用起算）· **改 schema 要重编**（只改 `name`/`description` 不作废）· 可选参数上限 **24**（严格工具调用上限 20）、带 `anyOf`/类型数组的参数是**指数级编译代价**，超限返回 **400**「编译不出来」，另有 **180 秒**兜底超时。
- [vLLM — Structured Outputs（官方文档）](https://docs.vllm.ai/en/latest/features/structured_outputs/)：请求级约束形态全表（固定选项／正则／JSON schema／文法），后端是 xgrammar 或 guidance；**旧的 `guided_json` 那一族参数已在 v0.12.0 移除**，新写法是 `response_format`／`structured_outputs`（Q2 的 vLLM 拼写照这页抄，2026-10-13 当场抓）。同页另有两句，是 Q2「引擎侧是配置、不是总开关」的出处：结构化输出「**supported by default in the OpenAI-Compatible Server**」（能力常备）；服务端可配 `--structured-outputs-config.backend`（默认 `auto`）与 `--structured-outputs-config.enable_in_reasoning=True`（思考模型里也要约束时）。
- [XGrammar（开源约束解码引擎）](https://github.com/mlc-ai/xgrammar)：「保证输出 100% 的结构正确」，且是 vLLM、SGLang、TensorRT-LLM 等引擎结构化输出的默认后端——Q1 里"不是新功能"的出处。
- [vLLM — Speculative Decoding（官方文档）](https://docs.vllm.ai/en/latest/features/speculative_decoding/)：Q4 的两处佐证——「Lossless guarantees」（理论无损**在硬件数值精度范围内**；拒绝采样器**跟目标分布一致**；贪心采样开不开草稿结果相等）与「Known Feature Incompatibility」清单（只列流水线并行、旧版 draft model；**没列结构化输出**）。
- Q5 的两处依据：429／529 的归层出自 [Anthropic — Errors（官方文档）](https://platform.claude.com/docs/en/api/errors)（429 管配额、529 是过载）；「换一家部署，同参不保证挑出一样的字」出自 [vLLM — SamplingParams（官方 API 文档）](https://docs.vllm.ai/en/latest/api/vllm/sampling_params.html)——它自己写着**批大小变化会让 logprob 和输出概率变化、同一请求两次可能不同**。
- Q1 末尾"本地部署偶尔解析失败"来自**学习者的本地实测观察**（不是文档）；"不加闸约三成是废的"来自初学版的配套脚本（玩具分表，量级不是真实模型的成绩）。详见 [RESOURCES.md](../../RESOURCES.md)。
