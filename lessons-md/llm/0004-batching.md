## 开场（页首框｜先别急着学，聊两句）

你发一个请求，等几秒，字就一个一个出来了。可那台机器只有一张显卡，**它同一时刻还在给别的几十上百个人回消息**。

它到底怎么做到的？**你并不是在跟一大堆人抢同一台机器**。你排着队，轮到你了，就从排队里挑一批人，你和他们凑成一批一起被算。

**它不是「同时」，是「排队 ＋ 拼车」。**一趟车坐的人越多，每个人分摊的车钱就越少。这也是模型 API 能卖得便宜的原因之一。

**学完这课，你能**：把「一张卡怎么同时服务几十上百个人」讲明白；看懂「多」和「快」这笔账；并且知道它的天花板卡在哪。

【选读框｜一条主线，记住它就不会晕】

写答案的每一轮，模型都要**把权重搬一遍**，而搬的时候计算单元大半在干等。**整门课只问一件事：这一趟搬运，能同时服务几个人？**

批越大 → 一起算的人越多、显卡越不闲，但每个人等得越久。批再往上加 → **显卡的算力已经用满，吞吐不再涨，只剩更慢。**

## 1. 你的请求到底经历了什么

先接上[第 2 课](../../lessons/llm/0002-prefill-vs-decode.html)：你发过去的那一整段输入，第 1 轮一次算完（术语叫 **prefill**）。**之后每轮只往外蹦一个字，每蹦一个字整条流水线都要重走一遍**（术语叫 **decode**）。**本课讲的就是后面这一段。**

这段话里有两个词后面一直用，先说清它们是什么：

- **权重（weights）** ＝ 模型里那些**训练学出来的参数**，本课里好比「同一把尺子」（[术语表](../../reference/glossary.html#weights)）。**所有请求用的是同一份**，它不会因为人多而变多。
- **KV cache** ＝ **每个人自己攒下的那份历史**，第 2、3 课那个「货架」。一个人一份，**互相不通用**。

这两样东西**不是一回事**（权重是尺子，KV 是量出来的数），**但有一个共同点：写答案的每一轮，它们都得从显存里搬到计算单元一遍。**本课讲的就是这一趟搬运。

你的请求到了服务商，**先排进一条队**。（[这一整套动作有个名字](../../lessons/llm/0008-who-does-what.html)）**排在同一个队里的，不会全跟你一起算**。轮到你了，服务商从当时排队的请求里挑一批（能挑多少是它自己定的），凑成一批一起上机器。忙的时候队排得长，这段等待就长，**它也算进「你等第一个字等了多久」**（[第 2 课](../../lessons/llm/0002-prefill-vs-decode.html)那条时间线里的第二段就是它）。

这一批人**共用同一份权重**。写答案的时候，**每走一轮，这一批每人往外蹦一个字**。你蹦你的，他蹦他的，**互不干扰**；可机器只被喂了一次权重。**这一批一起被算的请求有几个，就叫「批大小」（batch size）。**

【图】../../assets/batching-one-trip.svg（图片文件不动）

替代文字（alt）：请求先排队，轮到谁就从排队的人里挑一批，共用同一份模型权重的搬运：甲乙丙丁四个人的 KV 并排坐在同一批里，写答案的第 1 到第 5 轮，每轮每人各往外蹦一个字，往右是时间

图注：一个人看是这样，**四个人看还是这样**——只是每一格里多了几个字。图里**上面那一条**是权重（整批人共用、只搬这一次），**下面每一行**是一个人的 KV；**甲就是你的请求**。

那么「同时」到底是什么意思？**同一批人是同一时刻、同一台机器上一起被算的**，不是每人分到一张卡各自并行。只是这台机器一次只推一个字，推完一个再推下一个，**一轮一轮地往前挪**。

要凑的人多，批就大；深夜没什么人，批就小。那时候你很可能**独自一批**。

（agent 慢的时候，先按每一步量出它的耗时，那是你自己的活：[Agent 评估检查单](../../reference/agent-eval-checklist.html)）

## 2. 为什么这样能省钱：那趟车大部分是空的

第 2 课有个结论：写答案那一段**卡在「搬数据」上，不在「算」上**：要算的只有 1 个字，要搬的却是**模型权重**加上这一批每个人的 KV。搬数据的传送带就那么宽，所以计算单元大半在干等。

关键在这儿：**每一轮要搬的那个大头是模型权重，而它跟你一个人还是四百个人没关系。不管谁来，它都得搬一遍。**

要是这一轮只服务你一个，那这趟车就只为你一个人跑一趟：**车大部分是空的**。而「搬」这件事还省不掉（第 2 课：每一轮都得把攒下的历史整份读一遍）。

换个更好想的样子：仓库在城东、客户在城西，每送一趟货，卡车都得开完整的一趟。**只送 1 个包裹太亏**：油钱、司机时间一样没少。所以送货的诀窍是**一趟装满 N 个包裹**：车程没变，货多了 N 倍，**每个包裹分摊到的车钱降到 1/N**。

回到模型上就是：**权重搬一次，同时服务 N 个请求**，那趟「固定开销」被 N 个人分摊了。这就是 API 单价能压下来的原因之一。

以下几个名词后面会反复出现：

1. **吞吐（throughput）** ＝ 整个系统每秒一共往外蹦多少字。
2. **延迟（latency）** ＝ **你一个人**等多久（第 2 课的 [TTFT](../../reference/glossary.html#ttft)、[TPOT](../../reference/glossary.html#tpot) 量的就是它）。

## 3. 动手：跑一遍看数字

```
python exercises/llm/0004-batching.py
```

Windows 终端若中文乱码，先执行 `chcp 65001`。仍是刻意简化的量级模型，重点看相对关系。

先说清脚本用的是哪几个数——它们**写在脚本开头**（`exercises/llm/0004-batching.py`），**不是实测出来的，是设的假设值**：

- **权重 140GB** —— 这个数有出处：[Databricks](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices) 原文写「Llama2 的参数量按 float16 存是 140 GB」。
- **每个请求的 KV 0.5GB** —— 脚本设的量级值。**真值随对话长短变**：同一篇里按 1024 字长的对话算，一个请求是 0.312GB，批到 16 就是 5GB。
- **可用显存 200GB** —— 设定值，取的是大显存卡那个量级。

按这三个数跑出来是这样：

| 批大小 | 每步耗时 | 吞吐 tok/s | 单请求每 token |
|---|---|---|---|
| 1 | 0.141s | 7.1 | 0.141s |
| 8 | 0.144s | 55.6 | 0.144s |
| 32 | 0.156s | 205.1 | 0.156s |
| 120 | 0.200s | **600.0** | **0.200s** |

**批一变大，吞吐涨得飞快，而单请求只慢了一点。**这笔买卖实在太划算了。这就是为什么所有推理服务都在拼命凑批。（脚本跑出来：批 1 → 120，吞吐 84 倍，单请求慢 42%。）

### 但天花板有两道

- **第一道是显存**：权重先占掉 140GB，剩下 `200−140 = 60` GB 才装得下 KV。**0.5GB 是一个请求的 KV**，所以 `60 ÷ 0.5 = 120`，批大小最多 120。
- **第二道不是显存，是算力**：批再大，显卡每秒能做的运算就那么多。到那之后**吞吐不再涨，你等的时间还在涨**——就是下一节那个拐点。（上面这张表只画了「搬运」那一半，所以它只能走到第一道天花板，跑不出拐点。）

## 4. 于是有了「多」和「快」的拉扯

把上面那张表读一遍就是全部：**批越大，机器每秒产出的字越多，但单个请求等得越久。**真实世界的数字也一样。Databricks 在 A100 上测 7B 模型，**批大小 64 时吞吐 14 倍、单请求延迟 4 倍**，两个一起涨。

那要批多大？**看你在乎哪个**：聊天机器人、你的 agent，有人在盯着看，所以最在乎**延迟**；离线批处理（比如一口气总结一万份文档）没人盯着，最在乎**吞吐**。这分工不是我定的：Anyscale 的指标文档就是这么写的：**要互动的场景最在乎「多久出第一个字」和「出字有多快」，批量跑的场景最在乎「每秒一共出多少字」。**

但拉扯有个硬边界：**批大到一定程度，瓶颈就从「搬」变成「算」**。到那之后，再加大批量吞吐几乎不涨、延迟继续变差。纯亏。所以生产环境不会把批开到最大，而是挑一个**最划算的批大小**（[Databricks](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices) 的原话是 "a balanced batch size"）。（[这个拐点是怎么算出来的](../../lessons/llm/0004-batching-deep.html#q2-knee)）

## 5. 服务商在这条路上继续做的三件事

批处理只是开头。工业界又补了三招，**每一招都能用一句话说清它在干嘛**：

- **连续批处理**：谁先答完谁先下车，空出来的座位立刻坐新人。不用等整批人走完才接下一批。
- **PagedAttention**：别再给每个人按「最长的那份」预留一整块显存，改成一页一页按需要分配。省下来的空间能多塞几个人。
- **分块预填充 / prefill-decode 分离**：有人贴一篇超长文章进来时，机器会先花很久把它读完，那段时间别人的字全停着。改法是把长文切成几段，插在写答案的间隙里读；更干脆的做法是给「读」和「写」各配一批机器。

这三招都发生在服务商那边，**对你写代码没有影响**，知道有就行。原理在[进阶版](../../lessons/llm/0004-batching-deep.html)。

## 6. 检查一下你懂了没

**Q1　批处理（batching）为什么能大幅提升吞吐？**

- 让每个请求的计算量变得更少
- ✅ 一趟把模型权重搬给多个请求
- 把模型权重压缩得更小更快些
- 让用户少发一些请求过来就行

答对时：对。权重是每轮必搬的大头，批处理把它摊薄到 N 个请求上。
答错时：关键在「权重每轮都要搬一次」——批处理就是让这一趟同时服务多个请求。

**Q2　加大批大小的代价是什么？**

- 显存占用会变得更少一些
- 模型回答的质量会变差一些
- ✅ 单个请求的延迟会变差一些
- 吞吐会跟着一起掉下去一些

答对时：对。吞吐上去，但每个请求要等更久——这就是「多」和「快」的拉扯。
答错时：批处理不加内容也不减显存，代价是「单个请求变慢」。

**Q3　批处理的天花板主要由什么决定？**

- 看同时在线提问的人有多少
- 看用户的网速和客户端快不快
- 看模型有多少参数、多少层
- ✅ 看显存够装几个、显卡算不算得过来

答对时：对。显存决定能装下几个请求，算力决定再大也没用时的上限。
答错时：两道天花板：显存（能装下几个请求）和算力（批再大也算不过来）。

**Q4　服务商说它同时在给几十上百个人回消息，最接近真相的是？**

- ✅ 凑成一批共用一趟搬运，每人每轮各蹦一个字
- 几百个请求各分到一张显卡上同时算
- 它把每个请求都算完，最后一起返回给你
- 它先算完一个人的，才开始算下一个的

答对时：对。是排队 ＋ 拼车：一批人共用一次权重搬运，每轮每人各往外蹦一个字。
答错时：一张卡不会拆给几百个人。是排队等着凑成一批，每轮每人各蹦一个字，谁也不等谁。
