## 开场（页首框｜先别急着学，聊两句）

同样是跟模型打交道：让它**读**一篇长文档，几秒钟就"看完"了。让它**写**一篇同样长的文章，慢得让人想砸键盘。

更怪的是：读长文档明明是更多的字，为什么反而快？

**模型跑的始终是同一条流水线，但"跑法"分两段**。第一段一次能跑一大批字，第二段一次只能跑一个字。

**学完这课，你能**：说清这两段各在干嘛、为什么要这么分；判断一个请求是"读长文型"还是"写长文型"，谁更慢、谁更贵；并且能回答"为什么首字等了很久、后面却唰唰地出"。

【选读框｜一条主线，记住它就不会晕】

**第一轮跑这条流水线 ＝ prefill（预填充）；后面每一轮 ＝ decode（解码）。**

本课所有结论（谁快谁贵、TTFT、TPOT）都从这一句推出来。

**这两种跑法长什么样，先看这段动画。**它把**一次请求的 5 轮**从头走了一遍：第 1 轮，你给的 4 个 token **一整批一起送**；第 2 轮起，每次**只送刚蹦出来的那一个**。一分多钟，**会一直循环**。下面每讲一节，你都能在这段动画里认出它。

## 1. 先回顾：模型这条流水线

第 1 课我们完整走过一遍，这里只把最关键的一行复述一下：

```
文字 → token 编号 →（查表）→ 向量
     → 穿过 N 层（每层都是：注意力 → 残差 → FFN → 残差）
     → 打分 → 采样（挑一个）→ 下一个字
```

记住三件事就够了：

- **入口**：字先变成**向量**（查嵌入表）。
- **中间**：向量要**一层一层往上走**：几十层，每层都在那根向量上改写一次，**每层都有自己的权重**。
- **出口**：最后那根向量拿去**打分**，再**挑出**一个字。（挑出来的其实是**编号**，要变回向量还得再查一次嵌入表——第 3 节接着说）

**上面那条链，是「跑一趟」的配方。**第 1 课当时只关心一趟怎么走完：走完，一个字就出来了。

可**一次请求，要把这条流水线跑很多趟**。而且，**第一趟和后面几趟，跑法不一样**：

第一趟，你给的那一整段是**一起跑**的。后面几趟，每次只补**一个新字**，**前面那批字不再重新处理**（它们的 k、v 已经存在显存里，直接拿来用）。

**这个差别，就是本课的全部内容。下一节就展开讲。**

## 2. 一次请求，要把这条流水线跑很多轮

关键在这儿：**这条流水线一次只吐出一个字。**所以要写出一整段话，得把它跑很多轮。

```
你的输入（系统提示 + 历史 + 这一句）
   —— 拿「你是谁」→ 回「我是…」举例 ——
        │
        ▼
第 1 轮：把「你」「是」「谁」一起喂进去跑完 → 挑出「我」
        │
        ▼
第 2 轮：只把「我」补进去，再跑一轮 → 挑出「是」
        │
        ▼
第 3 轮：只把「是」补进去，再跑一轮 → 挑出「一」
        │
        ▼
   ……一直跑到结束（遇到结束符，或到长度上限）
```

**第 1 轮**：喂进去的是**你给的一整段**：里面**一个**模型产的字都没有。而且这些字**全是已知的**，所以能**一起**跑。这一轮有个专门的叫法：**prefill**。

**第 2 轮起**：只补**刚刚挑出来的那一个字**。为什么不多补几个？因为再往后的字，得等它先被挑出来，才知道是什么。**后面所有轮都叫 decode。**

**第 1 课**我们知道模型内部分很多**层**，刚才又说吐一个字算**一轮**。这两个词长得像，意思完全不是一回事。我们把这几个词说清楚，免得以后搞混：

- **请求**：一次 API 往返。你发过去，它把答案回过来，这就叫**一次请求**。
- **一轮**：模型内部每蹦出一个字，就要把整条流水线**完整走一遍**。这一趟，就叫一轮。一轮里，那根向量要**穿过所有层**才走得完。
- **层**：模型的**内部结构**，跟对话流程无关。真实模型有几十层，**Transformer 原始论文只有 6 层编码器**。所以「跑一遍」听着像一步，其实是几十步。

最容易错的一处：**一轮 ≠ 一层**。一轮 ＝ 把全部层走完。「再走一遍」是**第二轮**，不是第二层。

一次请求里有 **1 次 prefill ＋ 若干次 decode**，为什么这么分，下一节就说。

## 3. 于是分了两段——为什么第一轮叫「预填充」？

这两段干的事不一样，名字也不一样：

【goal 框】

**第 1 轮 ＝ prefill（预填充）** · **第 2 轮起 ＝ decode（解码）**

分界线只有一条：**这次喂进去的，是你给的字，还是模型自己刚蹦出来的字。**

那为什么第一轮叫「**预填充**」？得先看**注意力那一步**在干嘛（每层里都有这么一步）。

【goal 框】

每个字都会算出自己的三样东西：**q**（我要找什么）、**k**（我是谁）、**v**（我能提供什么）。<br> 然后拿自己的 **q**，去跟**前面所有字的 k** 比一遍；再按比出来的比例，把**它们的 v** 取过来、汇总。

所以你看：**要算任何一个字的注意力，都得用到前面所有字的 k 和 v。**那模型就得把它们**存起来**（存在显存里，正式名字叫 **KV cache**）。

**每个字的注意力都要算，一个都不少**。但这一批可以**一次算完**，不用排队。因为算某个字的 k、v **只用到它自己那一行**，谁也不依赖谁。（为什么"看前面"不等于"等前面"？[→ 进阶版 Q3](../../lessons/llm/0002-prefill-vs-decode-deep.html#q3-parallel)）

于是第 1 轮跑完，有**两个产出**：**摆满 k、v 的货架**（货架就是显存——k、v 一算出来就存下来，后面轮次直接取用），和**第一个字**（也就是这次请求返回给你的、用来回答你问题的那个字）。**pre**（预先）＋ **fill**（填充），名字就是这么来的。（[可点着一步步走的那张图](../../reference/one-request-end-to-end.html)里，货架就是画成了一排货架。）

每一个字，模型都预测了一遍下一个字：「你」预测「是」，「是」预测「谁」，「谁」预测「我」。**但只有最后一个字的预测被留下，前面几个的预测全部丢掉**：前面几个字预测出来的，本来就在你给的那段里；只有最后一个字后面还没写，它的预测才是新的。真正返回给你的，只有从「谁」那儿预测出来的「我」。（**每一轮都是这样**，不只是第 1 轮。）

「返回给你的那个字」只是个方便的说法：严格讲，交到你手上的是**编号**，不是字。轮与轮之间传的都是编号。下面那张图画的是完整过程。

【图】../../assets/every-position-predicts.svg（图片文件不动）

替代文字（alt）：每个 token 都往右预测下一个字：三个 token 向量「你」「是」「谁」各自都预测了一遍 ——「你」预测出「是」、「是」预测出「谁」，这两个预测丢弃；只有「谁」预测出的「我」被取走，再经打分、百分比、挑选，变成一个编号返回给你。

图注：每一轮都是这个过程。**字只是拿来演示的**——真实送进模型的是每行一个 token 向量（n 行 × d 列），不是字。

之后每一轮就轻松了：**一轮最后返回的是编号，不是向量。**预测出的那根向量先变成十几万个**分数**、再变成**百分比**、再**挑出**一个词表编号返回；下一轮就根据这个编号去查**嵌入表**，得到一根新向量，只算**它这一行**的 q、k、v。前面所有字的 k、v **直接从显存取**，不用再算。（这一步中间隔着好几步，摊开见[第 1 课进阶 Q10](../../lessons/llm/0001-from-token-to-next-token-deep.html#q10-sampling)）

**KV cache 省的是"重算"，不是"重读"。**旧的不用重算，但每次还是得把整份读一遍。

## 4. 两段的脾气完全相反

【选读框｜两个术语】

**算力受限（compute-bound）**：卡在"算得不够快"。<br> **显存带宽受限（memory-bandwidth-bound）**：卡在"数据搬得不够快"。

prefill 要把你输入的**每一个字**的 q、k、v 都算出来。这些运算**本质上是矩阵乘法，所以一次能算一整批**：2 万行就一起算完。这一趟干的活很多，时间都花在**"算"**上，所以容易**算力受限**。

decode 每一轮只**新算一个字的 q、k、v**。前面那些字的 k、v 早算好了存在缓存里，不用重算。

**送进去的只有它自己那一行**：新字查表得到 1 根向量，**前面所有字一个都不再送**（它们的 k、v 已经在货架上）。可它**照样"看见"了全部历史**。因为注意力那一步要拿它的 q 去比**全部前面位置的 k**、按比重取全部前面位置的 v。

所以每一层里的账是这样：**送进去 1 行、把货架上的整份（前面所有字）扫一遍**。**读的量覆盖了前面所有行，写的却只有新字那一行**，所以容易**带宽受限**。（**FFN 那一步只处理这 1 行**：它本来就是"每一行各走各的、谁都不看别人"，所以 1 行对它完全够用，它也不用进缓存——[→ 术语表 · KV Cache](../../reference/glossary.html#kv-cache)）

**而且这份会越攒越多**：对话越长，缓存里的 k、v 越多，每一轮要读的也越多。这正好回答"**为什么长上下文让每一步都更慢**"。不过生产上并不会每次都读全部 k、v，滑动窗口只读最近的一部分；能看到多远，见[第 1 课进阶 Q6](../../lessons/llm/0001-from-token-to-next-token-deep.html#q6-mask)。

数据也印证了：decode 时 GPU 的利用率会掉到 **20–40%**（大部分计算单元在干等数据）。prefill 时能跑到接近满载。（这两个数字来自 [Weka 的技术综述](https://www.weka.io/learn/ai-ml/prefill-and-decode/)，是转引的量级证据，不是原始实测）

## 5. 于是有了两个不同的「延迟」

因为两段脾气不同，所以你可能会感受到两种不同的"**慢**"。

**TTFT（首字延迟，首字要等多久）**＝ Time To First Token。从你按回车，到看见**第一个**字。它由 **prefill** 决定：输入越长，等得越久。

**TPOT（每 token 耗时，出字有多快）**＝ Time Per Output Token。开始输出之后，**每个**字花多久。它由 **decode** 决定：这就是你感觉到的"打字速度"。

一条真实的时间线长这样（[ClickHouse 实测](https://clickhouse.com/resources/engineering/llm-inference-latency)：3200 字输入、410 字输出）：

```
① t = 0            你按回车
② t = 0–50ms       网络 ＋ 排队
③ t = 50–400ms     prefill：3200 个输入字，一次全算完（顺手把 K/V 填好）
④ t = 400ms        第一个字出来了                ← TTFT ＝ 400ms
⑤ t = 400ms–12.7s  decode：每 ~30ms 一个字，一轮一个新字  ← TPOT
⑥ t = 12.7s        第 410 个字，结束              ← 端到端延迟
```

**总时间是这么凑出来的：首字等待 ＋（要写的字数 − 1）× 每字耗时。**这个例子里就是 `400ms ＋ 409 × 30ms ≈ 12.7 秒`。**TTFT 和 TPOT 看着都正常，全文却要写 12 秒多。**所以「慢」要分清是哪一种：开头等太久是 TTFT，出来得慢是 TPOT，答案长只是因为字数多。

**TTFT 和 TPOT 不要拿来比谁快。**它们量的是两件不同的事：一个量的是"等第一个字"（就一次），一个量的是"之后每多写一个字"（重复很多次）。那个例子里 decode 每 30ms 蹦一个字，单步比 prefill 那一次还快；**decode 的问题是每一步都得把攒下的 k、v 整份读回来**，这笔搬数据的开销每个字都要付，省不掉。prefill 那一次不用付这笔（k、v 正在被算出来），一次很慢，但只慢这一次。

所以，**想快 TTFT**，就缩短输入，或者把每次都一样的开头缓存起来；**想快 TPOT**，就得减少每一步要搬的东西（量化、换更小的模型、换更快的卡）。

[ClickHouse](https://clickhouse.com/resources/engineering/llm-inference-latency) 文中给的 TPOT 正常区间大约是 **10–50ms**，也就是每秒 20–100 个字。出字比人读得快，人就不会感觉到明显的迟滞，这条就算健康。

我实测的结果：（数字都是相对值，**看谁大谁小就够，不用记具体数**）

| 场景 | TTFT | 生成耗时 | 总耗时 | 相对成本 |
|---|---|---|---|---|
| 读长文（20k 进 / 50 出） | 1.000 s | 1.001 s | 2.001 s | 20250 |
| 写长文（500 进 / 2000 出） | 0.025 s | **21.499 s** | **21.524 s** | 10500 |
| agent 一轮 · 无缓存 | 1.000 s | 1.602 s | 2.602 s | 20400 |
| agent 一轮 · 命中前缀缓存 | **0.025 s** | 1.602 s | 1.627 s | **2850** |

**先看最后两行的对比：命中前缀缓存之后，首字从 1.000s 掉到 0.025s，成本也跟着掉了一大截（20400 → 2850，约 1/7）；可生成耗时一点没变，还是 1.602s。**

为什么生成耗时不变？**因为输入只要批量算一次，输出一个字就要算一次。**缓存省掉的是"把那一大段输入重新算一遍"这笔，而每一个输出字都得自己走一趟 decode。缓存帮不上。**所以上了缓存，模型还是保持原来的语速。**

**模型供应商的输入和输出都按 token 计费，而输出的单价更高。**现在你知道为什么了吗？

输出一个字和读一个字，供应商花掉的算力差很多：读进来的那一大批可以一起并行算（第 4 节那个 prefill），输出只能一个字一个字来（decode）。所以单价更高。

|---|---|---|---|---|
| [Anthropic](https://www.anthropic.com/pricing) | Fable 5.1 | $10 | $50 | 5 倍 |
| Opus 5.5 | $4 | $20 | 5 倍 |  |
| Sonnet 5.5 | $2 | $10 | 5 倍 |  |
| Haiku 4.5 | $1 | $5 | 5 倍 |  |
| [DeepSeek](https://api-docs.deepseek.com/quick_start/pricing) | V4.1-Flash（非高峰） | $0.15 | $0.60 | 4 倍 |
| V4-Pro（非高峰） | $0.66 | $1.98 | 3 倍 |  |

**那要省钱，往哪使劲？输入和输出两头办法不一样：**

- **输入：尽量让缓存命中。**同一段内容每次都要重发，命中就不用重算。具体怎么摆、怎么设断点让命中率上得去，正是[下一课](../../lessons/llm/0003-kv-cache-and-prompt-caching.html)要讲的东西。
- **输出：让模型少说废话、言简意赅。**输出既按高价计费、又没法靠缓存省，每多写一个字都是实打实的钱和时间。让它少说几句，是最直接的省法。

Agent 的提示词、工具定义这些**都是 [agent 框架](../../lessons/agent/0007-harness.html)预先写好的**，普通用户改不了，再叠上完整历史和刚拿回来的观察结果，输入天然就是长文。输出通常只有一句"调用某个工具"。所以 **agent 基本都是「读多写少」型**，缓存正好治它。agent 这块有[专门的课](../../lessons/agent/0001-what-is-an-agent.html)，这里就不展开了。

## 7. 检查一下你懂了没

**Q1　一次请求内部，通常分成哪两个阶段？**

- 先微调模型，然后再推理
- ✅ 预填充，然后逐 token 解码
- 先解码，然后回头做预填充
- 两段同时进行不分先后顺序

答对时：对。先 prefill 把输入那批一次跑完（顺手把 K/V 填好），再 decode 逐字输出。
答错时：顺序是：先 prefill（读输入），再 decode（逐字写）。

**Q2　解码（decode）阶段为什么慢？**

- 它要等用户把答案一个字一个字敲进去
- 它要反复把模型权重重新训练一遍
- ✅ 它要反复把存下的 K/V 整份读出来
- 它要每次联网查完资料再回答

答对时：对。要算的很少，但要搬的数据很多，瓶颈是显存带宽。
答错时：decode 每一步真正要算的只有一行，慢在「把整份 K/V 从显存搬一遍」。

**Q3　首字延迟（TTFT）主要由哪一段决定？**

- 主要由输出长度决定
- 主要由解码阶段决定
- 主要由网络传输决定
- ✅ 主要由预填充阶段决定

答对时：对。TTFT 由 prefill 决定，所以输入越长等得越久。
答错时：TTFT 卡在 prefill：得把整段输入跑完，才能蹦出第一个字。
