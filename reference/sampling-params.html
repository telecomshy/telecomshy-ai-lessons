采样参数：temperature、top_p、top_k、seed

配模型的时候照着抄。机制在 LLM 底层 · 第 1 课进阶 · Q10，这里只放怎么设、什么时候别设。

先划一条边界

这些旋钮一个都不改模型算出来的分（logits）。它们只改"从分表里挑一个字"的规则。

所以调温度不会让模型变聪明或变笨。觉得答案不好，先改提示词或换模型，别指望拧温度。

参数对照表

参数 调什么 常用值 什么时候动它
temperature
（温度）		 换算百分比前把原始分除以 T。T 小更尖，T 大更平 0～0.3 要准
0.7～1.0 要多样		 结果太飘就降，太死板就升。这是第一个该动的旋钮
top_p
（核采样）		 从高到低累加百分比，加够 p 就砍掉剩下的 0.9～0.95
1.0 ＝ 不砍		 明显开始胡说八道（小概率字冒出来）时
top_k 只留分数最高的 k 个，其余出局 40～100
0 ＝ 关掉		 想要一个固定个数的候选上限时。多半保持关掉
seed
（种子）		 固定"抽"这一步的运气 任意整数 要复现、要做对照实验时。想每次不同就别设

同一个参数表里还有几个邻居：max_tokens（最多生成多少）、frequency_penalty / presence_penalty（压住复读）、logit_bias（直接给某个词加减分）。它们管的是生成多少 / 别重复，不是"怎么挑"。

场景 → 怎么设

场景 怎么设 理由
agent 工具调用 / 结构化输出（JSON） 温度 0～0.3，top_p = 1.0 一个参数写错、一个括号没闭合，整条链就歪了
评估 / 回归测试 温度 0 + 固定 seed，并且跑多遍 单次结果不代表能力；而且 T = 0 也不保证逐字一样
创意写作 / 头脑风暴 温度 0.8～1.2，top_p = 0.9～0.95 要的是"第二个想法"，不是"最像的那个"
总结 / 抽取 / 翻译 温度 0～0.3 要忠于原文，不要自己发挥

三条别死记的（理由 + 反例 + 什么时候不适用）

  • 「温度越低越好」是错的。理由：低温＝每一步都挑最像的那个，长文本会一路滑向重复和套话——Holtzman 那篇论文的结论正是"拿最大值当生成目标，对开放式写作不合适"。反例：让它写十个不一样的标题，温度 0 会给你十个几乎一样的。不适用：任务本身有唯一正确答案（工具参数、JSON、抽取）。
  • 「温度 = 0 就能复现」是错的。理由：服务端把多条请求拼在一起算、浮点加法顺序不固定，都可能差上一两个字。反例：同一个请求连发两次，结论等价但字不全同。不适用：真需要逐字一致（哈希比对、快照测试）——那种场景得改用"结果等价"来判分，见 技巧篇 · 第 2 课。
  • 「top_p 和 top_k 一起设更保险」多半是错的。理由：两把刀叠着用，起作用的是更紧的那把，另一个等于没设。反例：top_k = 5 配 top_p = 0.95，实际由 top_k 说了算。不适用：确实要同时卡两个上限（少见）。

带走这张清单

  • 没想法 → 先全用默认（温度 1.0、top_p = 1.0、top_k = 0）跑一遍再说。
  • 结果太飘 → 先降温度，别急着动 top_p。
  • 结果太死板 → 先升温度，还不够再 top_p = 0.95。
  • 开始胡说 → top_p = 0.9 砍尾巴。
  • 要复现 → 温度 0 + seed，并接受可能差一两个字。
  • 要 JSON / 工具调用稳 → 温度低 + 让接口帮你约束格式（结构化输出），别只靠调温度。
  • harness 在替你设 → 它藏起来了不等于不存在。想知道默认值是什么，去看你那个 harness 的配置项。
