KV Cache 与「缓存命中」

两个被混为一谈的「缓存」。分清了，agent 的成本账才算得清。

先分清两个东西

KV Cache 前缀缓存 Prompt Cache
范围 单次请求内部 跨多次请求
目的 逐字生成时不重算前面的词 复用多次请求相同开头的算力
「命中」 自动生效，没有命中概念 开头一字不差才命中

KV Cache（同一次生成内）

  • Attention 里，每个词会算出三个向量：Query（去找别人）、Key（被别人比对）、Value（被取走）。三者都来自同一个词，是三种用途，不是三种信息。
  • 生成是「一次一个词」。写第 N 个词，要用前 N−1 个词的 K/V。
  • 把算过的 K/V 存下来 → 下一个词只算新词的，旧的直接接上。
  • 代价：显存。每个词都要存一对 K/V，随序列长度线性增长。

前缀缓存 / 缓存命中（跨请求）

  • 服务商把「多次请求里开头完全相同的那段」的 KV 张量存起来复用。
  • 缓存的是 KV 张量，不是 token 文本本身（OpenAI 官方文档原话）。
  • 顺序：tools → system → messages，严格前缀匹配。
  • 某一处不同 → 从该点往后的缓存全部失效。
  • 计费：cache read（命中读取）≈ 0.1× 输入价；cache write（首次写入）Anthropic 约 1.25×，OpenAI 新版也可能收费。
  • OpenAI：前缀 ≥ 1024 token 才可缓存，命中按 128-token 粒度；可用 prompt_cache_key 影响路由。
  • Anthropic：显式断点（块上写 cache_control，一次最多 4 个）与自动断点（请求顶层写一个 cache_control，系统标在最后一个可缓存块，随对话增长自动前移）都支持。查找窗口 20 个位置，含断点自己那一块；连着的一串工具调用、连着的一串工具结果，各算一个位置。断点本身不收费——只对写入（5 分钟 TTL 约 1.25×、1 小时 2×）与读取（约 0.1×）计费。缓存有 TTL，默认约 5 分钟。
  • 哪些改动会打断缓存：改早期消息、删消息、调换顺序——都会让从改动处往后的缓存作废（xAI 文档列的三种）。注意后两种：它们一个字的内容都不改，只动结构，照样作废。
  • 并发请求撞不上：Anthropic —— 缓存条目要等第一个响应开始之后才可用，所以同时发几个请求（哪怕开头一样），后几个都读不到。OpenAI —— 缓存存在某一台具体的机器上，请求得被路由到那台才撞得上；流量超过 15 请求/分钟可能触发溢出路由。prompt_cache_key 能让同一段前缀的请求归到一处，但 OpenAI 文档明说它只影响路由，不保证命中、不锁机器（GPT-5.6 及以后路由自动处理，不需要这个 key）。
  • 怎么核对有没有命中：Anthropic —— cache_creation_input_tokens 与 cache_read_input_tokens，两者都是 0 就是没缓存，而且不报错。OpenAI —— usage.input_tokens_details.cached_tokens 与 cache_write_tokens；命中率 = 累计 cached ÷ 累计 input。
  • ⚠ usage 三个字段是提示词的三段，不是三种结果：cache_read ＝ 断点之前、以前存过的那段（0.1×）· cache_creation ＝ 断点之前、这次新算的那段（1.25×）· input_tokens ＝ 最后一个断点之后的那截，按定义就进不了缓存（原价，每次重算）。官方特意强调过：input_tokens 不代表你送进去的全部输入，只代表最后一个断点后面那一截。三者相加才是总输入。
  • 最小可缓存长度：Anthropic 按模型 512 / 1024 / 2048 / 4096 token；不到就不建缓存、不报错。

四家对照：那一刀谁来切（进阶版 Q2 的浓缩）

谁 断点谁来定 读取时往哪找
Claude 你打（块上的 cache_control），或让它自动打在最后一个可缓存块 每个断点往回 20 个位置
OpenAI 你打（prompt_cache_options.mode ＋ 块上的 prompt_cache_breakpoint），或隐式打在最新一条合格消息末尾。⚠ 这两个参数只在 Responses API ＋ GPT-5.6 及以后有；更早的模型只有隐式 显式：最早 2 个 ＋ 最新 50 个断点；隐式：再加往前 20 个合格消息末尾，以及开头那串 developer 消息的末端
Gemini 请求里没有标记：默认隐式缓存（2.5 及以后全部模型默认开，用户什么都不用做）。另有「显式缓存」＝手动创建并管理缓存对象，只在 generateContent 支持 文档未给数字
DeepSeek 没有断点这个概念——默认开启、代码一行不改；系统自己在用户输入末尾／模型输出末尾／检测到的公共前缀／固定 token 间隔切出缓存单元 必须完整对上某个已落盘的单元才算命中

共同的只有三条：前缀一字不差才复用 · 往回找，范围有限 · 写进去要钱。「窗口多大」「谁来切」各家不同，照抄别家的数字没有意义。

还有一个容易误会的地方：断点存的是「从第一个 token 到这一块为止」的整段，不是「这一小段」——两个断点之间不会被单独存成一份。所以改了前面的内容，包含它的那些份一起作废。而写入费只按新增的那一段算（不是每轮重存一遍整段）。

对 agent 的工程结论（重点）

  • 稳定的放前面：系统提示、工具定义、少样本示例、长文档 → 提高命中率。
  • 易变的放后面：用户当前这句话、新的工具结果 / 观察。
  • 别动态改系统提示、别动态增删工具定义、别往中间插内容——都会把前缀打断。
