一次请求，从头到尾

prefill ＋ decode 的完整过程。点「下一步」一步步走——重点看上面货架（KV cache）怎么一点点变满。

先解一个最容易卡住的：同一套流水线，为什么算的量不一样？

计算方法一模一样——变的只是「一次喂几行」。流水线每一步都是矩阵乘法 输出 = 输入的表 × 权重矩阵：

prefill 输入 20000 行 → 一次算 20000 份
decode 输入 1 行 → 一次只算 1 份
读权重 同一张权重矩阵 —— 两段都得整张读一遍

读权重是固定开销，计算量随行数变。prefill 把这份开销摊到 2 万行上，decode 只摊到 1 行上——这就是"一段卡算力、一段卡带宽"的根。

货架 · KV cache（存在显存里）

① 你的输入 已知

你按下回车。发过去的是一整段：系统提示 ＋ 历史对话 ＋ 这一句。

特点：全是已知的——不需要等谁生成出来。这决定了它下一步能"一起算"。

货架：还是空的。

② prefill（预填充） 算力受限

把整段输入一起送进模型，一次走完所有层。每层都是：注意力 → 残差 → FFN → 残差。

  • 副产品 → 每层注意力算出的 K/V，存进货架（KV cache）
  • 主产出 → 最后一个位置的输出，采样出第 1 个 token
瓶颈是算力：一大堆乘法一起做，显卡算不过来才是问题。

③ decode 第 1 步 带宽受限

只喂第 1 个 token（刚蹦出来的那个）。走的是同一套流水线，只是这次只喂 1 个。

  • 读货架里所有历史的 K/V，才能算出注意力
  • 把自己新算出的 K/V 放到货架末尾
  • 产出 → 第 2 个 token
瓶颈是显存带宽：算的量很小，但每步都要把整份货架搬一遍。

④ decode 第 2 步 带宽受限

同样的动作，只是货架又长了一截——所以这一步比上一步略慢。

  • 读货架（更长了）＋ 追加自己那张 → 产出 第 3 个 token
注意：第 2 个字是上一步（decode 第 1 步）产出的，不是 prefill。

⑤ ……一直循环到结束 收束

  • prefill 只在最开头一次；后面每"吐一个字"都是一步 decode。
  • 货架只增不减 → 每扫一次越来越久 → 这就是"写长文慢"的原因。
  • 停止条件：遇到结束符，或到长度上限。
换个说法：输入＝造货（算力），输出＝扫货（带宽）。

这张图最容易看错的三处

① 两段走的是同一套流水线。decode 也做注意力、也做 FFN——别用"走没走完整流水线"来分。

② 分界线是"被处理的那个 token 是谁的"。你发过去的 → prefill；模型自己蹦的 → decode。

③ 第 1 个字是 prefill 产出的。decode 第 1 步产出的是第 2 个字——这里错位一格。
