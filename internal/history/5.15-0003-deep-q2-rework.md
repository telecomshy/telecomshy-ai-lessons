# 5.15 `llm/0003-deep` Q2 重写：「前缀越长越好吗」这个题问错了（2026-10-06 学习者提出）

> 本文件是 `NOTES.md` 第 5 节「决策与教训存档」的原文搬移（内容未改），供「当初为什么这么定」被质疑时查阅。回 [NOTES.md](../../NOTES.md)。

学习者的原话是「解释很晦涩，看不懂」，而且**第二句是元问题**：「断点这个机制，是大部分模型都一样，还是说只有 claude 这样的，要说清楚。」前一句指出了病，后一句指出了**旧稿把一个跨厂商的结论当成 Claude 的细节**。改完的题是《**一个字都没改，为什么还是不命中？**》——按 5.13.3 从读者会问的那句出发。

- **旧稿真正的病不是"难"，是"缺主语"。** 旧 Q2 一上来就说"从断点往回逐个找已经写过的条目，最多往回找 20 个位置"，**而"断点""块""条目"三个词整页没有定义**（`断点` 在全库只出现在目录页和 `0002` 一句"怎么设断点"里）。1.5 写着"术语必解释、定义在后面和没定义一样算违规"，**这页就是照着违反的**。
  - **判据：进阶版问句里出现"以 X 为例"要立刻警觉** —— 它是在用一个具体厂商的实现冒充一条通用机制，把该讲的差异压进灰字括注。差异要**摆到正文**（本轮落成一张两派对照表）。
- **"前缀越长越好吗"这个题本身预设了一个错误的因果**（5.13.3 同族）。真相不是"越长越不好"，而是"**越长能省得越多，但够不够得着是另一回事**"。旧稿的答案（20 块窗口）解释不了标题。**改题不是换个说法，是把因果改正。**
- **旧稿的"更省钱的做法：不缓存动态的那一截"整段被拆掉** —— 因为它给的行动建议（把断点标在稳定内容末尾）是**对的但埋在最后**，而前半句"还有个更省钱的做法"把读者的注意力引到了次要处。现在折进「该标在哪儿」那一条（标在稳定那段末尾 → 变的那截在标记之后 → 每轮新算但不付写入费）。
- **⭐ 写成 JSON 而不是继续用文字描述块（这一条最有用）**：学习者说"块已经在一个请求一眼就可以看出来吧？这样也不用费劲巴拉的用文字描述了"。于是给了**官方原样字段放法**的一个最小请求（`tools` 里最后一个工具挂 `cache_control` / `system` 那块 / 最后一条用户消息那块），**块是数组里每一项这件事一眼可见，不用解释**。
  - **判据（1.4 那条"文字讲不通就配图"的延伸）：结构性的东西——数据结构的字段、协议的形状、请求的分组——直接给原文，比任何文字描述都省。** 文字描述适合讲"为什么"，不适合讲"长什么样"。
- **⚠ 我自己写错了一处、必须记下来**：写过"标在每次都变的那块上（比如提问），就变成每次都存一次、一次也用不上"。**这是错的，而且是最常见的那种错** —— 多轮对话里官方正是**把断点标在最后一条用户消息上**（它下一轮就变成稳定的历史了）。真正会白存的反例是"**同一段模板反复发、每次只有一小块在变**（时间戳之类）"。5.9 已经有一条"举例前先问这个场景在实践中真的会发生吗"，这条是它的**第二例：还要问"在这个结构里它真的错吗"**。
- **"4 个"和"20 个"原来挤在同一段，读起来像"4 个断点、每个能退 20 块"** —— 学习者直接问"不是最多只能 4 个断点吗"。**这是两个不同维度的上限：4 ＝ 你能标几处（槽位），20 ＝ 读取时能往回看几块（窗口）。** 凡是并排出现的两个数，先问"它们是同一种量吗"。
- **⚠ "格"是我造的词，官方没有**（原文是 positions / "20 blocks"）。自造词清掉之后还留了个"格 ≈ 块"的近似说法 —— 同族于 5.9 的 `捡现成`、5.13 的 `新观察`。**判据：讲机制时，优先用官方那个词；造一个近义词等于让读者多记一张词表。**
- **"谁打这个标记"要答，而且只能答成推论**：API 层面是**发请求的一方**写进请求体（Anthropic 两种模式都是请求字段；OpenAI 文档明写"不打就没有缓存"），所以 Claude 网页版 / Claude Code / OpenCode 必然是**它们在底层替你打**。⚠ 但**没有任何产品文档说明它们怎么打**，课里照旧标成推论（5.13.5 的判据）。
- **新术语两条进术语表**（`#cache-breakpoint` / `#fingerprint`）—— 前者全库原先没有落点，后者顺带钉死"**指纹累积 → 改一处、包含它的份一起废**"这条机制（DeepSeek 文档的"each cached prefix is an independent, **complete** unit"是最干净的旁证）。

## 5.15.1 一手资料一处已过时（紧跟 5.13.4 的第二个例子）

**Anthropic 现在有两种缓存模式**：请求**顶层**写一个 `cache_control` → 系统**自动**把断点标在**最后一个可缓存块**上，随对话增长自动前移（旧稿完全没提，所以"写入只发生在你打的断点处"这句对自动模式是错的）。⚠ **官方明确说自动模式踩同一个坑**："it places the breakpoint on the last cacheable block, which in this structure is the one that changes every request"——**"标在每次都变的那块后面会白存"对新旧两种模式都成立**，这条反而更该讲。

- **"OpenAI 也支持断点"这句话离开版本和 API 就是假的**：`prompt_cache_options` / `prompt_cache_breakpoint` **只在 Responses API ＋ GPT-5.6 及以后**存在，更早的模型只有隐式缓存。学习者第一句就是"openai 兼容的请求我好像没看到过断点这个参数啊" —— **他是对的，因为他用的是 Chat Completions 那条路**。
  - **判据（5.13.4 的推广）：厂商能力断言要带三件套 —— 哪个 API、哪个模型版本、哪个模式。** 少一件，读者按自己的代码一对就发现对不上。
  - 顺带查到的两条也进了速查页：OpenAI 的查找边界是"**最早 2 个 ＋ 最新 50 个**显式断点"（不是块数），隐式再加"往前 20 个合格消息末尾"；**GPT-5.6 起"共享前缀自动就可复用"这个旧行为没了**，官方为此单列一节 `A shared prefix is not always a cached prefix`。
- **Gemini 的"显式"不是同一个形状**：它的显式缓存是"**manually creating and managing cache objects**"，且只在 `generateContent` 支持。**所以跨厂商那张表不能只写"支持/不支持"，得写清"是哪一种支持"。** ⚠ Gemini 那一页的显式小节是懒加载的，我只引了页面上明说的两句，**没敢给 API 名**。
- **DeepSeek 那行反而是最好的反例**：默认开启、代码不改，系统自己在"用户输入末尾／模型输出末尾／公共前缀／固定 token 间隔"切出缓存单元，**每个单元都是完整的一份**（这条直接支撑"存的是整段不是区间"）。
