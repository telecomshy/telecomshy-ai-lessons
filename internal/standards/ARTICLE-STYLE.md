# 文章体：课件写作标准

> 适用：`lessons/` 与 `lessons-md/` 的所有正文。写新课、精修旧课、派写作子代理，都以本文件为准。
> 页面零件、互链与交付检查单见 [`COURSE-STANDARD.md`](COURSE-STANDARD.md)；开发流程与核验纪律见 [`PROCESS.md`](PROCESS.md)；改课流程见 [`REVISION.md`](REVISION.md)。

## 一句话

课件是一篇让人从头读到尾的文章。读者读完，能顺着因果说出这件事为什么成立、下一步该做什么。

## 三条判据

1. **遮住所有小标题，仍能读出前后因果。** 读不出，写的是分块清单。
2. **段首那半句删掉，后文会不会散。** 会散，说明它在承上；不会散，它就是垫话。
3. **读出声。** 一个写代码的朋友不会这么说话，就改。

判据只管读得通不通，不管先说什么后说什么。先结论后理由、先场景后问题都允许，因果链不能断。

## 结构

- 一条叙事线走到底，不中途换主角。开头给场景或判断，之后按「问题 → 概念 → 做法 → 边界 → 收尾」推进；开头已经交代过的问题，不重复。
- 上一段留问题，下一段回答。节与节之间写过渡句，说清为什么从 A 讲到 B。
- 标题是叙事节拍，不是主题清单。「先读一遍，再一个字一个字往外蹦」是节拍；「prefill / decode / 批处理」是目录。
- 先场景后概念，或先判断后机制。先写谁在什么情况下做了什么、卡在哪、付出什么代价，再给术语；也可以先说结论，再用机制和例子说明为什么。两种开头一课内只用一种。
- 一个贯穿例子。需要第二个例子时，明说它是类比，别让读者以为换了主角。
- 同一概念只展开一次，后文用一句话回指。
- 顺序服从理解路径：先问题后概念，先主线后分支；具体和抽象的顺序跟着开头走——开头用场景，具体在前；开头给判断，机制在后。

## 段落

- 一段推进一步。段首句带内容；导航句按「作者风格·导航句带新信息」办，纯导航不写。
- 操作写全：去哪找、点什么、填什么、失败长什么样。别用「支持」「提供」一句带过。
- 表格只做对照，清单只做检查。表前说为什么现在看它，表后说它改变了什么判断；清单前有引导句，后有收束句。
- 列表条目写成完整句子。一节不能只有列表、没有正文。
- 每节至少一个具体场景或一次操作走查，让读者看到动作，不只看定义。场景可以压成一句，但压完要能让读者认出「这就是我」；其余细节交给示例、操作段和表格。

## 句子

- 句子要完整：主语、条件、结论写齐。「同一个 ID 出现两份，后注册的那份生效」这种电报句不要。
- 该长就长。一句话 40 到 60 字很正常，条件句不要拆成两句。解释清楚优先于篇幅。
- 一句话只说一件事，但「一件事」可以带条件、原因和结果。删的是并行堆叠，不是从句。
- 不写一行一段的伪小标题（「先说装。」「再说用。」）。小节之间用过渡句推进。
- 动词干活。少用「进行」「实现」「具备」这类空壳动词。
- 术语第一次出现给中文，之后统一叫法；括号里不套括号。需要时用单层括号补一句白话，例如「ID（技能的身份证）」。术语必须当场自洽：「定义在后面」和「没定义」一样算违规，第 N 问／第 N 节用到的字段和术语，得在这一问／这一节里说清（反例见存档 5.15）。
- 用「如果……那么……」「因为……所以……」「先……再……」把关系写出来。连接词是路标，不是废话。

## 具体

- 生动来自具体，不来自修辞。写清人、时间、数字、动作、代价。
- 数字给来由：为什么是 30 秒、为什么是 3 次，能算就算，算不出就说这是经验值。
- 比喻是工具。用完要落回具体动作，不能停在喻体上；比喻会让人误解机制时，再补一句「哪里不成立」，然后回到真实机制。一课一个，已经升为课程术语的可以复用。
- 找不到合适场景就直接讲问题，不硬编。

## 少用与不用

- 删元话语：「值得注意的是」「不难发现」「这里要说明的是」「先定个落点」；「一句话钉死」「这一条值得记住」这类贴标签开场白同族。武断的收口动词也别用，把「钉死」说成「分清／说清」。（范式与同族清单见存档 5.16.7）
- 删自证：「我之所以这样讲，是因为」「这里之所以……是因为」。给事实。
- 删出镜句：数数、宣布总结、布置任务、空预告。判据：这句在说这件事，还是在报道我怎么讲这件事。带「去哪、看什么」的导航句按「作者风格·导航句带新信息」处理。
- 不用空词：赋能、抓手、闭环、底座、心智、生态、沉淀、颗粒度、对齐。
- 不用翻译腔：「在……方面具有重要意义」「提供了一个……的能力」「对于……而言」。写成「X 能做 Y」。
- 不用主持人口吻：「你看」「咱们」「对吧」、感叹号、卖萌形容。语气词全课个位数。「我们」可以用，指读者和作者一起往下走，每节最多一处。
- 「不是 A，而是 B」一节课最多一处，用在真正的转折上。
- 破折号可以补充说明，每段至多一处，不要一句接一句；破折号、括号、分号不三层嵌套。
- 不用压缩短语：「走深一层」「落了地」「拍扁」「一眼看得穿」这类把两个动作压进一个短语的写法，读者得先解压。改写成白话直陈。
- 加粗每节最多两处，不当小标题，不用「**标签**：解释」的格式。
- 收口警句只在第一遍就能读懂时用；读着要解谜的，改成直说。

## 作者风格

作者自己的改写稿里反复出现下面六种做法。它们和前面的结构、段落、句子、具体条款冲突时，以本节为准；本节没写的，按前文执行。三条判据不动。

- **先给判断，再给机制。** 段首直接给结论，机制、数字、例外放后一两句。场景压成一句，压完要能让读者认出「这就是我」；具体的判断留给后面的示例和操作段。一课内「先场景」和「先判断」只选一种。整篇不能只有判断没有具体：每条判断都要落到某个示例、表格或操作上。
- **操作走查到底。** 路径、扫描顺序、失败表现，写到读者能照着做的粒度。涉及优先级时，必须附一个具体顺序实例：「先扫 A，再扫 B，所以 B 里的同名项会盖掉 A 里的」。
- **约束写三层。** 字段和命名这类约束，写齐规则、违反会怎样、最稳妥怎么做。例如 `name` 要与目录名一致；不一致可能导致注册失败；拿不准时就按目录名写。
- **成因要具体。** 「为了兼容」「约定俗成」这类说法，要落到具体的人或事：谁推动的、谁用得最多、解决什么问题。交代成因时可以插一句口语（「毕竟它最有名，用的人最多」），每节不超过两处。
- **导航句带新信息。** 「接下来我们进入技能文件夹，看看 `SKILL.md` 的格式」可以留，因为它说了去哪、看什么；「接下来我们看下一节」要删。每节最多一句。
- **设问自答。** 每节最多一次，问句要是读者真会问的，问完下一句就答，不隔段。例如「两个地方有同名技能怎么办？opencode 先注册全局，再注册项目，后者覆盖前者。」

## 排版一致

- 产品名统一写法：`opencode` 全篇小写，不写 OpenCode；`Claude Code` 首字母大写。
- 中文和英文、中文和数字之间空一格，例如「用 agent 写周报」「10 个文件」。
- 数字写法同一篇只用一种：正文用汉字（十、二十），和代码、路径、参数并排时用阿拉伯数字。
- 反引号成对闭合；表格里的术语与正文叫法一致。

## 正反例

### 一、对称口号：补上条件与后果

不要：

> 项目技能跟着仓库走。全局技能跟着这台机器走。

改成：

> 项目技能放在当前项目的 `.opencode/skills` 目录里，只在这个项目里生效。全局技能放在用户主目录下，放进去就对所有项目生效，换项目也还在。

改法：原句用两个「跟着……走」对齐，读起来像口号，读者不知道两者差在哪。改后每句有主语、有位置、有生效范围，读者知道该放哪。

### 二、电报句：补主语、条件和动作

不要：

> 同一个 ID 出现两份，后注册的那份生效。搞不清优先级时，删掉重复的那份。

改成：

> 如果两个目录里放了同名技能，harness 会按自己扫描目录的顺序处理：后读到的覆盖先读到的。哪一份生效，要看扫描顺序，不看文件名。比如 opencode 先扫 `~/.config/opencode/skills`，再扫 `.opencode/skills`，所以项目里同 ID 的那份会盖掉全局那份。搞不清时，把重复的那份删掉最省事。

改法：原句省了主语和条件，读者得自己补「谁在读」「什么情况下」。改后把条件放在前面，动作和结果跟上，再给一个「先扫 A 再扫 B」的实例，读者能自己推。

### 三、压缩小结：把差别摊开

不要：

> 这两家放在一起看，做法很接近：技能包里通常有 `SKILL.md`，软件按自己的规则找它。差别在软件去哪些目录找，以及你怎么喊它出来。

改成：

> opencode 和 Claude Code 的做法差不多：都把技能当文件夹放在固定目录里，由软件启动时自己去找，差别在查找规则和调用方式。opencode 从当前目录一路向上找到项目根，还会读 `.claude/skills` 这类兼容目录，调用时写 `@技能 ID`；Claude Code 只读自己那几处，调用时写 `/技能名`。

改法：原句把两家压成一句「做法接近」，读者拿不到能用的差别。改后先给共同点，再逐个说去哪找、怎么喊。

### 四、清单腔：写成动作和验证

不要：

> 安装分三步。第一，下载。第二，解压。第三，放进目录。

改成：

> 技能装起来只有一件事：把文件夹放到软件会扫的位置。下载下来的包先解压，里面那个带 `SKILL.md` 的目录就是技能本身，整个目录一起放到 `.opencode/skills` 下。放完重开会话，问 agent 现在有哪些技能，看它认不认得。

改法：三条命令没有因果，读者不知道哪一步容易错。改后先给目标，再给动作，最后给验证。

### 五、空泛总结：给出收益和代价

不要：

> 合理地使用技能，可以显著提升 agent 的工作效率。

改成：

> 同一个任务，把要求写成技能之后，你不必每次重复交代格式和步骤；模型每次按文件做，输出更稳。代价是多一个文件要维护，改了做法就得同步改它。

改法：原句没有可执行的信息。改后说清收益和代价，读者能判断值不值得做。

### 六、比喻停在喻体：落回动作

不要：

> 工具是厨具，技能是菜谱，agent 是厨师。

改成：

> 工具是厨具，技能是菜谱，agent 是厨师。厨师拿什么工具、按什么顺序下锅，看的是菜谱；agent 调什么工具、先做哪一步，看的是技能。

改法：比喻铺开就收，读者只记住三个标签，不知道对应到哪一步。改后把喻体和动作对上：菜谱管顺序，技能管顺序；厨具管切炒蒸，工具管调用。比喻会让人以为技能是死规则时，再补一句「菜谱是死纸，技能是模型会取舍的文本」，然后回到机制。

## 验收

写完一课，按顺序过五条：

1. 遮住小标题读一遍。读不出因果，回去补过渡句。先判断后机制的开头也要过这一条。
2. 读出声。拗口、喘不过气、像念稿的地方，改。
3. 找电报句：没有主语、没有条件、两个名词硬拼的句子，补全或重写。
4. 找出镜句和元话语：在报道「我怎么讲」的，删；纯导航句删，带新信息的导航句每节留一句。
5. 找空词和翻译腔：换成具体行为或对象；换不掉就删整句。

## 作者风格自查

与验收分开做。按「作者风格」六条对照：判断是否前置；优先级规则是否带「先扫 A 再扫 B」实例；字段约束是否写齐三层；成因是否具体；导航句是否带新信息且每节不超过一句；设问是否每节最多一次。再查排版：产品名大小写、中英空格、数字写法、反引号闭合。

事实与口径另有过法：一手资料当场核，机制说法与前后课对齐，数字与实跑输出对账。

## 参照

拿不准句子长短和名词密度时，对照三类原文：阮一峰的教程短句（术语随用随释）、Simon Willison 的写法（一句一事实、先结论后解释）、余光中《中文的常态和病态》（少名词化，让动词干活）。

## 执行范围

- **新写课**：从初稿起按本文件写。
- **精修旧课**：整课重过，不做标点级手术。学习者交回的 md 是文字底稿，回写 HTML 时只做表现层映射，不改他的说法。
- **派写作子代理**：把本文件全文放进提示词，再给一两段范文。只给禁令清单，产出会变成电报句和对称口号（`agent/0004` 第三轮的反例，见存档 5.85）。
