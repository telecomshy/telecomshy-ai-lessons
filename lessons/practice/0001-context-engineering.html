Agent 技巧篇 · 0001

上下文工程：别让 agent 淹死在自己的记忆里

放什么、放哪、什么时候丢——三件事决定你的 agent 靠不靠谱。

先别急着学，聊两句

你的 agent 跑到第 20 轮，开始胡说八道：忘了最早的要求、把工具结果张冠李戴、还开始编。

很像"模型变笨了"。但多数时候不是——是上下文烂了。

学完这课，你能：给 agent 的上下文排座次、算预算、决定什么该丢——而且知道每种做法什么时候会翻车。

这一篇的规矩（技巧篇都这样）

原理篇讲"是什么、为什么"，这篇讲"怎么做、怎么不翻车"。

所以每条技巧都配三样：做法、理由 + 一个反例、什么时候不适用。最后一条最重要——技巧会过时，也会有例外。

主线一条：上下文是一张有限的桌子，不是一个无限的抽屉。

1. 先算账：agent 的上下文里都装了什么

不是只有你跟它的对话。一轮完整请求里，上下文通常有五层：

┌─ 系统提示        你是谁、规矩是什么
├─ 工具清单        名字 + 说明 + 参数（每轮都要重发）
├─ skill 说明      各技能的那句 description
├─ 历史            之前说过的话、调过什么工具、拿到什么结果
└─ 当前输入        用户这一句
关键的账

每一轮都要重新付全部的钱。不是"多了才付"，是整段重发一遍——API 这一层你确实每次都把全部历史重新发过去。（但模型内部只算新增的那一段：前面的部分以 KV cache 复用、不重算——账单和算力是两回事，见 第 3 课。这一层不拆开，很容易误以为每轮都在全量重算。）

所以真正的成本是：轮数 × 每轮上下文长度。跑 20 轮、每轮 2 万 token，就是 40 万 token 的输入账单。

2. 技巧一：把稳定的放前面

做法：按"变不变"排座次——
系统提示 → 工具清单 → skill 说明 → 历史 → 当前输入
越靠前越稳定，越靠后越爱变。

理由：前缀缓存只认"开头一字不差"（LLM 底层第 3 课）。稳定的放前面，就一直命中；变了的放后面，只重算那一小截。命中缓存的输入，价格约 1/10。

反例：把用户名、当前时间、随机数塞进系统提示开头。看起来无害，但它们每轮都变——开头一变，后面全部缓存作废，成本直接翻几倍。

什么时候不适用

一次性短对话（一轮就完，没有"下一轮"可命中）——这时候排座次没意义，别为它扭曲 prompt 的可读性。

另外：如果开头真的必须变（比如每个用户一套独立规则），别硬塞，考虑把"变的那部分"挪到末尾，或者按用户分组复用前缀。

3. 技巧二：留白，别想着填满

做法：给上下文留余量，别用满。经验上，用到七成左右就该清理。

理由：上下文腐烂（context rot）——不是"塞满才出问题"，是长了就开始变笨：注意力被稀释、早期指令被冲淡、开始张冠李戴。
"窗口够大"不等于"塞得多效果好"。

反例：把整个仓库的文件全塞进去，理由是"反正窗口 20 万"。结果模型抓不住重点，还把第 3 个文件的结论安到第 7 个文件头上。

什么时候不适用

确实需要全量上下文的任务（比如让它逐行审一个大文件、做全文一致性检查）。这时不是"塞不塞"的问题，而是怎么分批：读一次、只留结论、后续引用结论而不是原文。

4. 技巧三：工具结果先裁再塞

做法：限制单个工具的返回大小；返回模型能用的信息，不是原始 JSON。
常用手段：只返回需要的字段 / 截断 / 分页 / 转成一段人话。

理由：工具是上下文里最容易失控的一块。一个"读文件"就可能返回几万 token，一次吃掉半张桌子；而且后面每一轮都要为它重新付钱。

反例：查数据库 SELECT * 把 40 列全返回；或者把整个文件原文塞回对话——模型要用的其实只有 3 个数。

（检索回来的那几段，其实也是"工具结果"的一种——RAG 检索到的资料怎么裁、怎么放，见 RAG · 第 2 课。）

什么时候不适用

模型确实需要完整原文的时候（比如逐行审代码、找全文里的某个模式）。这时候硬裁会出错——该分批给，一次一段，而不是一次裁掉。

5. 技巧四：历史太长，三种取舍

没有"最好的压缩"，只有"丢什么你能接受"：

做法 丢什么 什么时候用
截断（丢最老的几轮） 早期的指令、细节 前面已经不重要，只要"最近在干嘛"
压缩（几轮合成一句） 细节，保留进度 只需要知道"做到哪一步了"
摘要（生成一段总结替换原文） 原文；还多花一次调用 结论比过程重要
什么时候不适用

需要精确引用早期内容的任务——比如"把刚才那份合同的第三条改一下"。任何压缩都会丢原文，这时该做的是只保留原文、砍掉工具结果，或者干脆把关键原文另存成文件，用到再读。

7. 动手：算一算你自己的预算

脚本在工作区，纯离线。改顶部几个常量（各部分多长、跑几轮），它给你算账：

python exercises/practice/0001-context-budget.py
=== 上下文预算（窗口 200000 token）===
构成              每轮 token   占比    是否稳定
系统提示              1200    6.0%      稳定
工具清单              4800   24.0%      稳定
历史（第 20 轮）     13800   69.0%      易变
当前输入               200    1.0%      易变

每轮合计 20000 token；跑 20 轮 = 400000 输入 token
稳定前缀 6000（30%）→ 这部分可走缓存，约省 90%

重点看两行：历史占了七成（该清理了），和稳定前缀只占 30%（工具清单值得考虑"按需加载"，别全塞）。
