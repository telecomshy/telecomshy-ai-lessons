什么时候不该上 RAG

"我有文档 → 上 RAG"这个反应，一半时候是错的。

先别急着学，聊两句

RAG 现在很热，很多人一有文档就想到它。

但有些场景上 RAG 是纯亏：更慢、更贵，还更容易错。

学完这课，你能：面对一个具体需求，说清该不该上 RAG、不上该用什么。

记住一条主线，后面就不会晕

RAG 解决的只有一个问题：模型手上没有那份资料。

别的问题——要精确值、要实时、要推理——它解决不了，甚至会更糟。

1. 先问一句：你到底在解决什么问题？

用户说"它答不准"，可能是三种完全不同的毛病：

症状 真正的原因 该用什么
答案在你的私有资料里，模型没见过 信息不在它手边 ✅ 这才是 RAG
要精确的数或此刻的状态（余额、库存、今天几号） 资料会变，存起来就过期 用工具查，不是检索
要推理、对比、总结、改写 这是模型本身的能力 换更强的模型，或把活拆细

只有第一行该上 RAG。后两行上了只会更糟。

2. 四种不该上的场景

  • 文档很短。500 字整个塞进提示词就行。切块只会额外引入两种新毛病（切碎、检索不到）——你为了省事，反而买了两个麻烦。
  • 要精确值。检索回来的是"相关的几段"，模型可能顺手把 2107 总结成 2100。要精确，就让它去调工具拿原文那一行。
  • 要实时数据。向量库里存的是建库那天的快照。余额、天气、今天的汇率——查出来必错，而且错得很有说服力。
  • 要跨段推理。"三份合同的付款条款有什么差异"——检索只能各给你"相关的几段"，做不了对比，还可能漏掉某一份。

（RAG 还有个成本：每次请求多几步、多几段 token。能不用就不用。）

3. 带走一句口诀

第一问：模型手上有没有这份资料？
        没有 → 往下问；有 → 别上 RAG。

第二问：我要的是【查得到的事实】，还是【要推理】？
        事实、会变 / 很精确 → 用工具查，别用检索
        事实、稳定、量大    → 这才是 RAG 的地盘
        要推理              → RAG 只当资料入口，别指望它给结论

  场景 2：一份 500 字的产品说明书，用户会围绕它提问。
    → 不该上，直接塞
    理由：500 字整个塞进提示词就行。切块只会额外引入「切碎 / 检索不到」两种新毛病。

  场景 6：查错误码 E-2107 是什么意思。文档里有 3000 个错误码。
    → 该上，但要用「按词匹配」
    理由：错误码是精确编号，语义相似度反而抓不准（它连 2107 和 2108 都分不太清）。

场景 6 值得多看一眼：它是"该上 RAG"，但要换一种比法（按词匹配的稀疏检索）——见第 1 课动手那节。"该不该上"和"怎么上"是两个问题。
