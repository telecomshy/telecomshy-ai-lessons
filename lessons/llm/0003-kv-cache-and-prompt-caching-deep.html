KV Cache：六个绕人的细节

初学版讲「两回事」，这篇答「那具体到多轮、到工具、到断点，又是怎样」。按需跳读。

怎么用这篇

只收读完初学版仍会冒出来的疑问。有些还带真实的坑——踩过的人不少。

总链：一次任务 → 很多次请求 → 每次请求里几百轮 decode。"请求内复用"总是发生；"跨请求命中"要条件。

Q1 · 多轮对话里，上一轮模型的回答会不会命中？

会命中。官方文档给了张很清楚的表：

第几次请求 送进去的内容 缓存怎么动
第 1 次 系统 + 问1 + 答1 + 问2 整段写进缓存
第 2 次 … + 答2 + 问3 前面读缓存；答2 + 问3 写进缓存
第 3 次 … + 答3 + 问4 前面读缓存；答3 + 问4 写进缓存

看第 2 次那行的粗体："答2"是上一次模型的输出，这一次它被写进了缓存。第 3 次它就变成"读缓存"的一部分了。

官方文档列的三种打断方式

改早期消息、删消息、调换顺序——都会让从改动处往后的缓存作废。注意后两种：它们一个字的内容都不改，只动结构，照样作废。

Q2 · 上一轮的思考内容会不会被丢掉？谁说了算？

用会思考的模型（会输出"思考过程"的那种）时，思考块（thinking block）算不算进你的前缀，要看两边配合——客户端和模型各管一半。

客户端那一侧：必须原样带回去。官方规则写得很硬：把 thinking block 完整、不改动地带回来。而且要原样回传那条助手消息——官方原话是：重建了它、或者过滤掉里面的块，会直接 400 报错，请求根本发不出去。

那"网页版聊天和 harness 软件会不会自动带回去"？能正常用，就说明它已经做了——（这是从"不带就报错"推出来的结论，不是对某个产品的实测。）

模型那一侧：留不留，取决于版本。官方文档列得很清楚：

  • Opus 4.5+ 与 Sonnet 4.6+：thinking block 默认保留在上下文里，缓存仍然有效。
  • 更早的 Opus / Sonnet 和所有 Haiku：它们会被剥掉，而且跟在其后的消息也从缓存里移除。

被保留下来的 thinking block 算输入 token——从缓存里读出来时也一样计入你的 usage。（为什么会思考、那笔账怎么算？→ 看 LLM 第 5 课；术语表「思考 reasoning」）

比"带不带回去"更容易踩的坑

改 thinking 的配置会让缓存作废，而且是连着系统提示和工具定义一起作废。换模式、改预算、改 effort 都算——因为这份配置是被渲染进 prompt 的。

所以"我只是想把思考深度调低一点"，代价可能是整段前缀全部重算。

Q3 · 缓存到底省了什么？第一次用会不会更贵？

先破一个误会：缓存不是一块硬盘，不存在"存进去要交保管费"这回事。

第一次把某段前缀放进缓存时，那次请求该跑的算力一点没少跑——K/V 就是 prefill 算出来的。所以写入那一遍照常按输入价计费（Anthropic：5 分钟缓存写 1.25× 输入价、1 小时 2×）。

真正省下来的是后面每一次：读缓存约 0.1×。所以这笔账取决于"这段前缀会被用几次"——只用一次就别开缓存。

反过来还有个坑：每次都变的前缀，开缓存等于倒贴。你付了更贵的写入，却一次都没读到。

这也是为什么现在很多服务商提供"只在静态内容结尾打断点"的做法：动态的那一截干脆不写，省下写入费。

Q4 · 前缀越长越好吗？有个真实的坑

直觉是"历史越长、能命中的越多"——但有个反例，而且很坑。

机制是这样的（以 Claude 为例）：缓存写入只发生在你打的"断点"处；读取时，系统从断点往回逐个找已经写过的条目，但最多只往回找 20 个位置。

所以：

  • 只要每轮新增的内容少于 20 块——前一轮的写入还在窗口里，能命中；
  • 某一轮一口气加了一大堆（比如一次塞了 30 块）——上一轮的条目被挤出窗口，命中不了。
怎么救

多打几个断点。比如在"稳定内容"和"对话历史"交界处再放一个，等于开了第二个查找窗口。

或者用一个更稳的做法：把断点放在"最后一段不变的内容"结尾，而不是放在每轮都在变的那块上。

（各家实现不同：有的用"块数"算窗口，有的按 token 增量、有的有断点数量上限。原则一样——写入要有人打点，读取只认打过的点，窗口有限。）

一条官方例外：一轮里的并行工具调用只算一格

官方文档专门写了一条例外：连续的一串"工具调用"算一格，连续的一串"工具结果"也算一格。

翻译成人话：哪怕你一轮里并行调了 20 个工具，官方也只当 1 格算——不会把上一轮的条目挤出这个查找窗口。

Q5 · 那"命中"到底能省多少？为什么不是免费？

别以为命中就是免费，实际有三道折扣。

因为省的是算 K/V 那部分工作，而不是"不用送"。命中之后：

  • 只是不用重新算——所以又快又便宜，但不是零；
  • 缓存不保证一定有：可能被淘汰、可能路由到别的机器。

一句话：命中是"打折"，不是"免费"；是"尽量"，不是"保证"。

那怎么确认自己真的命中了？看响应里的 usage 字段——官方给的核对方法就是它：

  • cache_read_input_tokens：命中了多少（这次省了多少）
  • cache_creation_input_tokens：写进去多少（这次多花了多少）
  • 这两个加上 input_tokens，就是这次的总输入

OpenAI 那边对应的字段是 usage.input_tokens_details.cached_tokens 和 cache_write_tokens；命中率就是"累计命中的 ÷ 累计输入"。

最要紧的一句：不命中不会报错。官方原话是"如果 cache_creation_input_tokens 和 cache_read_input_tokens 都是 0，这个 prompt 就没有被缓存"，多半是长度没到门槛。所以别拿"没报错"当"命中了"，一定要看数。

最常踩的一种"为什么不命中"：前缀太短

各家都设了最小可缓存长度（按模型不同，512 / 1024 / 2048 / 4096 token 都有）。不到这个长度，请求照常处理，但一点缓存都不建——而且不报错、不提示。

所以"我怎么一次都没命中过"，先别急着查代码，先去 usage 里看那两个字段。它俩是不是 0？

（反直觉的一笔账：如果你的稳定前缀刚好卡在门槛下面一点，把它补长到门槛以上反而更便宜——因为跨过门槛之后，后面每一次都在打折。补的内容要是稳定且有用的，别拿废话凑。）

另一种"没命中"：请求是并发发出去的

缓存条目要等第一个响应开始之后才可用。所以你同时发出几个请求（哪怕开头一样），后几个也撞不上——那一刻缓存里还没有那份前缀。

OpenAI 那边还多一层原因：缓存存在某一台具体的机器上，请求得被路由到那台才撞得上；而流量超过 15 请求/分钟可能触发溢出路由。prompt_cache_key 能让同一段前缀的请求归到一处——但官方紧接着说了：它只影响路由，不保证命中。

Q6 · 如果前缀命中缓存了，还占不占用上下文窗口？

占。先说清一个容易缠上的点：命中缓存和上下文窗口没有直接关系——缓存省的是"重算"，不是"行数"。那段前缀的 K/V 正因为还占着窗口里的行数，才谈得上被"命中"。窗口数的是行数，不是"算没算过"。

一条推论：缓存救时间，不救窗口。多轮会话越聊越长，命中率再高，前缀照样一段段摞进窗口——顶到上限时，命中多少次都救不了你，只能决定往里塞什么、丢掉什么（这一套叫上下文工程）。（窗口是什么、里面装的是谁的 token，见 第 1 课进阶 Q9。）
