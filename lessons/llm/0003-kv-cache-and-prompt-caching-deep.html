KV Cache：五个绕人的细节

初学版讲「两回事」，这篇答「那具体到多轮、到工具、到断点，又是怎样」。按需跳读。

怎么用这篇

只收读完初学版仍会冒出来的疑问。有些还带真实的坑——踩过的人不少。

总链：一次任务 → 很多次请求 → 每次请求里几百轮 decode。三条："请求内复用"总是发生；"跨请求命中"要条件；缓存不打折输出。

Q1 · 多轮对话里，上一轮模型的回答会不会命中？

会命中。而且这正是多轮对话越聊越省的原因。官方文档给了张很清楚的表：

第几次请求 送进去的内容 缓存怎么动
第 1 次 系统 + 问1 + 答1 + 问2 整段写进缓存
第 2 次 … + 答2 + 问3 前面读缓存；答2 + 问3 写进缓存
第 3 次 … + 答3 + 问4 前面读缓存；答3 + 问4 写进缓存

看第 2 次那行的粗体："答2"是上一次模型的输出，这一次它被写进了缓存。第 3 次它就变成"读缓存"的一部分了。

所以那条铁律要再强调一次

只追加，不修改。官方文档明确列了三种打断缓存的做法：改早期消息、删消息、调换顺序——全都会让从改动处往后的缓存作废。

Q2 · 工具结果为什么算「输入」？为什么必须追加在末尾？

因为送去匹配缓存的那段前缀里，工具结果也在里面：

官方的说法是：送去匹配缓存的那段前缀，是整个序列化后的请求——系统消息、对话历史、工具定义、助手消息、工具调用、工具结果，全都算在里面。

所以：工具结果 = 输入前缀的一部分。它按输入计价，也能命中，而且会一直留在前缀里。

那为什么必须是末尾追加？因为缓存认的是"从头开始、一字不差"。你只有往末尾加东西，前面那截才原封不动——一旦插到中间去，后面每一格都得重算，等于把前面攒的便宜全吐回去。

顺带一个真实的坑

用会思考的模型（会输出"思考过程"的那种）时，上一轮的思考内容如果不原样带回去，缓存就断了。这被列成多轮缓存失效的头号原因；而且有的厂商更严——直接报错，请求根本发不出去。（为什么会思考、那笔账怎么算？→ 看 LLM 第 5 课；术语表「思考 reasoning」）

Q3 · 既然便宜 10 倍，那"缓存写入"为什么还要加钱？

因为写入和读取是两笔账：

  • 写入（cache write）：第一次把这段前缀算好、存起来。有的服务商收得比普通输入还贵一点（因为多干了存储的活）；
  • 读取（cache read）：后面命中时捡现成，约 0.1×。

所以"便宜 10 倍"的前提是这段前缀会被反复用。如果每次都变，你只付了更贵的写入、一次都没读到——反而亏。

什么时候不适用

一次性请求（这段前缀这辈子只用一次）——别开缓存，写入的钱白花。

这也是为什么现在很多服务商提供"只在静态内容结尾打断点"的做法：动态的那截干脆不写，省下写入费。

Q4 · 前缀越长越好吗？有个真实的坑

直觉是"历史越长、能命中的越多"——但有个反例，而且很坑。

机制是这样的（以 Claude 为例）：缓存写入只发生在你打的"断点"处；读取时，系统从断点往回逐个找已经写过的条目，但最多只往回找 20 个位置。

所以：

  • 只要每轮新增的内容少于 20 块——前一轮的写入还在窗口里，能命中；
  • 某一轮一口气加了一大堆（比如一次塞了 30 块）——上一轮的条目被挤出窗口，命中不了。
怎么救

多打几个断点。比如在"稳定内容"和"对话历史"交界处再放一个，等于开了第二个查找窗口。

或者用一个更稳的做法：把断点放在"最后一段不变的内容"结尾，而不是放在每轮都在变的那块上。

（各家实现不同：有的用"块数"算窗口，有的按 token 增量、有的有断点数量上限。原则一样——写入要有人打点，读取只认打过的点，窗口有限。）

好消息：这个坑 agent 基本碰不到

官方文档专门写了一条例外：连续的一串"工具调用"算一格，连续的一串"工具结果"也算一格。

翻译成人话：哪怕你一轮里并行调了 20 个工具，官方也只当 1 格算——不会把上一轮的条目挤出窗口。

所以上面那个"塞 30 块就失效"的坑，对多轮聊天是条真警告，对并行调工具的 agent 基本不成立。别为它改坏了自己的架构。

Q5 · 那"命中"到底能省多少？为什么不是免费？

"白捡"听着很美，但实际有三道折扣。

因为省的是算 K/V 那部分工作，而不是"不用送"。命中之后：

  • 那段前缀还是要塞进上下文、照样占位置（它在窗口里——为什么，见 Q6）；
  • 只是不用重新算——所以又快又便宜，但不是零；
  • 缓存还有 TTL（几分钟到一小时），过期就没了；
  • 而且缓存不保证一定有：可能被淘汰、可能路由到别的机器。

一句话：命中是"打折"，不是"免费"；是"尽量"，不是"保证"。

最常踩的一种"为什么不命中"：前缀太短

各家都设了最小可缓存长度（按模型不同，512 / 1024 / 2048 / 4096 token 都有）。不到这个长度，请求照常处理，但一点缓存都不建——而且不报错、不提示。

所以"我怎么一次都没命中过"，先别急着查代码，先去量一下你的稳定前缀到底多长。它够长吗？

（反直觉的一笔账：如果你的稳定前缀刚好卡在门槛下面一点，把它补长到门槛以上反而更便宜——因为跨过门槛之后，后面每一次都在打折。补的内容要是稳定且有用的，别拿废话凑。）

所以监控要盯两个数

缓存读取量（省了多少）和 缓存写入量（花了多少）。只盯一个会误判。

Q6 · 如果前缀命中缓存了，还占不占用上下文窗口？

占。先说清一个容易缠上的点：命中缓存和上下文窗口没有直接关系——缓存省的是"重算"，不是"行数"。那段前缀的 K/V 正因为还留在显存里、占着窗口里的行数，才谈得上被"命中"。窗口数的是行数，不是"算没算过"。

一条推论：缓存救时间，不救窗口。多轮会话越聊越长，命中率再高，前缀照样一段段摞进窗口——顶到上限时，命中多少次都救不了你，只能决定往里塞什么、丢掉什么（这一套叫上下文工程）。（窗口是什么、里面装的是谁的 token，见 第 1 课进阶 Q9。）

附 · 两个别误会

① 缓存不改变"怎么生成"，但不保证每次生成出同一个字。官方原话是：缓存只省掉"重新处理前缀"这一步，模型生成输出的方式一点没变。至于同一个问题会不会每次答得一样——那是另一回事：采样本来就是按百分比抽的，本来就有随机性，跟缓存没关系。

② 缓存不等于"存了你的数据"。存的是 K/V 张量（中间计算结果），不是可读的原文；而且会过期。
