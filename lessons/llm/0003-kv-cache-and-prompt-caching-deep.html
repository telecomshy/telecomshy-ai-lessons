KV Cache：三个绕人的细节

初学版讲「两回事」，这篇答「那具体到多轮、到工具、到断点，又是怎样」。按需跳读。

怎么用这篇

只收读完初学版仍会冒出来的疑问。有些还带真实的坑——踩过的人不少。

总链：一次任务 → 很多次请求 → 每次请求里几百轮 decode。"请求内复用"总是发生；"跨请求命中"要条件。

Q1 · 上一轮的思考内容会不会被丢掉？谁说了算？

用会思考的模型（会输出"思考过程"的那种）时，思考块（thinking block）算不算进你的前缀，要看两边配合——客户端和模型各管一半。

客户端那一侧：必须原样带回去。Anthropic 官方文档的规则写得很硬：把 thinking block 完整、不改动地带回来。而且要原样回传那条助手消息——文档原话是：重建了它、或者过滤掉里面的块，会直接 400 报错，请求根本发不出去。

那"网页版聊天和 harness 软件会不会自动带回去"？能正常用，就说明它已经做了——（这是从"不带就报错"推出来的结论，不是对某个产品的实测。）

模型那一侧：留不留，取决于版本。Anthropic 文档按模型版本列得很清楚：

  • Opus 4.5+ 与 Sonnet 4.6+：thinking block 默认保留在上下文里，缓存仍然有效。
  • 更早的 Opus / Sonnet 和所有 Haiku：它们会被剥掉，而且跟在其后的消息也从缓存里移除。

被保留下来的 thinking block 算输入 token——从缓存里读出来时也一样计入你的 usage。（为什么会思考、那笔账怎么算？→ 看 LLM 第 5 课；术语表「思考 reasoning」）

比"带不带回去"更容易踩的坑，是改配置。Anthropic 官方文档《Extended thinking》里的「Prompt caching in manual mode」一节明确写：改 thinking 的配置会让缓存作废，而且是连着系统提示和工具定义一起作废，因为这份配置是被渲染进 prompt 的。所以"我只是想把思考深度调低一点"，代价可能是整段前缀全部重算。

这里的"配置"是两个旋钮。旧模式用 budget_tokens 给思考定一个 token 目标（拿多少 token 用来想——文档特别说明这是目标、不是硬上限）；新模式改用 output_config: {effort: ...} 分档（low / medium / high），同一份文档的原话是"用它代替 token 预算来控制推理深度"——也就是深度由模型自己定。两个都会被渲染进 prompt，所以动任何一个都要重建缓存。（这两个是 Anthropic 的参数名，别的厂商不叫这个；它们属于思考模型本身，见 LLM 第 5 课）

那一节还给了三行实测数字，可以直接摆成一张表看。两个字段先看懂：cache_creation ＝ 这一轮新算出来、存进缓存的 token 数；cache_read ＝ 这一轮从缓存读回来的 token 数；input ＝ 两者都没盖住、正常计价的那部分。

请求 cache_creation（存） cache_read（读） input（正常计价）
第 1 次 · 建立缓存 1370 0 17
第 2 次 · 参数不动（文档标注预期命中） 0 1370 303
第 3 次 · 改了 budget（文档标注预期不命中） 1370 0 747

三行连起来看就清楚了：第 1 次把 1370 个 token 算出来存进去；第 2 次原样读回来，一个都没重算；第 3 次因为改了 budget，前缀作废，只好又算了一遍 1370 个 token 存进去。而 cache_read = 0 那一行还顺带说明另一件事：没命中的那次不只白算，还要多付一笔写入费（写入比普通输入更贵，各家倍数见速查页）。文档最后特意补了一句：在新模式里，effort 扮演的正是 budget_tokens 在这里的角色——所以换到新模式，这个坑照样在。

Q2 · 前缀越长越好吗？有个真实的坑

直觉是"历史越长、能命中的越多"——但有个反例，而且很坑。

机制是这样的（以 Claude 为例）：缓存写入只发生在你打的"断点"处；读取时，系统从断点往回逐个找已经写过的条目，但最多只往回找 20 个位置。

所以：

  • 只要每轮新增的内容少于 20 块——前一轮的写入还在窗口里，能命中；
  • 某一轮一口气加了一大堆（比如一次塞了 30 块）——上一轮的条目被挤出窗口，命中不了。

怎么救？多打几个断点——比如在"稳定内容"和"对话历史"交界处再放一个，等于开了第二个查找窗口。或者用一个更稳的做法：把断点放在"最后一段不变的内容"结尾，而不是放在每轮都在变的那块上。

（各家实现不同：Anthropic 用"块数"算窗口，有的按 token 增量、有的有断点数量上限。原则一样——写入要有人打点，读取只认打过的点，窗口有限。）

还有个更省钱的做法：不缓存动态的那一截。既然写入要按更贵的价格算，那就只在静态内容结尾打一个断点——系统提示、工具定义这些不变的部分照常缓存，而后面每次都变的那一截干脆别写，省下写入费。代价是那一截每轮都要重算，所以只适合「变化的那截本来就不长」的情况。

还有一条 Anthropic 的例外：一轮里的并行工具调用只算一格。文档专门写了：连续的一串"工具调用"算一格，连续的一串"工具结果"也算一格。翻译成人话：哪怕你一轮里并行调了 20 个工具，官方也只当 1 格算——不会把上一轮的条目挤出这个查找窗口。

Q3 · 那"命中"到底能省多少？为什么不是免费？

别以为命中就是免费，实际有三道折扣。

因为省的是算 K/V 那部分工作，而不是"不用送"。命中之后：

  • 只是不用重新算——所以又快又便宜，但不是零；
  • 缓存不保证一定有：可能被淘汰、可能路由到别的机器。

一句话：命中是"打折"，不是"免费"；是"尽量"，不是"保证"。

那怎么确认自己真的命中了？看响应里的 usage 字段——Anthropic 官方文档给的核对方法就是它：

  • cache_read_input_tokens：命中了多少（这次省了多少）
  • cache_creation_input_tokens：写进去多少（这次多花了多少）
  • 这两个加上 input_tokens，就是这次的总输入

OpenAI 那边对应的字段是 usage.input_tokens_details.cached_tokens 和 cache_write_tokens；命中率就是"累计命中的 ÷ 累计输入"。

最要紧的一句：不命中不会报错。Anthropic 文档原话是"如果 cache_creation_input_tokens 和 cache_read_input_tokens 都是 0，这个 prompt 就没有被缓存"，多半是长度没到门槛。所以别拿"没报错"当"命中了"，一定要看数。

而最常踩的"为什么不命中"，就是前缀太短。各家都设了最小可缓存长度（按模型不同，512 / 1024 / 2048 / 4096 token 都有）。不到这个长度，请求照常处理，但一点缓存都不建——而且不报错、不提示。所以"我怎么一次都没命中过"，先别急着查代码，先去 usage 里看那两个字段：它俩是不是 0？

还有一种"没命中"只有自己写 API 的人会碰到：请求是并发发出去的——缓存条目要等第一个响应开始之后才可用，所以同时发几个请求（哪怕开头一样），后几个都撞不上。OpenAI 那边还多一层：缓存存在某一台具体的机器上，流量超过 15 请求/分钟可能触发溢出路由；prompt_cache_key 能让同一段前缀的请求归到一处，但 OpenAI 文档明说它只影响路由，不保证命中。（用网页版聊天或现成 harness 基本碰不到；真要自己发并发请求，办法在速查页，做法在技巧篇 0001 · 上下文工程 · 技巧五）

还有一个反直觉的账：如果稳定前缀刚好卡在门槛下面一点，把它补长到门槛以上反而更便宜——跨过门槛之后，后面每一次都在打折。但补的内容要是稳定且有用的，别拿废话凑。

再来三个更难的

Q1 一次响应的 usage 里，cache_read 和 cache_write 两个字段都是 0，说明什么？

Q2 用会思考的模型时，上一轮的思考内容会不会留在上下文里？

Q3 某一轮一口气加了很多新内容，可能发生什么？

Anthropic — Prompt caching（官方文档）：那张多轮缓存表、断点机制、20 个位置的查找窗口、Q1 里"哪些模型保留思考块"、Q3 的 usage 字段名与最小可缓存长度，以及写入 / 读取的计价倍数，都出自这里。

Anthropic — Extended thinking：Q1 那张三行表和 budget_tokens / effort 两个参数名都出自这里的「Prompt caching in manual mode」一节。 OpenAI — Prompt caching：前缀匹配、只追加不改写、工具结果算在前缀里、Q3 的 cached_tokens / cache_write_tokens 字段。多轮时序表与"三种打断方式"见基础课与速查页。
