KV Cache：三个绕人的细节

初学版讲「两回事」，这篇答「那具体到多轮、到工具、到断点，又是怎样」。按需跳读。

怎么用这篇

只收读完初学版仍会冒出来的疑问。有些还带真实的坑——踩过的人不少。

总链：一次任务 → 很多次请求 → 每次请求里几百轮 decode。"请求内复用"总是发生；"跨请求命中"要条件。

Q1 · 上一轮的思考内容会不会被丢掉？谁说了算？

用会思考的模型（会输出"思考过程"的那种，见 第 5 课 · 它真的在思考吗？）时，思考块（thinking block）算不算进你的前缀，要看两边配合——客户端和模型各管一半。

客户端那一侧：必须原样带回去。Anthropic 官方文档的规则写得很硬：把 thinking block 完整、不改动地带回来。而且要原样回传那条助手消息——文档原话是：重建了它、或者过滤掉里面的块，会直接 400 报错，请求根本发不出去。

那"网页版聊天和 harness 软件会不会自动带回去"？能正常用，就说明它已经做了——（这是从"不带就报错"推出来的结论，不是对某个产品的实测。）

模型那一侧：留不留，取决于版本。Anthropic 文档按模型版本列得很清楚：

  • Opus 4.5+ 与 Sonnet 4.6+：thinking block 默认保留在上下文里，缓存仍然有效。
  • 更早的 Opus / Sonnet 和所有 Haiku：它们会被剥掉，而且跟在其后的消息也从缓存里移除。

被保留下来的 thinking block 算输入 token——从缓存里读出来时也一样计入你的 usage。（为什么会思考、那笔账怎么算？→ 看 LLM 第 5 课；术语表「思考 reasoning」）

比"带不带回去"更容易踩的坑，是改配置。Anthropic 官方文档《Extended thinking》里的「Prompt caching in manual mode」一节明确写：改 thinking 的配置会让缓存作废，而且是连着系统提示和工具定义一起作废，因为这份配置是被渲染进 prompt 的。所以"我只是想把思考深度调低一点"，代价可能是整段前缀全部重算。

这里的"配置"是两个旋钮。旧模式用 budget_tokens 给思考定一个 token 目标（拿多少 token 用来想——文档特别说明这是目标、不是硬上限）；新模式改用 output_config: {effort: ...} 分档（low / medium / high），同一份文档的原话是"用它代替 token 预算来控制推理深度"——也就是深度由模型自己定。两个都会被渲染进 prompt，所以动任何一个都要重建缓存。（这两个是 Anthropic 的参数名，别的厂商不叫这个；它们属于思考模型本身，见 LLM 第 5 课）

那一节还给了三行实测数字，可以直接摆成一张表看。三个字段先看懂：cache_creation ＝ 这一轮新算出来、存进缓存的 token 数；cache_read ＝ 这一轮从缓存读回来的 token 数；input ＝ 断点之后的那一截——它进不了缓存，每次都重算、按原价计价（这三个字段在 Q3 细讲）。

请求 cache_creation（存） cache_read（读） input（正常计价）
第 1 次 · 建立缓存 1370 0 17
第 2 次 · 参数不动（文档标注预期命中） 0 1370 303
第 3 次 · 改了 budget（文档标注预期不命中） 1370 0 747

三行连起来看就清楚了：第 1 次把 1370 个 token 算出来存进去；第 2 次原样读回来，一个都没重算；第 3 次因为改了 budget，前缀作废，只好又算了一遍 1370 个 token 存进去。而 cache_read = 0 那一行还顺带说明另一件事：没命中的那次不只白算，还要多付一笔写入费（写入比普通输入更贵，各家倍数见速查页）。文档最后特意补了一句：在新模式里，effort 扮演的正是 budget_tokens 在这里的角色——所以换到新模式，这个坑照样在。

（表里那三行 input 分别是 17 / 303 / 747，都是断点之后的那截——本例的断点打在思考块＋系统提示之后，所以每次新加的那句提问都落在这一栏里。它们不是"没命中"，是压根不进缓存。）

Q2 · 一个字都没改，为什么还是不命中？

这一问写给要自己发请求的人（不写代码的可以整段跳过）。要带走的只有一句：缓存只认上次存过的那一份，而且只往回找有限的距离。

先看一个真的发给模型的请求。请求不是一整坨字，而是分成若干块——下面这个例子里：

{
  "model": "claude-sonnet-5-5",
  "max_tokens": 1024,

  "tools": [
    { "name": "search_docs", "description": "在知识库里搜索",
      "input_schema": { "type": "object", "properties": { "q": { "type": "string" } } } },
    { "name": "read_doc",   "description": "按编号读一篇",
      "input_schema": { "type": "object", "properties": { "id": { "type": "string" } } },
      "cache_control": { "type": "ephemeral" } }
  ],

  "system": [
    { "type": "text", "text": "你是一个可以查资料的助手，回答要简短。",
      "cache_control": { "type": "ephemeral" } }
  ],

  "messages": [
    { "role": "user",
      "content": [ { "type": "text", "text": "帮我查一下火星车。",
                     "cache_control": { "type": "ephemeral" } } ] }
  ]
}
  • 块＝数组里的每一项。tools 里每个工具一项、system 里每段一块、每条消息的内容又是一组块（content 直接写字符串也算一块）。这些结构由 API 定死，所以你数得出来；一块里装着好几个 token。
  • 断点＝写着 "cache_control" 的那一项的末尾。上面出现了三次，就是三个断点。它挂在第二个工具上，标一个就盖住整组工具说明。

断点的意思是"从第一个 token 到我这块为止的整段，存下来"。服务端会给这一整段算一个指纹（一串代表它的编号）存好，下次好认出"这段我算过"。改一个字，指纹就变，那份就作废——所以指纹是从第一个 token 一路累积的，天然包含前面所有块：你改一下系统提示，第二个和第三个的指纹一起变、一起作废，只有第一个还能用。

下一轮同一个对话，请求变成这样——多了一轮回答，断点挪到最后一条消息：

  "messages": [
    { "role": "user",      "content": "帮我查一下火星车。" },
    { "role": "assistant", "content": "我找到了 3 篇，都跟火星车有关。" },
    { "role": "user",      "content": [ { "type": "text",
                                          "text": "再详细说说毅力号。",
                                          "cache_control": { "type": "ephemeral" } } ] }
  ]

这一轮服务端做两件事：

  • 存：断点那块算一个指纹，写下来。只有断点这一处会存。
  • 读：从第一个 token 到最后一块算一个指纹，跟以前存下来的那些比。对上了，说明这段已经缓存，那一块之前的内容整段复用；对不上就往上退一块，再算一次，最多退 20 块。

本轮算出来的指纹，是跟"过去存过的"比，不是跟自己比。它只认存过的记录，不会看你这段内容稳不稳定就临时帮你存——一段一个字都没改的内容，你从来没在那一处打过标记，它就一次都不会被命中。

一次最多能标 4 个断点。这跟"往回退最多 20 块"是两回事：4 是你能打几个标记，20 是它能往回看几块。

有时候前面内容都一样，却没有命中。断点总是打在当前最后一块上，对话每走一轮，最后一块就往后挪好几块；而存下来的记录留在原地不动，距离一轮比一轮远。比如下面这个 Anthropic 文档里的例子：

轮次 断点落在第几块 结果
第 1 轮 第 10 块 缓存是空的，存一份
第 2 轮 第 15 块（往前挪了 5 块） 退到第 10 块 → 命中，只有 11–15 新算
第 3 轮 第 35 块（又挪了 20 块） 只能退到第 16 块；上一轮那份在第 15 块，差一块 → 一次都不命中

断点应该标在"每次请求都一模一样的那段"末尾，变的那截留在标记之后。如果标记落在每次都变的块后面（比如时间戳），那么每次断点处的指纹都会变，这个断点永远不会命中。

断点不是 Claude 特有的，但分两派：

谁 标记谁来打 往回退多少
Claude、OpenAI 你或你用的工具打，或让它自动放到最后一块 有上限，各家不同
Gemini、DeepSeek 没这个概念，服务商自己切 由它们自己定

OpenAI 那两个参数只在 Responses API ＋ GPT-5.6 及以后有，更早的模型和 Chat Completions 只有隐式缓存（不打标记，服务商自己按前缀来）；Claude 两种都有。共同的那层只有三样：前缀一字不差才复用、往回找且范围有限、写进去要钱。窗口多大，照抄别家的没有意义。

这些标记是 Claude 网页版、Claude Code、OpenCode 这类工具替你写进每个请求的——自己手写代码就得自己写。不打就没有缓存，所以一定有人在打，只是没有任何产品文档说明它们具体怎么写。

Q3 · 命中到底能省多少？怎么确认自己真命中了？

命中是打折，不是免费。它省掉的是"重新算 K/V"那份工作，不是"不用把内容送过去"——读缓存那一次照样按 0.1× 付钱，只是比原价便宜十倍。而且缓存不保证还在：可能被淘汰，也可能你的请求被路由到另一台机器上。

所以两条都要记住：命中是"打折"不是"免费"，是"尽量"不是"保证"。

怎么知道自己真命中了？看响应里的 usage。Anthropic 官方文档给的核对方法就是它，三个字段各管一件事：

  • cache_read_input_tokens：命中了多少（这次省了多少）
  • cache_creation_input_tokens：写进去多少（这次为缓存多付了多少）
  • input_tokens：最后一个断点之后的那一截，按定义就进不了缓存，每次重算、按原价计价

这三条不是"命中／没命中／第三种结果"，是提示词被断点切成的三段。断点之前那一段，要么以前存过（cache_read），要么这次新算（cache_creation）；断点之后的那截不在这一份里，所以永远是 input_tokens。文档特意强调过：input_tokens 不代表你送进去的全部输入，只代表最后一个断点后面那一截。

三个加起来就是这次的总输入。Q1 那张表就是照这三个字段列的——第 1 次 1370 全记在"存"那栏、第 2 次 1370 全变成"读"，一眼看出省没省。

OpenAI 那边字段名不一样：usage.input_tokens_details.cached_tokens（命中）和 cache_write_tokens（写入），断点之后那一截照旧在 input_tokens 里。命中率就是"累计命中的 ÷ 累计输入"，自己按请求累加。

不命中不会报错。Anthropic 文档的原话是——如果 cache_creation 和 cache_read 都是 0，这个 prompt 就没有被缓存。请求照常跑完、照常给你答案。所以别拿"没报错"当"命中了"，一定要看那两个字段是不是 0。

这两个字段为 0，最常见的原因是前缀太短。各家都设了最小可缓存长度（Anthropic 按模型分 512 / 1024 / 2048 / 4096，OpenAI 是 1024）。不到这个长度，一点缓存都不建——请求正常处理、不报错、不提示。所以"我怎么一次都没命中过"，先别查代码，先看那两个字段是不是 0。

如果前缀差一点才够到门槛，把它补长过去反而更便宜。假设门槛是 1024 token，你的稳定前缀只有 1000——那这 1000 个每次都按原价付，一次也享受不到折扣。要是补 24 个字凑到 1024，第一次多付一小笔写入费，但从第二次起，这 1024 个全都按 0.1× 算。请求发得越多越划算。OpenAI 文档算过这笔账：连着发 10 次的话，把 221 token 以上的补到 1024 就已经省了；只有 103 token 的要发够 1963 次才回本；102 token 以下的补了也不划算。

补的内容得是稳定而且有用的东西——多补的每一轮都要重发，写废话就是自己给自己加钱。

还有一种"没命中"，是自己同时发几个请求才会碰到的。设想你写了个程序，一次要拿三份结果，于是一个 API 请求还没回来，你就同时把三个都发出去，三个的开头一模一样：

问题是缓存要等第一个响应开始返回了才建好。三个请求挤在一起发，缓存此刻还是空的，所以三个全都没命中——明明前缀一个字都没差。正确做法是先发一个、等到响应开始回来，再发剩下两个（OpenAI 还多一层：prompt_cache_key 能让这几个请求路由到同一台机器，但 OpenAI 明说它只影响路由、不保证命中）。（网页版聊天和现成 harness 基本碰不到；真要自己发并发请求，参数见速查页，做法见技巧篇 0001 · 上下文工程 · 技巧五）

再来四个更难的

Q1 一次响应的 usage 里，cache_read 和 cache_creation 两个字段都是 0，说明什么？

Q2 用会思考的模型时，上一轮的思考内容会不会留在上下文里？

Q3 某一轮一口气加了很多新内容，可能发生什么？

Q4 三个断点分别打在工具说明、系统提示、提问的末尾。你改了系统提示，哪几份还可用？

这篇的一手资料：
Anthropic — Prompt caching（官方文档）：Q2 几乎全部——三条核心规则（"写入只发生在断点处／读取只往回找以前写过的／查找范围 20 个位置"）、那段 10→15→35 的走法、Q2 那两段 JSON 的字段放法（工具定义上标最后一个、系统消息里标、最后一条用户消息里标）、"Common mistake: Breakpoint on content that changes every request"、请求顶层写一个 cache_control 就自动标在最后一个可缓存块（自动模式也踩"标在每次都变的那块上"的坑）；另外还有那张多轮缓存表、Q1 里"哪些模型保留思考块"、Q3 的 usage 字段名与最小可缓存长度，以及写入 / 读取的计价倍数、"连着的一串工具调用与工具结果各算一块"和"断点本身不收费"（这两条见速查页）。
Anthropic — Thinking in tool and multi-turn workflows：Q1 的客户端义务——"完整、不改动地带回 thinking blocks""原样回传助手消息，否则 400 报错"。
Anthropic — Caching with thinking blocks："改 thinking 配置会让缓存前缀作废，连系统提示和工具定义一起作废"（因为配置被渲染进 prompt）。
Anthropic — Extended thinking：Q1 那张三行表和 budget_tokens / effort 两个参数名都出自这里的「Prompt caching in manual mode」一节。 OpenAI — Prompt caching：前缀匹配、只追加不改写、工具结果算在前缀里、Q3 的 cached_tokens / cache_write_tokens 字段；Q2 那张两派对照表里的 OpenAI 一行（prompt_cache_options / prompt_cache_breakpoint，只在 Responses API ＋ GPT-5.6 及以后有，更早的模型只有隐式缓存）也出自这里。多轮时序表与"三种打断方式"见基础课与速查页。
Google — Gemini Context caching：Q2 对照表里 Gemini 一行——默认隐式缓存、用户什么都不用做；显式缓存是"手动创建并管理缓存对象"，不是提示词里的标记。
DeepSeek — Context Caching：Q2 对照表里 DeepSeek 一行——默认开启、代码不改，系统在"用户输入末尾／模型输出末尾／公共前缀／固定 token 间隔"切出缓存单元，命中要求完整对上其中一个。
