KV Cache 与「缓存命中」是两回事

一个决定你的 agent 花多少钱的小机关。先把"请求"这个词钉死，后面全通。

先别急着学，聊两句

跟模型聊久了，有没有觉得它变慢、变贵？更怪的是——你在提示词里改一个标点，账单能翻好几倍。

拆穿了其实很朴素：有一套"算过的别重算"的机制在省钱，而它认的是"开头一字不差"。你动了开头，它就罢工。

但这套机制有两个，被混为一谈。这一课先分清它们。

学完这课，你能：说清两个机制各管哪一层；看一眼 prompt 就判断会不会命中；并且不再被"请求"这个词绊倒。

记住一条主线，后面就不会晕

两个机制，管的是不同层的事：

KV Cache　＝ 一次请求内部，算过的别重算。总是发生，没有"命中/不命中"。
缓存命中　＝ 跨多次请求，上次算的这次接着用。要条件满足，才有"命中/不命中"。

所以——先得知道"请求"是哪一层。

1. 前置：三个层次

先把三个容易混的层次放这儿：一次任务（用户发起的一件事）、一次请求（一次 API 调用）、一轮 decode（模型内部每蹦一个字）。

本课所有"请求内 / 跨请求"，说的都是「一次请求」这一层。

（这一条在术语表里也有；第 2 课开头会把「一轮」和「一次请求」钉死。）

2. 请求内：算过的别重算（KV Cache）

先把"请求内复用"这句话说白：decode 这一步读的 K/V，是前面（prefill ＋ 更早的 decode 步）算好留下的——不是重新算的。这就是"复用"。
一句话对照：请求内复用 ＝ 后面每一步，接着用这一步之前算好的；跨请求复用 ＝ 这一次请求，接着用上一次请求算好的（那是有条件的，见第 3 节）。

你的直觉是对的：输入那部分是一次性算完的。先把一次请求拆成两段，这事立刻就清楚了。

一次请求 ＝ 两段

前段 · prefill（预填充）：你输入的那张表（n 行），一次性、并行算完。每个位置的 K/V 都到手了，顺手也蹦出第一个新字。

后段 · decode（解码）：之后每蹦一个字，只喂这一个新的（1 行），前面的 K/V 从缓存里读。

所以"一个一个来"只发生在后段——也就是输出。输入那段从来不会重算。

（这两段脾气完全不同：一个算力受限、一个带宽受限。第 2 课专门讲。）

那 KV Cache 省的是什么？省的是后段的重算。假设没有它，decode 每一步都得把前面的全部重新算一遍：

  • 蹦第 1 个字 → 把前面的重算 1 遍；
  • 蹦第 2 个字 → 重算 2 遍（第 1 个又算了一遍）；
  • 蹦第 3 个字 → 重算 3 遍；
  • ……蹦第 100 个字 → 重算 100 遍。

加起来：1 + 2 + 3 + … + 100 = 5050。只蹦了 100 个字，却做了 5050 次重算——平均每个字被重算约 50 遍。

再看谁被重算得最多：第 1 个被算 100 遍、第 2 个 99 遍……越靠前越惨。这就是"平方级浪费"：总量不是随长度线性涨，而是像 1+2+3+… 那样垒起来，约与长度的平方成正比。

（上面这个 5050 只算了"重算"那一部分。如果你还输入了一段长提示——比如 2000 个 token——没有缓存的话，每一步还要额外把这两千个一起重算。所以长提示 + 长输出 = 双重贵。）

KV Cache 就是：算过的 K/V 向量别扔，留着。这样蹦下一个字时，前面的直接拿现成，只算新蹦出来的那 1 个。100 个字的计算量，从 5050 次降到约 100 次。

注意：这一层没有「命中 / 不命中」

在一次请求内部，KV Cache 是必然生效的——算过的就留着，这是模型天生的做法，不是"看运气"。

所以那句话真正的意思是："KV cache 命中"这种说法，本身就不成立。"命中"是下面那一层的词。

代价呢？这些 K/V 要占显存。序列越长占得越多——这就是长上下文又慢又贵、且有上限的物理原因之一。

3. 跨请求：要条件满足才叫「命中」

现在看请求之间。你发的第 2 次请求，开头很可能和第 1 次一模一样（系统提示、工具定义、前面的对话）。

那这些算过的 K/V，能不能跨请求接着用？

能——但有条件。服务商会把上次算的 K/V 存起来，下次谁的开头跟它一字不差，就直接捡现成的用。这件事成功发生，才叫命中（cache hit）。

术语四连

前缀（prefix）：一次请求从第一个 token 开始的那一段。按官方的拼装顺序，它就是 工具定义 → 系统提示 → 消息（历史 + 这一句）——所以日常说"我的对话记录 + 提示词"，基本就是它。
命中（cache hit）：你的开头和缓存里某段对上了，白捡。
cache write / cache read：第一次写进缓存 / 命中读取（约 0.1× 价格，便宜约 10 倍）。
TTL（存活时间）：缓存不是永久的，几分钟没人用就过期。

（顺带说清"缓存什么时候没"：一次请求的 K/V，通常在请求结束时就被释放——显存要腾出来给下一个请求。只有服务商特意开的前缀缓存，才会把"前缀那一段"多留一会儿；而且它会过期（TTL），也只认一字不差的前缀。）

（写入为什么还要加钱？前缀越长越好吗？→ 进阶版 Q3 / Q4）

为什么必须是「前缀」，而且一断就全废

用接龙来想：缓存只能顺着最前面连续地往后延。因为第 5 个 K/V 是依赖前 4 个算出来的。你在前 4 个里改一个标点，第 5 个的结果就完全不同——从改动的位置往后，全部作废。

工具定义不变
→
系统提示不变
→
历史对话缓慢增长
→
用户这一句每次都变
绿色是「共享前缀」——它越稳定、越长，每次能省的就越多；红色的部分每次都得重算。

4. 输出的字，有缓存吗？

好问题，容易糊。答案分两半——机制和账单不是一回事。

机制上：不分输入输出

缓存里存的是K/V 向量，它不关心这段文字是"用户给的"还是"模型写的"。

  • 同一次请求内：模型刚蹦出来的字，它的 K/V 立刻被复用——不然 decode 就退化成平方级重算。这就是 KV Cache 的本义。
  • 跨请求：上一次的输出，要等到下一次它变成输入前缀的一部分，才能被复用。（多轮对话就是这样——上一轮模型的回答，这一轮成了"历史"。）
账单上：只对输入打折

缓存折扣（那个 0.1×）只作用于输入 token。输出 token 是另一个更贵的价，不享受折扣。

所以你的直觉"缓存只针对输入"——账单上对，机制上不完全对。输出的 K/V 照样在缓存里、照样被复用，只是不体现在折扣上。

那「工具结果」算哪一侧？（agent 场景一定会问）

答案是：算输入。

工具结果虽然不是你打的字，但它是在下一次请求里、作为 prompt 的一部分送进去的——所以按输入计价，也能命中缓存。

而且它在对话末尾追加，下一轮就变成了前缀的一部分。所以 agent 越跑，可命中的前缀越长（前提是前面的都没动）。（为什么说"末尾追加"这么重要？→ 进阶版 Q2）

（那"上一轮模型的回答"呢？→ 进阶版 Q1，有张官方给的时序表）

5. 三条铁律

  1. 稳定的放最前面：系统提示、工具定义、长文档。
  2. 易变的放最后面：用户当前这一句、新拿到的观察结果。
  3. 别做这三件事：动态改系统提示、临时增删工具定义、往对话中间插内容。开头多一个空格，后面整段就报销。

（典型应用：RAG 检索回来的那几段，就属于"易变的放最后面"——问题不同、检索到的段也不同，所以它们每次都变，必须排在稳定前缀之后。见 RAG · 第 2 课。）

为什么这对 agent 特别要命

因为 agent 一次任务 = 十几次请求，每次请求都要重发「系统提示 + 一堆工具定义 + 完整历史 + 新观察」。

开头不变 → 每次都命中 → 又快又省。为了"精炼"每轮重写系统提示 → 每次都归零 → 账单翻倍，而且是十几倍地翻。

6. 动手：亲眼看看差几倍

脚本在工作区：exercises/llm/0003-cache-hit-simulator.py。它模拟"前缀匹配"，对比两种结构的命中率和成本。

python exercises/llm/0003-cache-hit-simulator.py

Windows 终端若中文乱码，先执行 chcp 65001。

核心逻辑就这几行——注意那个 break：

hit = 0
for a, b in zip(cached, prompt):
    if a == b:
        hit += 1
    else:
        break        # 一旦对不上，从这里往后全部作废

我实测的结果（6 次请求）：

  • A. 前缀稳定：命中率 96%，合计等效成本 45；
  • B. 把用户名塞进系统提示开头：命中率 0%，合计等效成本 168；
  • 结论：B 明显比 A 贵，差距不是一点半点——而你只改了开头一个细节。（本课实测约 3.7 倍。）

挑战（选一个，5 分钟）

  1. 把 questions 从 6 个加到 20 个，看 A/B 的倍数怎么变（提示：第一次请求永远是冷的，请求越多，差距越大）。
  2. 试着把变化的东西挪到更靠后的位置，看命中率能救回来多少。
