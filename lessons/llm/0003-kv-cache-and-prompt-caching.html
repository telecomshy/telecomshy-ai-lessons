KV Cache 与「缓存命中」是两回事

一个决定你的 agent 花多少钱的小机关。它认的不是"你说了什么"，而是"开头一字不差"。

先别急着学，聊两句

跟模型聊久了，有没有觉得它变慢、变贵？更怪的是——你在提示词里改一个标点，账单能翻好几倍。

拆穿了其实很朴素：模型里有一套"算过的别重算"的机制在替你省钱，而它认的是"开头一字不差"。你动了开头，它就罢工。

但这套机制其实有两个，总被混为一谈。这一课先分清它们。

学完这课，你能：说清两个机制各管哪一层；看一眼 prompt 就判断会不会命中；并且不再被"请求"这个词绊倒。

记住一条主线，后面就不会晕

两个机制，管的是不同层的事：

KV Cache　＝ 一次请求内部，算过的别重算。总是发生，没有"命中/不命中"。
缓存命中　＝ 跨多次请求，上次算的这次接着用。要条件满足，才有"命中/不命中"。

所以——先得知道"请求"是哪一层。

1. 先把「请求」这个词钉死

本课要说"请求内"和"跨请求"，得先知道请求指哪一层。第 2 课已经钉过，这里只复述本课用得上的两个：

  • 一次请求　＝　一次 API 往返：你发过去，它把答案回过来。
  • 一次任务　＝　用户发起的一整件事。聊天时它大概等于一次请求；agent 一次任务会发出十几次请求，每调一次工具就是一次新请求。

为什么非要分这一层？因为"命中"这个词只在请求之间才有意义——一次请求内部没有"碰巧"这回事，那是下一节要说的。

（这一组词，术语表里一次钉全了；本课只用到"请求"这一层。）

2. 请求内：算过的别重算（KV Cache）

先把一次请求的样子想起来，这正是第 2 课讲的：你输入的那一整段（n 行）一次性、并行算完，这一段叫 prefill；之后每蹦一个字，只算新蹦出来的这 1 个，前面那些从显存里取，这一段叫 decode。

所以"一个一个来"只发生在输出那一段，输入那段从来不会重算。这就是本课的第一个机制：请求内复用 ＝ 后面每一步，接着用这一步之前算好的。它跟"跨请求复用"（这一次请求接着用上一次请求算好的）不是一回事——后者要条件，见第 3 节。

那 KV Cache 省的是什么？省的是输出阶段的重算。假设没有它，每蹦一个字都得把前面的全部重新算一遍：

  • 蹦第 1 个字 → 把前面的重算 1 遍；
  • 蹦第 2 个字 → 重算 2 遍（第 1 个又算了一遍）；
  • 蹦第 3 个字 → 重算 3 遍；
  • ……蹦第 100 个字 → 重算 100 遍。

加起来是 1 + 2 + 3 + … + 100 = 5050：只蹦了 100 个字，却做了 5050 次重算，平均每个字被重算约 50 遍。而且越靠前越惨——第 1 个被算 100 遍、第 2 个 99 遍。总量不是随长度线性涨，而是像 1+2+3+… 那样垒起来，约与长度的平方成正比。

KV Cache 就是解法：算过的 K/V 别扔，留着。蹦下一个字时，前面的直接拿现成，只算新蹦出来的那 1 个——100 个字的计算量，从 5050 次降到约 100 次。

还得说清一句：这一层没有"命中/不命中"。在一次请求内部，KV Cache 是必然生效的，算过的就留着，模型天生这么跑，不是看运气。所以"KV cache 命中了"这种说法本身就不成立——"命中"是下一节那个机制的词。

它的代价是占显存：序列越长占得越多。这就是长上下文为什么又慢又贵、而且还有个上限——物理原因之一。

3. 跨请求：条件满足了才叫「命中」

现在把镜头拉到请求之间。第 2 课结尾留了个话头：想让首字更快，可以"把每次都一样的开头缓存起来"。这一节讲那是怎么做到的。

实际上，你发出的第 2 次请求，开头很可能和第 1 次一模一样：同一份系统提示、同一批工具定义、同一段历史对话。那些算过的 K/V，能不能接着用？

能，但有条件。服务商会把上次算好的 K/V 存起来；下次谁的开头跟它一字不差，就直接接着用，不必重算。这件事真的发生了，才叫命中（cache hit）。能被接着用的那一段叫前缀（prefix）——一次请求从第一个 token 开始的那一截，按官方的拼装顺序是工具定义 → 系统提示 → 消息（历史 ＋ 你这一句），日常说的"提示词 ＋ 对话记录"基本就是它。

这里有笔账要分清，否则"便宜 10 倍"很容易被听成"免费"：把这段前缀存进去，这一次照常计费（有的服务商还收得更贵一点），读缓存那一次才是折扣价——约 0.1×，也就是便宜约 10 倍。（缓存到底省了什么？）还有一件要记住：缓存会过期，通常几分钟到一小时，所以它不保证下次一定命中。

还要说清一件容易误会的事：一次请求的 K/V 通常在请求结束时就被释放——显存要腾出来给下一个请求用。跨请求还能接着用，是因为服务商特意留了"前缀缓存"这一份，它比普通缓存活得久一点，但同样会过期。

为什么非得是「前缀」，而且断一处就全废

用接龙来想：缓存只能从最前面连续地往后延。因为第 5 个 K/V 是拿前 4 个算出来的，你在前 4 个里改一个标点，第 5 个的结果就完全不同——从改动的那一处往后，全部作废。

工具定义不变
→
系统提示不变
→
历史对话缓慢增长
→
用户这一句每次都变
绿色是「共享前缀」——它越稳定、越长，每次能省的就越多；红色的部分每次都得重算。

4. 输出的字，有缓存吗？

这个问题容易糊，因为同一段文字会在好几笔账里反复出现。跟着"上一轮模型写出来的那几个字"走一遍就清楚了。

它刚被生成的那一次请求里，按输出价计费——输出 token 是最贵的那一档。

到了下一轮，这几个字不再由模型写，而是跟着历史对话一起送进去，于是它变成了输入。输入同样要钱，但它已经算过一次了：命中缓存就按缓存读价算，约 0.1×，比原价便宜约 10 倍。（上一轮的回答具体怎么命中？）

可你要是动了前缀——换了工具定义、临时改了系统提示——从改动那一处往后的内容全部重新算，之前模型写过的字也一起算进去，这时候它们按原价的输入价收费，一分不省。

那工具结果算哪一侧？算输入——它是在下一次请求里作为提示词的一部分送进去的，所以按输入计价、也能命中。而且它加在末尾，只往后接、不动前面的，所以 agent 越跑，可命中的前缀越长（前提是前面的都没动）。

所以"缓存只针对输入"这句直觉要改一个字：折扣不跟着"输入还是输出"走，跟着"这一轮是读缓存还是重算"走。机制上 K/V 也不挑作者——用户打的字和模型写的字，在它眼里没区别。

5. 三条铁律

  1. 稳定的放最前面：系统提示、工具定义、长文档。
  2. 易变的放最后面：用户当前这一句、工具刚返回的结果。
  3. 别做这三件事：动态改系统提示、临时增删工具定义、往对话中间插内容。开头多一个空格，后面整段就报销。

为什么这三条对 agent 特别要命？因为agent 一次任务会发出十几次请求，每次都得重发「系统提示 ＋ 一堆工具定义 ＋ 完整历史 ＋ 这一轮新加的那点东西」。这四样里只有最后一样每次都变（你刚问的那句、工具刚返回的结果），前面三样不动，每一次请求都命中——多轮对话越聊越省，省的就是它。

要留意的是别在多轮对话进行到一半时动工具定义：增删一个工具、换一批工具。因为工具定义排在最前面，一改就是从第一个 token 起全部重算——这一遍付全额，前面几轮攒下的便宜一次性吐回去。不过只贵这一遍：这一遍算完，缓存里又存下一份对得上的前缀，下一次请求照样命中。（要改就在开场之前改好；中途确实要换，就另起一段对话——这条属于工程做法，在技巧篇 0001 · 上下文工程）

一个现成的例子是 RAG：检索回来的那几段，问题不同、结果也不同，每次都变，所以必须排在稳定前缀之后，不能塞在最前面。

6. 动手：亲眼看看差几倍

脚本在工作区：exercises/llm/0003-cache-hit-simulator.py。它模拟"前缀匹配"，对比两种请求结构的命中率和成本。

python exercises/llm/0003-cache-hit-simulator.py

Windows 终端若中文乱码，先执行 chcp 65001。

核心逻辑就这几行——注意那个 break：

hit = 0
for a, b in zip(cached, prompt):
    if a == b:
        hit += 1
    else:
        break        # 一旦对不上，从这里往后全部作废

我实测的结果（两次对话各问 6 个问题。第 1 次请求永远是冷的——缓存里还是空的，所以 A 从第 2 次才开始命中）：

请求结构 命中率（第 2 次起） 合计等效成本
A · 前缀稳定 96% 45
B · 把每次都变的用户名塞进系统提示开头 0% 168

B 比 A 贵了约 3.7 倍——而你只改了开头一个细节。

挑战（选一个，5 分钟）

  1. 把 questions 从 6 个加到 20 个，看 A/B 的倍数怎么变（提示：请求越多，差距越大）。
  2. 试着把变化的东西挪到更靠后的位置，看命中率能救回来多少。
