总链先放这儿，方便对照：文字 → token → 编号 → 向量 → [注意力 → 残差 → FFN → 残差] × N → 打分 → 百分比 → 采样

Q1 · 词表是什么？有多大？遇到生词怎么办？

它不是解释意思的词典，就是一张清单：模型认识的每一个 token 都列上，每条配一个编号。所谓"对号"，查的就是这张表。

  • 有多大？各家分词器的实测数字：GPT-2 ＝ 50,257；GPT-4（cl100k_base）＝ 100,256；GPT-4o（o200k_base）＝ 199,997；Llama 3 ＝ 128,000。
  • 它跟分词器是一套的、绑死的。分词器学出来的"合并规则"决定了哪些片段算 token，词表就是这些片段的名单。换掉分词器，同一段文字切出来的编号完全不同，模型也就认不出来（所以分词器是原配，不能随便换）。
  • 遇到生词怎么办？词表外的东西没有编号，只能切成词表里有的小块拼出来。所以"模型的词汇量"＝词表大小——它只能输出词表里存在的 token。
  • 它跟最后一步的关系：打分时逐个对分的对象就是这张表。词表多大，logits 就有多少个数（十几万到二十万个分）。

Q2 · 嵌入表是什么？查表怎么就查出向量了？

它就是一张大数字表：词表多大就有多少行，每行 d 个数。拿编号去查第 N 行，就是查表；把这一行读出来，那根向量就有了——所以这一步只是照抄，不用算。

  • 嵌入表有多大呢？词表行数 × d。GPT-2 小模型 ＝ 50,257 × 768 ≈ 3,860 万个数字，而整个模型 1.24 亿——三分之一的模型是这张表。GPT-3（1750 亿）＝ 50,257 × 12,288 ≈ 6.2 亿，却只占整个模型的 0.35%。规律：模型越小，词表这块占得越重；到今天这个量级，权重基本都在后面那几十层里——第 0 课说的"骨架"才是主体。
  • 嵌入表就是第 0 课提到的权重参数中，最大的一块。训练刚开始时它是一堆很小的随机数，之后每一轮都被梯度更新一点点——具体怎么从随机数长成有意义的向量，下一问接着说。

关于嵌入表，有两点要注意：

  • 坑一：向量不能跨模型比。d 是每个模型自己定的（小模型 256 / 768，大模型 4096 / 8192），跟词表是两回事。「天」在 A 模型的向量和在 B 模型的向量毫无可比性——只有同一个模型的同一张表里，两串数字才能比。所以"越接近说明关系越近"这句话，只在同一个模型内部成立。
  • 坑二：它常常兼任输出那层。不少模型（比如 GPT-2）让嵌入表和最后打分用的那张表是同一张——同一个 token，"进来时的向量"和"出去时打分的权重"是同一行数字。也有的模型分开训练，见 LM Head。

Q3 · 嵌入表是怎么训练出来的？它一开始不就是一堆随机数吗？

对应 第 0 课那套「出题 → 扣分 → 拧」的训练流程。这里分开答四个问题：表什么时候定下来 · 一开始里面是什么 · 答案是从哪来的 · 每一步在拧什么。

先说表什么时候定下来：训练开始的那一刻，V × d 的矩阵已经分配好了——V ＝ 词表大小（GPT-2 是 50,257），d 是这个模型自己选的（GPT-2 是 768），哪一行对应哪个 token 也在这一刻定死（词表早就冻结了）。所以准确的说法不是"一开始没有嵌入表"，而是：一开始就有了一张形状已定的表。

那里面装的是什么？随机数——0 附近的小随机数（GPT-2 取的是标准差 0.02 的正态分布）。此时模型给每个字的打分基本随机，平均扣分约 ln(50257) ≈ 10.8——训练刚开始的模型是在均匀地乱说。

看到"全是随机数"，很容易卡住下一步：那"正确答案是哪个字"从哪来？——从词表来，跟嵌入表无关。用「天气很好」走一遍：

输入侧   「天气很」→ 查词表 → 312, 1092, 55 → 拿这三个编号去嵌入表取第 312/1092/55 行
         ＝ 三根向量，进模型

目标侧   「好」    → 查词表 → 4021
         ＝ 训练信号：第 4021 个分数该最高

输出侧   最后一根向量 → 跟嵌入表每一行都算一遍相似度 → 得到 50257 个分数
         其中第 4021 行的分，就是「好」的分数

这里的关键是：标准答案早就是已知的——词表在训练之前就冻结了，「好」的编号就是 4021，跟嵌入表此刻填着什么数字毫无关系。所以"表里全是随机数"，一点不妨碍我们出这道题。

那怎么知道答得好不好？把预测出来的那根向量，跟嵌入表的每一行各算一遍相似度（打分用的就是这张表本身——权重共享，见 Q2 的坑二）：第 4021 行的相似度应该最高。是不是最高，一眼就知道——差多少就扣多少分，再往回拧参数，拆开就是下面这几步：

  • 出题：抓一句现成的话，往后挪一格，标准答案自带。
  • 对答案：答案「好」查词表得 4021。训练信号就是一个 one-hot——50257 个位置里第 4021 个是 1，其余全是 0。
  • 算扣分：模型在第 4021 个位置上给了多少分，跟 1 差多少。
  • 往回拧：从出口追责一路追到入口，落在刚才读进来的那几行上——被读进来的每个 token，它那一行都被拧一点点。「这一行是训练出来的」说的就是这个。打分那头也一样被拧："「好」该得高分的那个权重"也是训练拧出来的（权重共享时，它就是第 4021 行本身）。

所以那 3860 万个数字，没有一个是人填的，也没有一个是事先安排好的——每一轮都被扣分推一小步，跑完整个语料之后，才长出"「好」跟「很」关系近"这类规律。

（顺带解释「权重共享」为什么能成立：共享时「好」那一行同时出现在两处——进来时当上下文、出去时当打分依据，而训练本来就同时在这两个方向上拧它，所以它们能长在同一行。坑二见 Q2。）

Q4 · 分词、查词表这两步，算不算「模型」的一部分？

分词、查词表这两步看着像"模型在干活"，其实不是——

步骤 算不算模型 说明
分词 tokenizer❌ 不算配套的小程序，把文字切成 token
查词表 vocabulary❌ 不算同一个小程序，把 token 变成编号
查嵌入表 embedding✅ 算就是模型的第一层，参数是训练学出来的

那「输入模型的」到底是什么？两种口径都对，看你把边界划到哪：

  • 宽口径：模型吃的是张量（n 行 × d 列）。
  • 严口径：模型吃的是编号（一串整数）；第一层（词嵌入表）把编号变成张量，张量才进 N 个 Block。

差别只在"词嵌入算不算模型的开头"。因为它是训练学出来的参数（会被梯度更新），算。所以严口径更准：模型 ＝ 词嵌入表 ＋ N 个 Block ＋ LM Head，分词器站在门外。

那每一轮都要重做吗？都要做——但便宜的那几步每次都重来，贵的那几步靠缓存避开。

  • 分词 / 查词表 / 查嵌入：每轮都要走一遍（至少对新增的部分）。这几步是纯查表，几乎不花时间。
  • N 个 Block 的计算才是贵的。而这部分，前面 token 走过的路会被 KV Cache 省掉，只算新蹦出来的那一个——这就是第 3 课的主角。

"每轮都查嵌入"确实是重复，但那就是一次表查找，成本可忽略；真正被缓存省掉的是后面几十层的计算。

Q5 · 为什么是「n 行 × d 列」的表，而不是把 n 串拼成一根大向量？

核心在权重共享（weight sharing）：表里的 n 行用的是同一套换算规则，不是 n 套。更像"一个老师同时批改 n 份卷子，用同一把尺子"。

  • 为什么不能拼？一旦拼起来，3 个字和 4 个字拼出来的长度就不一样了——同一把尺子就没法用在每个位置上。只有每一串都同样长（d），同一套规则才能通吃所有位置、所有长度。
  • 所以是"表"不是"一根"：d 固定、n 可变。再多一个 token，表就多一行，别的什么都不用改。
  • 那 n 行是 n 个各干各的小单元吗？画面可以这么想，两处要修正：① 用的是同一套规则，不是 n 套；② 不是每一步都互相看——只有注意力那一步互相看，FFN 那一步各走各的。
  • 真在显卡上跑时并没有真的摆 n 个小零件——是把 n 行数字排成一张表、一次算完。但逻辑上按"n 个位置各走各的"想没问题。

Q6 · 表里的 n 行，互相能看到对方吗？（因果掩码）

不能随便看。每个位置只能看自己和它之前的那些行，看不到后面——后面还没写出来。这个硬规定叫因果掩码（causal mask）。

为什么必须这样？模型的任务是"猜下一个字"，要是能看到后面的字，就成了抄答案。

那能不能看到更少？掩码划的是上限，不是下限。既然"往右看"是禁止的，那"往左看太远"完全可以再收一收——这叫滑动窗口（sliding window）：每个位置只允许看最近 N 个，更早的那些干脆够不着了。

做法 每个位置能看到 代价
标准注意力 全部前文 看得越全越准，但算得慢、占地方
滑动窗口 只有最近 N 个 更快更省，但老信息够不着了

要注意：滑动窗口是真的把老货位扔掉（不是"留着但不读"）。生产上确实在用——Mistral 7B 就是滑动窗口：官方原话是每一层只关注前 4096 个 token，靠层数堆叠把有效上下文撑到 32k。所以这不是教科书里的选项，是跑在生产上的模型的选择。（那么"每步都得把缓存扫一遍"这件事在滑动窗口下也不成立了。）

Q7 · FFN 那一步到底在改什么？

它做的是一次更细的改写：把训练里学到的知识，按当前的语境补进这根向量——某个概念被补上，它的分就往上抬。

拿一句真话走一遍。Eiffel Tower is located in ⊙（埃菲尔铁塔位于 ⊙）：下一个字还没出现，但要决定它的那根向量已经有了——就是那张 n 行 × d 列向量表的最后一行。这一行的向量是经过注意力层才算出来的：前面各行先算出各自的 k、v，注意力再把它们的信息取回来、混进这一行——⊙ 向量里面因此包含了"埃菲尔铁塔位于"的语境信息。它是一根实打实的向量，只是还不代表任何一个字。这时 FFN 上场——

  • FFN 的权重也是训练学出来的：里面存着一条条"模式 → 该补什么"的对应，很像一张查找表。
  • 认出模式，就精修向量：让 ⊙ 这根向量最后被预测成「Paris」的几率变大一点。

所以 FFN 干的活是补充知识、推动概念：它不是变出答案，是把答案的分抬起来——等走完剩下的层、到最后一站打分，「Paris」的分就显出来了。（论文原例就是这句：Geva et al., EMNLP 2021。）

（上面走的只是一层里的事：真实模型有几十层，每一层都这么来一遍——⊙ 这根向量被一层层反复精修。下一问看它"改到一半"什么样。）

Q8 · 中间某一层的向量，能不能直接拿去用？

那根向量改到一半，能不能直接拿去用？

能，而且结果有点意外。就算只走一半的层，拿当时的向量去词表里对分，也能猜出个大概。

这说明预测是一层一层"磨"出来的，不是最后一层突然顿悟。Geva et al.（EMNLP 2022）甚至把它看成"逐层推动概念"的过程。

（这个手法有个名字叫 logit lens：把中间那层的向量，直接接到最后那道"打分"的表上，偷看它当时想说哪个字。正式出处见下面的 Belrose et al. 2023。）

Q9 · 上下文窗口是什么？它是哪一步的上限？

上下文窗口（context window）是"模型"的属性：它就是送给模型的那张表（n 行 × d 列），行数 n 的上限。流程是切分 → 查编号 → 查表 → 送进模型——前三步都在门外，窗口卡的是最后那一步。所以超没超，切分完数一下行数就知道，不用等送进去才发现。

它数的是这张表的行数：每一行就是一个 token 的位置（第几个进来的，就是第几行）。而且输入的和模型写出来的都算——写出来的字得留在前文里，供后面回头去看：

上下文窗口 ＝ 一次请求里 token 向量的个数：输入的 ＋ 已经写出来的，加起来不能超过它。

所以厂商标的"百万上下文"，说的就是这个上限。多轮会话里，每一轮请求都把前面的全部内容重新带上——用户的提问、模型的回答、连"思考"的 token 都算（它们是真 token，见 第 5 课）：越聊越长，直到顶到上限。

那上限是谁定的？模型定的。架构、位置机制、训练时定下的长度，厂商标出来的那个数就是它——换一块更大的显卡，窗口不会变大。它跟 KV 缓存没有直接关系，只有一个连带：每一行都要留一份 K/V，所以窗口越大、要留的 K/V 越多，显存的账越重——那是代价，不是上限。（如果前缀命中了缓存，行数照样占——缓存省的是"重算"，不是"行数"，见 第 3 课进阶 Q6。）

真超过上限会怎样？官方 API 直接把这次请求拒掉、报错（Anthropic 文档的原话：输入超过窗口就返回 prompt is too long 的 400 错误），不会偷偷丢掉前面的内容。真嫌长，得你的程序在送进去之前先删掉或压缩掉一部分——往里塞什么、丢掉什么，就是 上下文工程。

最后说 agent：它的一次请求里装的比普通对话多好几样，而且有几样用户根本看不见：

  • 用户看不见的：系统消息、工具定义与说明——用户从没见过它们，但每一轮都完整地占着窗口；
  • 看得见的：用户的提问、模型的回答；
  • 中间产生的：工具调用与工具的返回、模型的思考。

全都占窗口。它们拼进前缀的顺序各家不完全一样（术语表按 Anthropic 文档记的是：工具定义 → 系统提示 → 消息）——顺序只影响缓存能不能命中；不管什么顺序，全部都会占窗口。

Q10 · 「按百分比抽一个」到底是怎么抽的？temperature、top_p 调的是什么？

从分表里挑一个字，听着像只有一种挑法。其实不是——怎么挑是你可以调的，那一组旋钮叫采样参数，随请求一起传。

先把这一环摊开，因为它中间隔着好几步，而每一步都有个容易搞错的地方：

最后一层、最后那根向量
      │ ① 乘上「反嵌入表」—— 给词表里十几万个字，每个打一个分
      ▼
  十几万个分数（叫 logits）
      │ ② softmax → 换算成百分比
      ▼
  十几万个百分比
      │ ③ 挑一个（默认按百分比抽签；温度推到 0 就变成挑最高——这一步叫采样）
      ▼
  一个 token 编号   ←←←  这个才是「蹦出来的那个字」
      │ ④ 下一轮：拿这个编号去查表
      ▼
  一根新向量 → 再走一遍

向量 →（打分）→ 分表 →（挑一个）→ 字 →（查表）→ 新向量。中间那步不能省——模型直接产出的不是字，是那张分表；字是从分表里挑出来的。

③ 这一步挑出来的其实是编号，不是向量。要变回向量，得拿这个编号再查一次嵌入表——这就是下一轮送进模型的那一行从哪来。（所以第 2 课的「一轮吐一个字」，交到手上的一直是编号；这一点跟prefill / decode 无关，两段都一样。）

模型只负责给出那张分表（logits）。分表之后的事，模型管不着。

温度、top_p 这些一个都不改分表，只改"从分表里挑一个"的规则。所以调温度不会让模型变聪明或变笨——只会让它的话更多样，或者更保守。

那"挑一个"到底是怎么挑的？默认是按百分比掷一次骰子——把那些百分比当成概率，抽签抽一个。拿下面「动手」那节的分表当例子（5 个候选）：T = 1 时是「好」49.7%、「冷」20.7%、「坏」13.9%、「差」9.3%、「热」6.4%，抽一千次大约一半落在「好」上；温度调到 0.2，「好」被拉到 98.6%，几乎每次都抽中它；调到 2.0，「好」只剩 33.7%，五个字都常有机会。每一次抽中哪个都是随机的，不是每次都挑最大的。那四个旋钮，调的就是"掷骰子之前，概率长什么样"和"谁有资格进签池"：

旋钮 干什么 效果
temperature
温度		 换算百分比之前，把所有原始分除以 T 只改差距有多悬殊，不改名次。T = 1 原样；T 越小越尖（几乎只挑那个高的），T 越大越平（小概率的字也有机会）
top_k 只留分数最高的 k 个，其余直接出局 按个数砍尾巴
top_p
（核采样 nucleus）		 从高到低累加百分比，加够 p 就停；留下的那一批叫核 按攒够多少砍尾巴——分布尖就少留几个，分布平就多留几个
seed
种子		 让"抽"这个动作可以复现 不改分布，只固定运气

温度是最该先动的那个旋钮，它只改"差距有多悬殊"：T = 1 原样不动，换算出来的就是模型给的那个分布本身；T 小于 1，差距被拉大、分布变尖——回答更稳、更保守，适合要准的场合；T 大于 1，差距被拉小、分布变平——小概率的字也有机会，回答更发散、更有创意，也更容易跑偏。把温度推向 0，就看见了另一种挑法：百分比塌成一个点，"按比例抽"退化成永远挑最高分——那叫贪心（greedy），已经不是抽了。（贪心不是万灵药：论文的结论正是"拿最大值当生成目标，对开放式写作不合适"。）

工程上的常用值（速查 · 采样参数 的推荐）：temperature 0～0.3 要准、0.7～1.0 要多样；top_p 0.9～0.95（1.0 ＝ 不砍）；top_k 40～100，但多半保持关掉。落到场景上：工具调用 / JSON、总结 / 抽取 / 翻译 → 温度 0～0.3；创意写作 / 头脑风暴 → 0.8～1.2；评估 / 回归测试 → 温度 0 ＋ 固定 seed，而且要跑多遍（T = 0 也不保证逐字一样）。

两把刀叠着用的时候，有先后。通行顺序是：先按温度调锐度 → 再用 top_k / top_p 砍尾巴 → 最后从剩下的里面抽（HuggingFace 的 generate 里就是按这次序排成一串处理器）。所以两把刀叠着用时各砍各的，起作用的往往是更紧的那把。

那"挑"这个动作，到底是谁在执行？模型只算到分表为止。真正动手挑的，是跑模型的那个推理引擎——vLLM、SGLang，或者各家 API 的服务端。所以同一个模型换一家部署，同样的参数不保证挑出一模一样的字。

那为什么现在很少听人提这些了？因为 harness 把旋钮收走了，替你定了一套默认值，你只管写提示词。藏起来不等于不存在——它正是"同一个 prompt 两次答案不一样""评估跑两遍对不上"的来源。什么时候该自己动手调，见 速查 · 采样参数。

Q11 · 关于向量本身，哪五个地方最容易说错？

这五处都是把向量想成了别的东西，一个一个来：

  • 别去猜每个数字的含义。不要想象"第 1 个数字代表'动物性'、第 2 个代表'大小'"——这些数字人读不懂，是模型自己学出来的。
  • 它不是词典里的意思，而是"此刻、在这句话里"的意思——所以会随前文变化。
  • 它不是死的。整条流水线剩下的工作，就是反复修改这串数字——从嵌入表查出来的那一刻起，这根向量就一直被改写到最后一层。
  • token 也不是向量。token 是文本零件，先变成编号，编号才变成向量（见 Q1）。
  • 每过一层，都是同一根在变——不是每层造一根新的。改写它的是每层那四步（注意力 → 残差 → FFN → 残差），式子就是那句「新的 ＝ 原来的 ＋ 从别人那里取来的」：只增补、不覆盖——这根向量从嵌入表一路走到最后，每一层往它身上加一点东西。
    （这根正在被改写的向量，正式叫 hidden 向量（hidden state）；它不被缓存——要缓存的是每层从它身上投影出来的 K/V，理由见术语表。）
