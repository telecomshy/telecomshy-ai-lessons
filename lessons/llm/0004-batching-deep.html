批处理：拐点、工业界的招

初学版讲「为什么能提吞吐」，这篇答「它什么时候到头、工业界怎么绕过去」。按需跳读——每条都能从初学版的括号直达。

怎么用这篇

只收读完初学版仍会冒出来的疑问。初学版已经讲清楚的（"一趟装满 N 个包裹""吞吐涨、延迟也涨"），这里不再重复。

总链先放这儿，方便对照：权重 + N 份 KV 一起搬 → 批越大吞吐越高 → 但搬运里 KV 占比越来越大 → 某个点开始卡算力 → 工业界用三招绕开

Q1 · 那个「拐点」长什么样？为什么批大了吞吐就不涨了？

接着第 2 课（进阶版）· Q2的算术强度往下推。一批 N 个请求走一步：

要搬的（约） 要算的（约） 算术强度
权重 W ＋ N 份 KV N × 单 token 计算量 随 N 一路涨
刚开始：分母里权重占大头 分子很小 卡带宽
N 很大：分母里KV 才是大头 分子线性涨 涨到显卡那个比值 → 卡算力

一旦算力用满，吞吐就等于显卡的算力上限，再往上堆批量也涨不动了——可延迟还在一份一份地涨。所以存在一个"甜点批大小"，越过它就是纯亏。

这解释了配套脚本为什么跑不出拐点

配套脚本是个只画了"搬运"那一半的模型：没有算力上限，所以它永远只会一路渐近，撞到的是显存的墙。真到拐点长什么样，脚本演不出来——那个数字来自 Databricks 的实测（批 64 时吞吐 14×、延迟 4×，再往上吞吐就基本不涨）。

Q2 · 队头阻塞是什么？连续批处理怎么解决？

问题出在"一批"这个单位是怎么定的。

朴素批处理：一批请求凑齐，一起跑，得等最慢的那个跑完，整批才能散才能接下一批。于是——一个短请求跟一个长请求凑成一批，短的就得陪着干等。这叫队头阻塞（head-of-line blocking）。

连续批处理只改了一件事：把"一批"的单位从"一整个请求"缩到"一个 token"。

  • 每走一步就重新组一次批；
  • 谁跑完了立刻退出，空位当场塞进新请求；
  • GPU 不再等最慢的那个。

效果：Orca 论文报告同延迟下吞吐提升 36.9 倍；vLLM 自己测是 23 倍。

Q3 · PagedAttention 在解决什么问题？

这条跟"搬运"和"算力"都没关系，它管的是显存怎么摆。

问题出在"预留"：请求长短不一，但按连续显存分配的规矩，你得按最长的那份预留。结果短请求占着一大块只用一点点，碎片一堆，谁也塞不进去。

PagedAttention 借的是操作系统管内存的老办法：把 KV cache 切成固定大小的"页"，哪一页要用才分配。于是几乎不浪费显存 → 能塞进更多请求 → 批能开得更大。

接回 Q1

所以三条其实是一条链：PagedAttention 抬高"能开多大的批"，连续批处理让"每一批都塞得满"，而 Q1 那个拐点决定"开到哪儿就该停"。三件事缺一件，收益就打折。

Q4 · 分块预填充和 prefill/decode 分离，是两件不同的事

这两件事解决的不是同一个毛病。

分块预填充（chunked prefill）：同一批机器上错开

第 2 课说过两段瓶颈相反。于是一段超长输入会让 GPU 忙着算很久，正在解码的那些请求被晾在一边。

改法：把长 prefill 切成小块，和 decode 交替跑。代价是首字延迟可能略升，回报是总吞吐更高。据 Weka 的综述，Sarathi 论文引入这一招，可带来最多 6.9 倍吞吐提升。

prefill/decode 分离（disaggregated serving）：换一批机器

更彻底：干脆把两段放到两批不同的机器上，各用最适合的硬件。

据 Weka 综述，DistServe（OSDI 2024）报告多服务 7.4 倍请求，或 SLO 达标收紧 12.6 倍；Perplexity、Meta、LinkedIn、Mistral 都已在生产里这么跑。

一句话分清

分块预填充是"错开"，prefill/decode 分离是"分家"。前者还在同一批卡上，后者要跨机器调度。
