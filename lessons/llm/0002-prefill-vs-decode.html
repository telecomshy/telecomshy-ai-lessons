LLM 底层 · 第 2 课 · 初学版

为什么「读长文」快、「写长文」慢？

同一条流水线，两种完全相反的跑法：prefill 与 decode。

先别急着学，聊两句

同样是跟模型打交道：让它读一篇长文档，几秒钟就"看完"了；让它写一篇同样长的文章，慢得让人想砸键盘。

更怪的是——读长文档明明是更多的字，为什么反而快？

拆穿了很简单：模型跑的始终是同一条流水线，但"跑法"分两段。第一段一次能跑一大批字，第二段一次只能跑一个字。

学完这课，你能：说清这两段各在干嘛、为什么要这么分；判断一个请求是"读长文型"还是"写长文型"，谁更慢、谁更贵；并且能回答"为什么首字等了很久、后面却唰唰地出"。

一条主线，记住它就不会晕

第一轮跑这条流水线 ＝ prefill（预填充）；后面每一轮 ＝ decode（解码）。

本课所有结论（谁快谁贵、TTFT、TPOT）都从这一句推出来。

1. 先回顾：模型这条流水线

第 1 课我们完整走过一遍，这里只把最关键的一行复述一下：

文字 → token 编号 →（查表）→ 向量
     → 穿过 N 层（每层都是：注意力 → 残差 → FFN → 残差）
     → 打分 → 采样（挑一个）→ 下一个字

三件事记住就够了：

  • 入口：字先变成向量（查嵌入表）。
  • 中间：向量要一层一层往上走——几十层，每层都在那根向量上改写一次，每层都有自己的权重。
  • 出口：最后那根向量拿去打分，再挑出一个字。（挑出来的其实是编号，要变回向量还得再查一次嵌入表——见下面第 3 节）

上面那条链，是「跑一趟」的配方。第 1 课当时只关心一趟怎么走完 —— 走完，一个字就出来了。

可一次请求，要把这条流水线跑很多趟。而且 —— 第一趟和后面几趟，跑法不一样：

第一趟，你给的那一整段是一起跑的；后面几趟，每次只补一个新字，前面那批字不再重新处理（它们的 k、v 已经存在显存里，直接拿来用）。

这个差别，就是本课的全部内容。下一节展开。

2. 一次请求，要把这条流水线跑很多轮

关键在这儿：这条流水线一次只吐出一个字。所以要写出一整段话，得把它跑很多轮。

你的输入（系统提示 + 历史 + 这一句）
   —— 拿「你是谁」→ 回「我是…」举例 ——
        │
        ▼
第 1 轮：把「你」「是」「谁」一起喂进去跑完 → 挑出「我」
        │
        ▼
第 2 轮：只把「我」补进去，再跑一轮 → 挑出「是」
        │
        ▼
第 3 轮：只把「是」补进去，再跑一轮 → 挑出「一」
        │
        ▼
   ……一直跑到结束（遇到结束符，或到长度上限）

第 1 轮：喂进去的是你给的一整段 —— 里面一个模型产的字都没有。而且这些字全是已知的，所以能一起跑。这一轮有个专门的叫法：prefill。

第 2 轮起：只补刚刚挑出来的那一个字。为什么不多补几个？因为再往后的字，得等它先被挑出来，才知道是什么。后面所有轮都叫 decode。

第 1 课我们知道模型内部分很多层，刚才又说吐一个字算一轮。这两个词长得像，意思完全不是一回事。我们把这几个词明确一下，免得以后搞混：

  • 请求：一次 API 往返 —— 你发过去，它把答案回过来，算一次请求。
  • 一轮：模型内部每蹦出一个字，就要把整条流水线完整走一遍。这一趟就是一轮。一轮里，那根向量要穿过所有层才走得完。
  • 层：模型的内部结构，跟对话流程无关。真实模型有几十层，原始论文只有 6 层——所以「跑一遍」听着像一步，其实是几十步。

最容易错的一处：一轮 ≠ 一层。一轮 ＝ 把全部层走完；「再走一遍」是第二轮，不是第二层。

一次请求里有 1 次 prefill ＋ 若干次 decode，为什么这么分，见下一节。

3. 于是分了两段——为什么第一轮叫「预填充」？

这两轮干的事不一样，名字也不一样：

第 1 轮 ＝ prefill（预填充）　·　第 2 轮起 ＝ decode（解码）

分界线只有一条：这次喂进去的，是你给的字，还是模型自己刚蹦出来的字。

那为什么第一轮叫「预填充」？得先看注意力那一步在干嘛（每层里都有这么一步）。

每个字都会算出自己的三样东西：q（我要找什么）、k（我是谁）、v（我能提供什么）。
然后拿自己的 q，去跟前面所有字的 k 比一遍；再按比出来的比例，把它们的 v 取过来、汇总。

所以你看：要算任何一个字的注意力，都得用到前面所有字的 k 和 v。那模型就得把它们存起来（存在显存里，正式名字叫 KV cache）。

每个字的注意力都要算，一个都不少——但这一批可以一次算完，不用排队。因为算某个字的 k、v 只用到它自己那一行，谁也不依赖谁。（为什么"看前面"不等于"等前面"？→ 进阶版 Q9；那"一个都不少"是为什么？→ Q10）

于是第 1 轮跑完，有两个产出：摆满 k、v 的货架，和第一个字（也就是这次请求返回给你的、用来回答你问题的那个字）。pre（预先）＋ fill（填充），名字就是这么来的。

补一件容易想当然的事：你给的每一个字，模型都预测了一遍下一个字——「你」预测「是」，「是」预测「谁」，「谁」预测「我」。但只有最后一个字的预测被留下，前面几个的预测全部丢掉，因为只有它后面还接着内容。真正返回给你的，只有从「谁」那儿预测出来的「我」。（为什么能这样、以及为什么前面几个字连自己的注意力都必须算——一步的细节见进阶版 Q9）

之后每一轮就轻松了：拿刚挑出来的那个字，重新变成一根向量（编号 → 查嵌入表 → 一根新向量），只算它这一行的 q、k、v；前面所有字的 k、v 直接从显存取，不用再算。（注意是从嵌入表重新查，不是接着上一轮那根——细节见进阶版 Q8）

一句话：KV cache 省的是"重算"，不是"重读"。——旧的不用重算，但每次还是得把整份读一遍。

（换个说法：那排存下来的 k、v 就像一排货架——每个字在每层留下一张标签 k ＋ 一个货箱 v。可点着一步步走的那张图里就是这么画的。）

（顺带答一个早晚会冒出来的问题：FFN 也有 K/V 吗？没有——K/V 只属于注意力。展开在进阶版 Q4）

4. 两段的脾气完全相反

术语：算力受限 / 显存带宽受限

算力（compute）：显卡"会算"的能力。显存带宽（memory bandwidth）：数据从显存"搬进"计算单元的传送速度。
算力受限（compute-bound）：瓶颈是"算得不够快"。
显存带宽受限（memory-bandwidth-bound）：瓶颈是"数据搬得不够快"。

Prefill：一大堆乘法一起做 → 算力受限

同一条流水线，方法一模一样，变的只是"一次喂几行"：prefill 一次喂 2 万行，decode 一次只喂 1 行。

而矩阵乘法有个特点：计算量随行数涨，但权重那张表，不管几行都得整张读一遍。所以 prefill 把"读权重"这份固定开销摊到 2 万行上，decode 只摊到 1 行上——这就是两段分野的根。

类比：数学天才与仓库

把显卡的计算单元想成一个数学天才。他做题飞快，但每做一道题之前，都得跑去仓库把整本书搬过来。

prefill ＝ 他一次接了 2 万道题：搬一趟书，一口气做完 → 时间几乎全在做题。
decode ＝ 他一次只做 1 道题：还是得搬同一整本书过来 → 时间几乎全在搬书。

Decode：每吐一个字，都要把存下的 K/V 整份读一遍 → 带宽受限

写一个字时，要算的其实很少（就一行），但前面所有字的 K/V 得从显存整份读上来。所以卡的不是算，是搬。

算一笔账。假设 32 层、每层的向量长 4096、已经攒了 1 万个字，那每吐一个字要搬的数大约是 2（k 和 v）× 32 层 × 10000 个位置 × 4096 ≈ 26 亿——而这一步真正要"算出来"的，只有一个字。

数据也印证了：decode 时 GPU 的利用率会掉到 20–40%（大部分计算单元在干等数据）；prefill 时能跑到接近满载。

（"必须把整份读一遍"有没有例外？有，但那是细节 → 进阶版 Q7）

别急着记「decode 就慢在搬 KV」

这一步要搬的其实有两样：模型权重（每步都要搬，非常大）＋ K/V（每个请求自己那一份）。本课盯 K/V，是因为只有它会随上下文变长——正好回答"为什么长上下文让每一步都更慢"。权重那半截在 第 4 课。

5. 于是有了两个不同的「延迟」

因为两段脾气不同，你感受到的"慢"其实是两种慢：

术语：TTFT 与 TPOT

TTFT（首字延迟）＝ Time To First Token。从你按回车，到看见第一个字。它由 prefill 决定——输入越长，等得越久。
TPOT（每 token 耗时）＝ Time Per Output Token。开始输出之后，每个字花多久。它由 decode 决定——这就是你感觉到的"打字速度"。

一条真实的时间线长这样：

t = 0–50ms   网络 + 排队
t =  50ms    prefill：3200 个输入字一次跑完（顺手把 K/V 填好）
t = 400ms    ── 第一个字出来了        ← TTFT = 400ms
t = 400ms+   decode：每 ~30ms 蹦一个字  ← TPOT
t = 12.7s    第 410 个字，结束         ← 端到端延迟

看到没：首字只等了 400ms，但全文写了 12 秒多。两段完全是两种体验。

我实测的结果：（数字都是相对值，看谁大谁小就够，不用记具体数。）

场景 TTFT 生成耗时 总耗时 相对成本
读长文（20k 进 / 50 出） 1.000 s 1.001 s 2.001 s 20250
写长文（500 进 / 2000 出） 0.025 s 21.499 s 21.524 s 10500
agent 一轮 · 无缓存 1.000 s 1.602 s 2.602 s 20400
agent 一轮 · 命中前缀缓存 0.025 s 1.602 s 1.627 s 2850

两个反直觉的结论（看粗体就够，括号里的数字只是证据）：

  1. "花钱最多"和"最慢"不是同一种请求——钱和时间是两笔账。（读长文最贵，却 2 秒就跑完；写长文便宜一半，却要 21.5 秒。）
  2. 前缀缓存让首字几乎立刻出来、总花费砍掉一大截，但生成耗时一动不动。（TTFT 1.000s → 0.025s，成本降到约 1/7，生成耗时还是 1.602s。）因为缓存只帮 prefill，帮不了 decode。

7. 这对 agent 意味着什么

agent 的典型请求长这样：输入巨大（系统提示 + 一堆工具定义 + 完整历史 + 新观察），输出很小（通常就是"调用某个工具"或一句话）。

所以 agent 是标准的"读长文型"：

  • 痛点在首字延迟和输入成本——这正是前缀缓存发威的地方（第 3 课讲它怎么运作，"什么该稳定放前面"的规矩在技巧篇 0001）；
  • 但 decode 那段省不掉：如果 agent 要写长输出（比如生成一份报告），那时间就是要付的；
  • 也解释了一个体感：agent 常常"卡在第一下"，然后才开始流畅地蹦字。

8. 三个常见误解

  1. "输入和输出的 token 一样贵。" 不一样。输出贵得多——因为 decode 串行又慢慢吞吞。（各家价目不同，大致是输入的几倍。）
  2. "上了缓存 agent 就全面变快。" 只快在 prefill / TTFT。decode 不受影响。
  3. "上下文长只是更贵。" 还更慢——每吐一个字都要把更长的 K/V 读一遍。
