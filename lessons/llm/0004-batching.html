一趟装满的卡车

批处理（batching）怎么救 decode——以及为什么「吞吐」和「延迟」永远在打架。

先别急着学，聊两句

你有没有想过：模型 API 按 token 卖，价格为什么能压这么低？要是你自己租一张显卡跑同一个模型，成本完全是另一个量级。

更怪的是——你发一个请求的时候，服务商其实正在同时给几百个人算。可你并没有等很久。

拆穿了就是一句大白话：一趟车装满 N 个包裹。车程没变，货多了 N 倍。

学完这课，你能：说清批处理为什么能大幅提升吞吐；看懂「吞吐 / 延迟」这笔账；并知道它的天花板卡在哪。

承接第 2 课

第 2 课我们得出：decode 是显存带宽受限——它在"等数据"，不在"算"。这一课就问：既然它在等，那能不能顺手多干点活？答案就是批处理。

1. 先看看 decode 在浪费什么

第 2 课的类比还记得吗：显卡是个数学天才，但每做一道题都得跑去仓库搬书。他大部分时间在搬书。

这里有个关键细节：他每一步要搬的那本书，是模型权重——几亿到几千亿个参数，非常大的一块。而"每个请求自己的历史 KV"相比之下只是薄薄几页。

于是浪费出现了

如果一次只服务 1 个请求，那这趟车（搬模型权重）就只为了一个人跑一趟。车大部分是空的。而搬运时间，是省不掉的。

2. 批处理：一趟车装满

类比：送货卡车

仓库在城东，客户在城西。每送一趟货，卡车都得开完整的一趟。
只送 1 个包裹，太亏了——油钱、司机时间，一样没少。
批处理 = 一趟车装满 N 个包裹。车程没变，但送的货多了 N 倍。每个包裹分摊到的"车程成本"就降到了 1/N。

放到模型上就是：把模型权重搬一次，同时服务 N 个请求。那 N 个请求，"搬书"的钱被摊薄了 N 倍。

术语三连

批处理（batching）：一次让多个请求并排前进一个 token，共用同一趟"搬权重"。
吞吐（throughput）：整个系统每秒总共能产出多少 token。
延迟（latency）：单个请求自己有多快（第 2 课的 TTFT、TPOT 就是在量它）。

3. 动手：跑一遍看数字

python exercises/llm/0004-batching.py

Windows 终端若中文乱码，先执行 chcp 65001。仍是刻意简化的量级模型，重点看相对关系。

我实测的结果（模型权重 140GB，单请求 KV 0.5GB，可用显存 200GB）：

批大小 每步耗时 吞吐 tok/s 单请求每 token
1 0.141s 7.1 0.141s
8 0.144s 55.6 0.144s
32 0.156s 205.1 0.156s
120 0.200s 600.0 0.200s

批一变大，吞吐涨得飞快，而单请求只慢了一点。这笔买卖实在太划算了——这就是为什么所有推理服务都在拼命凑批。（本课实测：批 1 → 120，吞吐 84 倍，单请求慢 42%。）

但天花板有两个

  • 显存：权重（140GB）已经占了大头，剩下的空间才能装各请求的 KV。本例里 (200−140)/0.5 = 120，批大小最多 120。
  • 显存带宽：当批大到"KV 的总量大过权重"时，瓶颈就从权重变成了 KV。吞吐的理论上限 ≈ 带宽 / 单请求 KV = 1000/0.5 = 2000 tok/s。本例因为显存先卡住，到不了这个上限。

4. 于是有了「吞吐 vs 延迟」的权衡

把上面的表画成曲线，就是一个经典的取舍：批量越大，吞吐越高，但单个请求越慢。

真实世界的数字（Databricks 在 A100 上测 7B 模型）也一样：批一大，吞吐和延迟一起涨。（批大小 64 时：吞吐 14 倍、单请求延迟 4 倍。）——和我们的玩具模型量级吻合。

谁在乎哪个？

聊天机器人 / 你的 agent：在乎延迟（用户盯着看，卡了就骂）→ 批要小一点。
离线批处理（比如一次总结一万份文档）：在乎吞吐（没人盯着）→ 批越大越好，慢没关系。

权衡有个硬边界

批大到一定程度后，decode 会从"显存带宽受限"变成"算力受限"。到那之后，再加大批量，吞吐几乎不涨，延迟继续变差——纯亏。所以生产环境要找一个"甜点批大小"。

（上面那张表只画了"搬运"那一半，所以它撞到的是显存的墙，跑不出这个拐点。真到拐点长什么样，看 Databricks 那个实测：批大小 64 时吞吐涨到 14 倍，可单请求延迟也涨到 4 倍——再往上，吞吐就基本不涨了。→ 这个拐点是怎么算出来的）

5. 工业界还在继续往这个方向榨

批处理只是开头。工业界又补了三招：

  • 连续批处理——让批每走一步就重排一次，短请求不用陪长请求干等。（它解决的那个毛病叫"队头阻塞"，是什么？）
  • PagedAttention——把 KV 像操作系统管内存那样切页，不浪费显存，于是能开更大的批。（它省的是哪一样？）
  • 分块预填充 / prefill-decode 分离——让两段各用各的机器。（这两件事是一回事吗？）

知道有这三招就够了——对你写代码没有影响，它们发生在服务商那边。

6. 对你写 agent 的启示

  • 并发能省钱：你的请求会被塞进别人的批里，权重搬运费被分摊了——API 的输出价格能压下来，这是原因之一。
  • 代价是你的请求可能变慢：批大了，你单个请求的 TPOT 会变差。
  • 你的 agent 很多时候在"排队"：一个 agent 通常一次只发一个请求，得等服务端把它塞进某个批。排队时间也算进 TTFT。所以"agent 慢"有时不是模型慢，是你在排队。
