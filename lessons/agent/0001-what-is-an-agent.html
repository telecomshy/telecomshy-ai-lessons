Agent 篇 · 第 1 课 · 理论

Agent 是什么：循环、工具、记忆

先别急着学，聊两句

你有没有想过："用 AI"和"用 agent"，到底差在哪？

你以为在"和模型聊天"，其实是你的软件在给模型供应商的 API 发请求、收回复。网页版和 TeleAgent 都不例外。

同一个模型，套上不同的壳（这层壳有个正式名字：harness）——一个只会一问一答；另一个却能自己查资料、读文件、一步步把活干完，中间不用你盯着。

差别不在模型，在模型外面那层结构：一个"决定了做、做了再看、看了再决定"的循环，外加工具和记忆。

学完这课，你能：说清"用 AI"和"用 agent"差在哪，中间还隔着哪一档；知道网页版和 harness 后台都是同一次请求/回复；分清模型、harness、agent 三个词；说清循环怎么转、什么时候停，工具从哪来，记忆为什么没有标准做法。

记住一条主线，后面就不会晕

先记住两件事：一次 API 调用＝一次请求换一次回复；agent 多出来的，就是把这些请求串成一个循环：推理 → 行动 → 观察 → 再推理，直到任务完成、或者撞上护栏。

本课先讲清这两件事，再看「把决定权交给模型」分几档；下一课把循环写成代码、用真模型跑起来。后面每一课，都是往这个循环里加零件。

1. 先看清后台：你在发请求，不是在和模型聊天

先看两个场景，都是同一句话："查明天上海到北京最便宜的机票，合适就订。"

在网页对话框里

你打开 ChatGPT、豆包这类网页，把这句话打进去。它回你一段文字：建议看哪几家航司、什么时段便宜、怎么比价。然后——到此为止。查航班、比价、付款，还是你自己来；它可能能上网搜两下，但那是产品里预置的能力，你没法把"订票"接进去。

对 TeleAgent 这类 harness 说

你把同一句话交给它，然后去倒杯水。它自己查航班（看到 23 个）→ 决定只看直飞、按价格排 → 调比价、下单 → 回来："订好了，620 元那班。要不要加 20 元选个靠窗？"

直观上，两者的区别看起来很大；但从和模型打交道的角度看，它们只是用的客户端软件不同——网页版是浏览器里的客户端，TeleAgent 是装在电脑上的客户端；这类软件在后面的正式名字是壳 / harness。模型可能是同一个，每一次"打包请求 → 调 API → 拿回复"的过程也一样。真正的差别在客户端拿到回复之后：网页版显示给你，harness 可能执行工具、再发一次。

后台只有一件事：发请求，拿回复

不管界面长什么样，后台都是同一件事：软件把你的输入打包成一个请求，发给模型供应商的接口（API），拿回一段回复，再决定怎么显示、或者接着做什么。你以为在"和模型对话"，实际是你的软件在替你和 API 打交道。

请求和回复都是结构化的数据（通常是 JSON），不是一句人话。请求里装什么？

  • messages：对话记录，一条一条，带角色（system / user / assistant / tool）；
  • tools：这个壳允许模型用的工具清单（第 8 节展开）；
  • model：用哪个模型，以及温度、最大输出长度这类参数。

写成伪代码，一次来回大概长这样：

请求 = {
  "model": "deepseek-flash",
  "messages": [
    {"role": "user", "content": "北京今天多少度？"}
  ],
  "tools": [ ... ]            # 可选：这个壳允许用的工具
}

回复 = 调接口(请求)           # 一次请求，只换一次回复

# 对循环来说，回复只有两种形状：
{"type": "text", "content": "北京今天 26 度"}
{"type": "tool_calls", "calls": [
    {"name": "get_weather", "arguments": {"city": "北京"}}
]}

（字段名各家略有出入，形状就这两类。真正的调用第 2 课写。）

这就是"结构化输入输出"：你发过去的是一组字段，拿回来的也是一组字段，双方都按格式来。壳按字段判读：看到 text 就当回答，看到 tool_calls 就去执行。

三件事记住：① 一次请求只换一次回复，模型不会自己接着做下一步；② 模型不替你记上一轮，每轮看到什么，全靠壳把 messages 重新发一遍；③ 拿到回复先看类型字段：text 还是 tool_calls，不能当成连续的正文来读。

那"自己查、比价、下单"是怎么发生的？一次请求只会回一段话或一组工具调用，不会自己转起来。答案是下一节：壳把很多次请求串成了一个循环。

2. 一次调用 ≠ 一个 agent

上一节说过：一次请求只换一次回复。那 agent 多出来的是什么？多出来的是"再来一次"。

网页版：一次请求 → 一段回复 → 显示给你，结束。

TeleAgent：壳拿到回复，发现里面带着"要查航班"的工具调用，就真的去调；把结果塞回 messages，再发一次请求；模型决定接下来做什么（比价、下单）……直到某次回复不再要工具，才把最后那段话交给你。这个"请求 → 看回复 → 做事 → 再请求"的反复，就是 agent 循环（第 4 节拆开讲它怎么转、什么时候停）。

把话说完整：你给 agent 一个目标，它会自己决定"现在该做什么"；做完看到结果，再决定下一步。这个"决定了做、做了再看、看了再决定"的过程，就是 agent 和单次调用最本质的差别。

差别说成三点：谁安排下一步（你 vs 它）、它能不能用上你的工具（产品预置的 vs 你能配的）、你要不要盯着（全程在场 vs 交代完就走）。两个场景里跑的甚至可能是同一个模型：差的只是外面那层壳，和壳里转的那个循环。

agent 答错的代价也更大：AI 对话答错了，无非回一句错话；agent 答错了，可能是真订错一张票。所以 agent 一定要有护栏，比如下单前先问你一声。护栏是后面反复出现的零件。

3. 三个词各指什么：模型、壳（harness）、agent

日常说"我装了一个 agent"，严格说装的不是 agent。拆开是三样东西：

  • 模型（Model）——只会算的那个零件：给它输入，它吐下一个字。它自己不会挑工具、不会动手、不会记事。
  • 壳（客户端软件 / harness，运行外壳）——套在模型外面的那套软件：拼提示词、递工具清单、执行工具、管上下文、装护栏。你下载安装的，是它。
  • agent（智能体）——不是软件，是行为：壳把"模型＋工具＋循环"装好、跑起来之后，表现出来的那种"自己决定下一步"的本事。

所以口语里说的"装一个 agent"，装的其实是 harness；agent 是它跑起来的样子。这层壳里到底装了什么、为什么值得单独拆开看——第 5 课把几个产品放在同一张零件表上对照。

4. 核心循环

循环长这样：

推理 / 规划Reason：下一步做什么？
→
行动Act：调用工具
→
观察Observe：拿到结果
↺ 把观察结果喂回去，继续下一轮推理

循环什么时候停

出口只有一个：某一次回复里，模型不再要求调工具，而是给出一段话。没有"完成"按钮，也没有一个叫 done 的动作——它不调工具了，壳就认为这一轮收尾了。

所以每一轮壳只做一个判断：这次回复是「一段话」还是「要调哪个工具、参数是什么」的结构化数据。前者收尾，后者继续。

如果它一直调工具、一直不收尾，就会卡死在循环里。所以工程上一定要有 护栏：最常见的是「最大步数」，走满就强制停。步数按调用模型的次数算，不是按工具次数——一步里可以调好几个工具（第 2 课真跑会看到）。

但"停"不代表"做对了"：模型可能提前收工（活没干完就说完了），也可能绕圈（一直说还要调）。这两种情况循环自己判断不了，得靠外面的检查：看 trace、看结果、关键动作让人确认。

谁在转这个循环：不是模型，是壳

第 1 节已经说过：一次调用只换一次回复，模型也不替你记上一轮。所以转圈的不是模型，是 harness：它决定还调不调、调哪个工具，把结果塞回 messages，再发下一次请求。

写成伪代码，就这么几行：

messages = [系统提示, 用户的问题]
工具清单 = [查天气, 列城市]              # 每一轮都随请求发出去

for step in range(1, 最多步数 + 1):
    reply = 调用模型(messages, 工具清单)  # 一次 API 调用，只换回一次回复

    if reply 没有要求调工具:              # 模型用一段话收尾
        return reply.text                # ← 循环的出口

    messages.append(reply)               # 模型说的那句，原样放回
    for call in reply.工具调用:
        result = 执行工具(call)           # ← 这一步是 harness 干的，不是模型
        messages.append(工具结果(call.id, result))

raise 超过最大步数                        # 护栏：模型一直不收尾

那个 return 返回的 reply.text，就是壳最后交给用户的回答。

三件事顺着读一遍：① 出口是"没有工具调用"，不是某个神奇的完成标志；② 每一轮都把全部历史＋工具清单重新发一遍，模型自己不留状态；③ 执行工具、把结果塞回、决定再调一次、走满步数强制停——全是壳的活。模型只负责"下一步做什么"这一个判断。

5. 放手三档：不是所有活都值得让模型定步骤

到这里，agent 的特别之处可以收成一句：把「下一步做什么」交给了模型。顺着这句话就有一个新问题：这个「下一步」，是全交给模型，还是留一部分给代码？答案是分三档（Anthropic《Building effective agents》把后两档统称 agentic system，代理式系统）：

  • 单次调用：一问一答，谈不上流程——第 1 节看过的样子。
  • workflow（工作流）：步骤由代码写死，模型只填每一步的内容。「读表格 → 算汇总 → 按模板写周报」，三步顺序永远不变，每一步内部才轮到模型说话。
  • agent：连「下一步做什么」也交给模型临场决定——就是上面那个循环，一步一判断，走到它认为做完为止。

判据还是第 2 节那个：谁安排下一步。你在产品里看到的「工作流编排／自动化」和「智能体」，差的也是这一层。workflow 在生产里有五种常见骨架，都出自同一篇文章（文末一手资料第一条）：

骨架 形状 一个例子
链式（prompt chaining） 一串步骤，前一步的输出是后一步的输入；中间可设「关卡」，不合格就打回 先写文案、检查过关，再翻译成英文
分流（routing） 先给输入分类，再送进各管一摊的专用提示或工具 客服提问分成咨询、退款、故障三条路
并行（parallelization） 拆成几路同时干完再汇总；或同一件事多跑几遍再表决 一路答用户，另一路检查内容出不出格
编排者-工作者（orchestrator-workers） 中心模型现场拆活、派几个工作者、汇总收工，子任务不是预先定的 一次改动横跨多个文件的编码任务
评估-优化（evaluator-optimizer） 一个模型先做，另一个模型挑刺给意见，循环到合格 文学翻译：译者模型初翻，审校模型提意见再改

这张表不是用来背的，是用来回答一个真问题：我的活，步骤写不写得死？写得死就用 workflow：每步固定，可预测，出了错好排查，花多少钱也事先算得出。写不死——比如「要改哪些文件取决于任务本身」——才轮到 agent。Anthropic 的工程建议（大意）：先找最简单的可行解，只在不够用时再加复杂度；有时这意味着根本不用上 agent。agent 是拿延迟和成本换任务表现的买卖，错误还会滚动放大：一步走岔，后面每一步都建在这一步上。所以要么测够，要么上护栏——护栏第 4 节刚出现过，最大步数就是一种。

这些骨架在哪能摸到？三处

Anthropic 那篇是工程博客，默认读者是自己写代码的开发者，所以读起来像纯理论。但在产品里，这些骨架有三处摸得到。①可视化编排平台：Dify、扣子（Coze）、n8n 这类产品，把骨架做成画布上的节点，拖拽连线就是「把步骤钉死」；Dify 官方对 Workflow 的定位原话是「可靠、可重复的流程」。②Agent harness：正相反，OpenCode、TeleAgent 这类把「下一步」整个交给模型，界面上找不到「工作流」这个词。这不是缺功能，是押了另一档。③自己写：门槛比听起来低。第 4 节的循环去掉「判断要不要继续」这个环节，剩下的就是按固定顺序调几次 API——这正是链式。Anthropic 的建议也是同一个方向（大意）：先用 API 直连，多数模式几行代码就够。

五个骨架逐一指认（Dify 节点名按官方文档，2026-10-21 抓；扣子、n8n 为同类平台，不展开）：

骨架 在 Dify 里长什么样 在 harness 里
链式 大语言模型节点串行直连；中间放 If-Else 当「关卡」 没有对应物（这类产品不给钉步骤的界面）
分流 问题分类器把输入分到不同下游分支 没有对应物
并行 节点并行排列，汇合后下游可读全部分支 没有对应物
编排者-工作者 Agent 节点：流程中的一步自主推理＋调工具 有——多 agent 派单（第 4 课）
评估-优化 循环节点（直到满足条件才停）里嵌一个「审校」模型 没有现成的（可拿两个 agent 仿，但不是内建）

现实中三档经常套着用：Dify 流程图里就有一个 Agent 节点，把一小段自主循环嵌进固定步骤；agent 干活之前，也常有固定的开场步骤。所以听到「用 Dify 搭一个××」，可以直接翻译成：那多半是一个 workflow。哪几步钉死、哪一步放给模型，看节点连线就知道。

这个问题上面还有一层：用一个 agent，还是一群？多 agent 的形状就是表里第四行。什么时候值得上、怎么不出事，第 4 课接着讲。往下看，先把 agent 本身拆开：它靠三根柱子撑着。

6. 这个循环靠三根柱子撑着

领域里常用一张地图来拆 agent：规划、记忆、工具，常被叫做三大支柱（出处见 Lilian Weng 那篇《LLM Powered Autonomous Agents》）。三根柱子不是循环之外的三件东西，它们就长在循环上：规划发生在"推理"那一步，工具是"行动"那一步的手段，记忆管"观察到的结果放哪、下次还认不认得"。下面三节一根一根看。

① 规划 Planning

怎么把大目标拆成能一步步执行的子任务？怎么在失败后改主意？

② 记忆 Memory

当前上下文里放什么？跨会话的东西怎么存、怎么取回来？

③ 工具 Tool Use

如何让模型"伸出手"去调 API、查库、改文件，并把结果读回来？

7. ① 规划：拆任务，和改主意

大活要拆成能执行的小步：「写一份周报」＝查数据 → 算环比 → 写结论。更难的是另一件事，失败后改主意：查不到上周的数据，就换个来源，或者先算前一周。这两件事有专门的叫法：拆子目标、自我反思（self-reflection）。好的 agent 不是一条路走到黑，而是每走一步都检查一下要不要换路。

还要分清两件事。规划不等于"思考"：思考是"想"的总称，验算、打草稿都算；规划只是其中管"接下来做什么"的那部分。一次普通回答里也有规划（先列提纲再写）。agent 的规划多一层：它安排的是接下来动手做什么，还会被行动的结果改写——"改主意"就是这么来的。

这里要分两层。会不会拆任务、会不会根据反馈换路，这个本事长在模型身上（怎么练出来的，见 LLM 底层 · 第 5 课）；第 4 节那种最简的壳——拿到回复、执行工具、塞回结果——拦不住它。但计划要不要明说出来、写成什么格式、存在哪里，这是 harness 定的。裸循环里的计划是隐式的：藏在每一步推理里，不写下来、不留档，上下文一丢就重来。harness 可以把它变成固定的动作：OpenCode 的 Plan 模式就是一例，换成 Plan 档，模型必须先交一份计划，你确认了它才动手；再进一步，就是把计划和进度做成文件落盘（下面的周报例子会碰到，第 5 课 State 子系统展开）。本事是模型的，制度是壳的。壳给不了本事，但能决定本事发挥出几分。

拿「周报」走一遍就清楚了。动手之前，模型先把目标摊成一条路线：查数据，查不到就换来源；算环比，算不出就退回上周口径；最后写结论。这条路线不在代码里，就是上下文里的一段话，模型自己写的；有些 harness 还会把它单独存成一份「进度」。动手之后，这条路线会被每一步的结果改写。比如查回来的数据格式不对，模型就在下一步先转换格式再继续。普通程序的流程表在运行前就固定不变；agent 的计划在运行中一直会被修正——这是两者最大的区别。

拆多细、要不要经常改主意，都有代价。每一步都是一次真实的 API 调用，都是花钱的（第 2 课会算账）。拆得太碎，步数翻倍，账单也翻倍；拆得太粗，一步里要做的判断太多，模型容易漏。改主意也一样：每改一次多走一步，改得太勤会原地打转，改得太懒就一条路走到黑。

8. ② 工具：给模型一双手

最原始的工具，就是你自己在程序里写的一个普通函数：

def get_weather(city: str) -> dict:
    return {"city": city, "temp_c": 26, "cond": "晴"}

但模型看不见这个函数，也调不动它。你得再给模型一张说明卡：名字、一句话说明、参数。模型照着这张卡挑工具、填参数：

{
  "name": "get_weather",
  "description": "查某个城市今天的天气。返回气温（摄氏度）和天气状况。",
  "parameters": {
    "type": "object",
    "properties": { "city": { "type": "string", "description": "城市名" } },
    "required": ["city"]
  }
}

说明卡是模型挑工具的主要依据：写"什么时候该用、返回什么"，不是写给人看的注释。写得含糊，它就调得不准。

这张卡每一轮都要随请求发出去，不是只发一次。所以工具越多，每一轮为它们付的 token 越多。它们是稳定前缀，能吃到缓存（LLM 底层 · 第 3 课），但"稳定"也意味着别在中途增删：一改，前缀就变了，缓存就接不上了。

模型只"说要调"，不执行。它输出的是一段按约定格式写的文字（行话叫 tool_use，OpenAI 那边叫 tool_calls："我要调 X，参数是 Y"）。真正去执行的，是壳里的程序——程序调完，把结果（tool_result）塞回对话，模型才知道发生了什么。所谓"agent 能做事"，全靠这个来回反复转。

为什么非要给它手？因为它伸手去拿的，往往是生来没有的三样东西：现在的信息（今天的航班，模型只学到旧闻）、动手算的能力（它只会吐字）、你公司的数据（它训练时没见过）。

自己写函数，写到什么时候是个头

三五个工具没问题，再多就会撞墙：

  • 不能复用：这个函数只能在你的程序里被调用。换个应用、换个 harness，函数、参数说明、认证、错误处理都得重新搬一遍。
  • 每接一家都要重写：N 个应用接 M 个工具，最笨的做法是写 N×M 份适配。
  • 工具一多，管理全归你：谁能用、要不要审批、版本怎么升、别人怎么发现你的工具。

所以工具后来演化出两个新形态：MCP 把工具做成「标准插口」，写一次，任何支持 MCP 的 harness 都能接；Skill 把「怎么做一类事」打包成文件，不是函数。这两个下一课专门讲。

9. ③ 记忆：模型只看得见上下文

它为什么会忘

模型每来一轮，都要把上下文从头读一遍。它不是"接着上次往下想"，而是每次把摊在眼前的记录重看一遍。上下文里没有的事，它就不知道。而且不是"装满才出事"：上下文越长，它从里面找回信息的准确度越低（Anthropic 管这叫 context rot，上下文腐烂）。它像一个每天失忆的员工，工作台上摊着一圈便签——要紧的不是他记性好不好，是谁在替他写便签、换便签。

两层记忆：这次的，和跨会话的

短时记忆＝上下文：这一轮里放了什么，会话结束就散了。长时记忆＝存在外面的东西：你的偏好、上次的结论，写在文件或数据库里，用到时再取回来，塞回上下文它才"想起来"。所谓记忆，是外面的程序替它存、替它取——模型自己什么都存不了。

四种真实做法：存、取、管，产品之间差得很远

先破一个想当然：长期记忆没有行业标准。研究文献常按内容分成经历／事实／做法（episodic / semantic / procedural），但产品不一定照这个分：怎么分、存哪、怎么取、怎么管，全是各家自己的设计选择。看四个真实取向（产品细节按 2026-10-18 的文档，会变）：不存——OpenCode 不内置长期记忆，跨会话靠项目里的规则文件和代码库，写代码的活，状态本来就该在文件和 git 里，这不是缺陷是取向；存成文件——TeleAgent 按来源＋时间存成几份 Markdown，底层就是文件，不是什么数据库；存成服务——Supermemory 把内容抽成一张带时间的记忆图，新事实会更新、补充旧事实，不重要的自动遗忘；存成事实库——Mem0 把对话抽成一条条小事实，检索时多路打分着取。四家具体的存、取、管各什么样，速查里有一张四产品对照表和文档链接；这里只记结论：四条路没有谁更先进，要不要跨会话、记忆要不要可读可改、过期了谁来清，用你的场景答。

还有一路更彻底的：记忆本身就是给模型的工具——Anthropic 的 memory tool 让模型自己调一组文件命令读写"记忆文件夹"，用到才读回（just-in-time）。工具和记忆的边界，在这里就模糊了。

该记什么，要不要上

该进长时记忆的：稳定的偏好（"我住浦东"）、做过的结论、你纠正过它的话——下次还会用到、而且不会过期的东西。不该进的：一次性细节、全部流水账（存了也取不准，还越存越贵）、会过期的事实（今天的票价——记下来就是给将来埋雷）、敏感信息。

要不要上长期记忆，三个问题过一遍：忘掉的那件事下次真的还会用到吗？用到时能不能一句话补回来？存错了谁收拾？多数场景里，上下文＋让用户补一句就够用；真正值得存的，是"反复要用、而且稳定"的东西。
