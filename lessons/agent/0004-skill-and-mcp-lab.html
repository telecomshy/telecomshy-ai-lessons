Agent 篇 · 第 4 课 · 实操

写一个 skill、接一个 MCP

两件事动手做：打包一份「做法」，配上一个「插口」。

先别急着学，聊两句

上一课说清了 MCP 和 Skill 是什么。这课把两件事都落到手上：生成一个自己的 skill 骨架并自检，配一份 MCP 配置并走通"发现"。

顺手解决一个藏了很久的问题：工具的名字、描述、参数，到底怎么写模型才调得准——这是影响成功率最直接的一件事。

学完这课，你能：写出一个能被模型用起来的 skill；给 harness 接一个 MCP 工具；给任何工具写出"模型看得懂"的说明。

记住一条主线，后面就不会晕

两个命根子：skill 的命根子是 description 那句话（模型全靠它决定用不用）；MCP 的命根子是"发现"（先问"你能干什么"，别硬编码）。

这两处写坏，别的做得再好都白搭。

1. 先跑起来

两个脚本都在工作区，纯离线、不调 API：

python exercises/agent/0004-make-a-skill.py
python exercises/agent/0004-mcp-config.py

Windows 终端若中文乱码，先执行 chcp 65001 切换成 UTF-8。

2. 写 skill：生成、读懂、改坏一次

第一个脚本生成一个 skill 骨架（exercises/agent/my-first-skill/），并自检最常见的翻车点。实跑输出：

==========================================================
skill 骨架已生成：E:\code\my_projects\learn-ai-agents\exercises\agent\my-first-skill
==========================================================
  SKILL.md
  reference.md

[各部分干嘛]
  SKILL.md 的 frontmatter
      name         唯一标识
      description  「最关键的一句」——平时只有这句进上下文
  SKILL.md 的正文
      什么时候用 / 怎么做 / 输出格式 / 翻车怎么救
  reference.md
      正文里一句「看 reference.md」链过来，用到才加载

[自检] 这几条最容易翻车，逐条看：
  OK  名字小写字母+连字符、1~64 字符：weather-dress
  OK  description 长度 20~1024 字符（现在 45）
  OK  description 里说了「什么时候用」——光说功能不够，模型靠这句决定用不用
  WARN description 里最好写清适用场景，而不只是一句话概括

逐段看：目录里两个文件——SKILL.md 是正文（什么时候用我／怎么做／输出格式／翻车怎么救四段），reference.md 是补充资料（正文里一句"看 reference.md"链过来，用到才加载——这就是上一课的渐进式加载）。自检四条是按翻车频率排的：名字格式、描述长度、描述里有没有"什么时候用"、有没有写清场景。注意第三条——光说功能不够，"查天气并给出穿衣建议"只说了它是干嘛的，"当用户问今天穿什么、要不要带伞时使用"才是模型做判断的依据。

改一改：把 DESCRIPTION 换成"查天气。"再跑一遍——自检会亮出 WARN/BAD：太短、没说什么时候用。亲眼看它报一次警，比记十条规矩管用。

3. 接 MCP：配置、校验、发现

第二个脚本离线走一遍接入的四步。实跑输出（配置部分略，JSON 就三行）：

[第 2 步] 校验字段：
  OK   weather-server：command/args 齐了，env 可选
  （字段口径：command 必填；args 必填可空；env 可选，放 API key 这类）

[第 3 步] 发现：连上先问「你能干什么？」
  client -> server： 你能干什么？
  server -> client： get_weather —— 查某个城市今天的天气。返回气温（摄氏度）和天气状况。
  server -> client： get_forecast —— 查某个城市未来三天的天气趋势。返回每天的气温和天气状况。

[第 4 步] 清单就绪：2 个工具，交给模型的是「名字＋说明＋参数」：
  get_weather    参数必填：city
  get_forecast   参数必填：city

逐段看：配置就是一份 mcpServers JSON——服务名、启动命令（command）、参数（args）、环境变量（env，放 API key 这类）。真实 harness 读的就是它（TeleAgent 的"工具管理"就是往里填这份 JSON）。校验一步别省：照抄配置最容易翻在字段上（args 写成字符串、env 写成数组）；脚本把必填/可选的口径打在第二步。发现那一步是 MCP 的灵魂：连上先问"你能干什么"，server 把工具连名字带说明吐回来，你再交给模型——所以工具不用硬编码。

改一改：把配置里的 command 一行删掉再跑——校验会打出 BAD weather-server：缺 command。再想一下：清单里的工具越多越好吗？不是——清单会被算进上下文，用不上的工具每一轮都在收你的钱。

4. 工具描述决定调用准不准

模型看不到你的代码，它看到的只有你写的五样。这五样怎么写，直接决定它调得准不准：

  • 名字：动词＋名词，一眼看出干嘛（get_weather ✓ ／ do_thing ✗）。模型偶尔会照名字"编"相近的工具，名字越明确越少编。
  • 描述：两句话——它是干嘛的＋什么时候该用它（skill 的 description 同一个道理）。含糊的描述是"该调不调"和"调了不该调"的头号原因。
  • 参数：每个参数写清类型、格式、例子（"城市名，例如「北京」"）。能给例子就给例子——参数填错大多是没见过样例。
  • 返回值：小而明确。别把整个数据库扔回来——模型要的是答案不是原料；返回值也会塞回上下文，越大越贵、越容易看漏。
  • 错误信息：写成"模型看得懂、能改动作"的。"查不到「北京市」的天气"比"Error 404"强一百倍——错误也会塞回上下文，模型靠它自救（"哦，换个城市名再试"）。

反例：描述只写功能不写时机（模型不知道该不该用）；返回值原样吐一堆 JSON 让模型自己淘。什么时候不用抠这么细：一次性玩具脚本，能跑就行——这五件是给"要反复用"的工具准备的。

5. 翻车预演

  • description 只写功能：模型用不起来，或者在不该用的时候硬用——先看自检第三条。
  • 配置抄错字段：连不上先看校验那步，别急着怀疑网络。
  • 清单挂太多工具：每个都在吃 token；挑工具的准确率还会随数量下降。
  • skill 改了没同步：正文里写的步骤和脚本对不上，模型照旧文做——改 skill 记得连 description 一起过一遍。
