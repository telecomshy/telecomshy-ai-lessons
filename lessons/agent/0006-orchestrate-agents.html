编排一群 agent

一个 lead、三个 worker，把上一课的形状跑出来看——顺手把账算给你。

先别急着学，聊两句

上一课的形状是"编排者拆活派单、工作者只回结论"。这课把它写成能跑的脚本：一个 lead、三个 worker，中间还故意让一个 worker 失败一次，看兜底怎么写。

学完这课，你能：读懂并改动一个多 agent 编排脚本；说出"只回结论"到底省了多少；知道编排层的兜底该写在哪。

记住一条主线，后面就不会晕

看这份脚本盯三件事：派单三件套写没写全、worker 是不是只回结论、失败重派的兜底写没写。

这三件做对，多 agent 才是放大器而不是碎钞机。

1. 先跑起来

python exercises/agent/0006-orchestrate-agents.py

Windows 终端若中文乱码，先执行 chcp 65001。纯离线假模型；真模型只要给 lead/worker 各换一个模型函数（第 2 课的老办法）。实跑输出：

[lead] 拆活、派单（目标 / 输出格式 / 边界 三样写清）：

     目标：比较北京、青岛、广州下周的天气，挑一个最舒服的

  ...

[lead] 收到 3 份结论（只回结论，不回流水）：

  - worker-price：推荐青岛：人均 760 元，最划算
  - worker-activity：推荐青岛：海边烧烤+帆船

[lead] 汇总：综合推荐青岛：天气舒服、人均 760 最划算、能上海边烧烤+帆船。

上下文对账：
  lead 只装结论：约 45 字
  若装全部流水：约 582 字（12 倍）
  这就是「只回结论不回流水」省下的钱——多 agent 的账一半在这里。

2. 逐段讲解

派单：三件套写在配置里

WORKER_SPECS = [
    {"id": "worker-weather", "tool": "get_weather",
     "goal": "比较北京、青岛、广州下周的天气，挑一个最舒服的",
     "format": "一句话结论：推荐哪座城市、为什么",
     "bound": "只看天气，不要考虑价格"},
    ...
]

每个 worker 三样：goal（干什么）、format（交什么）、bound（别管什么）。上一课说的"派单写糊了会重复劳动、留缺口"，防的就是 bound 缺失——三个 worker 互相抢活或者互相漏活。

worker：小循环，只回结论

run_worker() 就是第 2 课那个循环的迷你版：调工具 → 看结果 → 回一句结论。注意返回值里 verdict 是一句话、logs 是流水——流水只给自己调试用，交给 lead 的只有 verdict。

兜底：失败重派写在编排层

        for attempt in (1, 2):
            r = run_worker(s, cities, attempt)
            ...
            if r["ok"]:
                ...
                break
            print(f"[lead] {s['id']} 失败，重派一次（兜底就写在这里）")

worker 会失败（工具超时、模型跑偏），兜底是 lead 的活，不是 worker 的自觉：重派一次、换工具、降级，都发生在编排层。脚本里 worker-price 故意第一次失败——看输出里它被重派的那一刻。

对账：只回结论省了多少

输出最后那段是全课的点睛：lead 的上下文只装 45 字的结论；装流水要 582 字，12 倍。worker 越多、任务越长，这个倍数越吓人——多 agent "token ×15"的账，一半就从这里来。

3. 改一改：亲手把它改坏

  1. 让 worker 回流水：把 verdict 换成 "；".join(r["logs"]) 交上去，再看对账那几行——倍数立刻塌下来。这就是"回结论"纪律的实证。
  2. 删掉一个 bound（比如 worker-price 的"只看价格"），把假模型的"推理"改成看两个维度——看它怎么开始抢 weather 的活。派单的边界是防抢活的墙。
  3. 把重派循环删掉（for attempt in (1, 2) 只留一次）——worker-price 失败后整份汇总缺一角。兜底不在，单点失败变全局缺口。

4. 翻车预演

  • 小题大做：任务两三个工具调用能完，就别开 worker——脚本收尾那两行提醒就是干这个的。
  • 汇总变拼接：lead 拿到结论后要合成一个答案，不是把三句话堆一起（脚本的 summary 是合成，不是拼接）。
  • 同步等待：脚本是挨个跑的；真实系统里 worker 可以并行，但最慢的那个决定总时长。
