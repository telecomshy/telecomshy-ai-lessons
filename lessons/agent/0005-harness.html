Agent 篇 · 第 5 课 · 理论

Harness：Agent = Model + Harness

先别急着学，聊两句

0001 说过：模型只会吐字，agent 是跑起来的行为，中间那层壳是 harness。这一课先把公式讲透，再看它由哪几个子系统撑起来、上下文快满时怎么处理、四个产品怎么选。

你平时比较的"哪个 agent 好用"，比的其实不是模型，是模型外面这层壳；但壳又没法脱离模型单独谈。公式把这两件事绑在一起。

学完这课，你能：说清为什么 Agent = Model + Harness；说出 harness 的五个子系统；看懂压缩和交接的区别；按场景在四个产品里挑一个。

记住一条主线，后面就不会晕

Agent ＝ Model（LLM）＋ Harness

模型负责"想"（下一个字吐什么），壳负责"能"——给它什么上下文、什么工具、什么权限、什么记忆、怎么验证、怎么恢复。

下面的对照只依据官方文档（2026-10-18），不是跑分；产品会变，版本以官方为准。

1. 公式：Agent = Model + Harness

先把三个词摆正：Model（LLM）是那个只会算下一个 token 的模型；Harness是围在它外面的软件；Agent是这两者装在一起、跑起来表现出的行为。所以：

Agent ＝ Model ＋ Harness
模型提供"想"的能力；壳决定这份能力能不能落到活上。
Model（LLM） Harness
负责 下一个 token 吐什么；知识、推理、写作风格 拼上下文、执行工具、管权限、存取记忆、验证结果、跨会话恢复
换掉它 能力上限、价格、速度、说话风格会变 默认行为、能干什么、敢不敢放手、接不接得上会变
出事时先看 知识不够、推理跑偏、模型本身做不到 上下文没给对、工具太差/太多、权限没拦住、状态没交接

为什么这个公式重要？因为它解释了三件日常会碰到的事：

  • 同一个模型，换个产品，体验差很多：模型没变，壳的 prompt、工具、上下文、权限变了。
  • "某某模型不行"经常是冤枉：先问是在哪个 harness 里试的；也可能是壳没把它的能力接出来。
  • 选产品，本质是选壳：模型可以换，壳的默认值、生态、权限、记忆却很难换。

但也别把公式当万能药：harness 不能把弱模型变强，它只能把强模型用得更充分，或者把好模型用废。模型是上限，壳决定你离上限有多远。

2. 一条请求：harness 在决定什么

把一次任务拆成一条流水线。模型只负责中间那一步"下一个字吐什么"；前后每一步，都是 harness 在安排。

环节 harness 在决定什么 用户能感知到什么
拼上下文 系统提示、规则文件、工具清单、历史、@文件——谁进、按什么顺序进 听不听话、贵不贵、会不会"忘了前面"
调模型 用哪个模型、开不开思考、超时/失败怎么切 快慢、稳不稳、回答风格
执行工具 给哪些工具、在哪个目录跑、沙箱/超时/错误怎么处理 能不能真的干活、干到哪一步
回填观察 工具结果截断、摘要、格式化，错误信息怎么给模型看 会不会越跑越乱、出错能不能自己改
过护栏 哪些动作要审批、最大步数、预算、权限范围 敢不敢放手、会不会误删/误发
记录与恢复 trace、checkpoint、undo、跨会话记忆 出事能不能查、能不能退、下次还记不记得

同一个模型，换一套默认值，体验就变了。工具清单从 3 个变成 30 个，模型更容易选错；上下文裁得更狠，长任务更容易丢线索；审批从"每次都问"改成"全自动"，速度上去了，风险也上去了。这些都不是模型的能力，是 harness 的选择。

3. 五个子系统：壳不是一层皮

把 harness 拆开，比较通用的一套分法是五个子系统。不同产品叫法不同，但要做的事绕不开：

子系统 管什么 缺了会怎样 产品里的影子
Instructions 告诉 agent 做什么、按什么顺序、开始前读什么；规则/技能按需加载 乱来、重复、每次都要人重讲 AGENTS.md、规则文件、Skill、Plan 模式
State 记录做了什么、在做什么、下一步；进度、feature list、git、记忆 下次接不上、重复干、忘了为什么改 progress 文件、任务列表、会话记忆、git log
Verification 怎么证明"做完了"：测试、浏览器、检查单、端到端验证 说 done 但跑不通；改一处坏三处 测试工具、浏览器 MCP、检查单、任务结果预览
Scope 一次做多大：一个 feature、一个目录、一个目标；什么时候停 贪多嚼不烂、半途而废、越界 工作空间、Plan、最大步数、任务边界
Session Lifecycle 开始怎么初始化、结束怎么收尾、怎么把干净状态交给下一次 烂摊子越滚越大；新会话从废墟开始 init 脚本、git commit、进度文件、压缩/清空

这五个子系统，功能表上不一定都写。但一个 harness 好不好用，往往就差在这里：Instructions 写得清不清、State 接不接得上、Verification 认不认账、Scope 管不管得住、Session 收不收得干净。

4. 上下文快满时：压缩、清空，还是交接

大多数人真正见到的不是"长任务"这个功能，而是：任务跑着跑着，界面提示上下文快满了，然后 harness 自动压缩/摘要，或者让你清空。压缩是主流做法。

压缩解决"装得下"：把旧对话、旧工具结果摘要成一段，腾出窗口继续跑。它不解决"接得上"：摘要会丢细节，下一段可能忘了为什么改、改到哪、什么算完成。任务越长，这个差别越明显。

策略 怎么做 适合 代价
压缩摘要 把旧历史/旧结果摘要成一段，继续跑 单次任务续命 丢细节、摘要本身可能偏
裁旧工具结果 先删最老/最大的观察，保留结论 上下文被工具输出塞满 可能把后面要用的证据删了
清空 / 新会话 手动清空，或开新会话 任务告一段落 要重新交代背景
外置状态 / 交接 把进度、feature list、git、记忆写到磁盘 跨多个窗口的长任务 要维护文件、要有纪律

你用的 harness 如果只显示"上下文快满"然后自动摘要，那就是第一行；TeleAgent 手册里还有上下文用量查看与清理；OpenCode / Claude Code 这类 coding harness 有 compaction。压缩是默认动作；"交接"是任务跨很多个窗口时才要加的码。

Anthropic 在长任务 harness 里讲的，就是后一种：

Initializer：先把场地铺好

第一次会话不急着写功能，而是写一份 feature list（每个功能带 passes 状态）、一个能跑起来的 init 脚本、一份进度记录，再做一次初始提交。

Coding agent：每次只推一个 feature

后续会话先读进度、feature list、git log，跑一次基本测试确认没坏，再挑一个未完成的功能做；做完提交、更新进度，留干净状态。

它要留的不只是摘要，还有四样东西：feature list（哪些功能、哪些已通过）、init 脚本、progress 记录、git 提交。这四样让下一次会话能快速回答：做到哪、下一步做什么、环境有没有坏。

只靠压缩时，常见翻车：

  • 想一口气做完：上下文在半路耗尽，留下做了一半、没文档的功能。
  • 过早宣布完成：看到"有进展"就说 done，其实功能没跑通。
  • 留下烂摊子：下次会话先花大量时间修上一次的破坏。
  • 没测就说完成：单元测试过了，端到端没跑；用户一用就露馅。

这套做法来自 Claude Agent SDK / Claude Code 的长任务实践，不是所有 harness 都提供；你的 harness 只做压缩也很正常。区别只在：任务跨很多个窗口时，压缩够不够用。

5. 没有"最好的 harness"，只有"任务-壳匹配"

LangChain 把这件事叫 task-harness fit：壳要和任务真正需要的东西匹配——需要什么上下文、会遇到什么失败、必须执行什么策略、在什么环境里跑。客服 agent 和长任务 coding agent 的壳，不可能是同一套。

任务 最需要什么上下文 常见失败 关键设计
写代码 仓库结构、规则、测试、最近改动 改坏、没测、越改越乱 沙箱、审批、测试/浏览器验证
办公文档 模板、历史文件、数据、格式要求 格式错、覆盖原件、数据看错 工作空间、备份、预览、结果可核对
常驻助理 消息、日程、跨会话记忆 重复、越权、记错 多平台接入、权限、记忆管理
长任务 进度、feature list、上次状态 接不上、提前宣布完成、留烂摊子 状态文件、验证、范围控制、干净收尾

所以"哪个 harness 最好"这个问题，得先换成：我这类任务，最需要哪几个子系统？答案不同，产品就不同。

7. 按场景选，不按功能多少选

功能表只能告诉你"它有什么"，不能告诉你"你用起来顺不顺"。更实用的问法是：我大部分时间在干什么？

你大部分时间在…… 先看谁
写代码、在终端里改项目、想自由换模型/接本地 OpenCode：终端/IDE/桌面都能跑，开源，provider 自由
做文档、表格、PPT、数据分析，还要接国内 IM WorkBuddy：办公桌面工作站，连接器和定时任务齐
国内办公、想用技能广场、授权想细一点 TeleAgent：桌面办公＋技能/MCP＋三选一授权
长期在线、用 Telegram/Slack/微信等指挥、跑服务器 Hermes：CLI/Desktop/服务器，20+ 消息平台＋cron

不是绝对：OpenCode 也能写文档，WorkBuddy 也能跑脚本；这里看的是默认值——你打开它时，它已经替你选好了哪条路。

8. 功能表之外的三个隐性成本

  • 工具越多，上下文越贵：每个工具的名字和说明都进 prompt；30 个工具不只多花钱，还会让模型更容易选错。功能多不等于好用。
  • 默认权限就是产品态度：默认全自动、默认审批、默认只碰工作区——出事时差别最大。看产品先看默认值，不要只看"能不能全自动"。
  • 迁移成本：技能、规则、记忆能不能导出？换一个 harness，是不是要从头教一遍？开源/闭源、云/本地，决定的不是今天，是半年后。

所以"功能表/榜单"只能做初筛；真正合不合手，还是拿你每天那类任务试。别人说好，不等于你的活好。
