Agent 原理篇 · 第 5 课 · 初学版

工具长出两个新形状：MCP 与 Skill

一个管「怎么接」，一个管「怎么做」。

先别急着学，聊两句

你的 agent 现在只会你自己写的那几个工具。但你大概已经撞到这两个墙了：

  • 别人写好的工具，怎么拿来就用？难道每接一家，都要为它写一遍适配？
  • 你做过的这类事，怎么做下一次才不用从头教？每次都要把"步骤、注意点、翻车怎么救"重讲一遍？

这两个墙，工具长出两个新形状来解决：MCP 管"怎么接"，Skill 管"怎么做"。

学完这课，你能：说清 MCP 和 Skill 各解决什么问题、跟工具差在哪，并且动手写出自己的第一个 skill。

记住一条主线，后面就不会晕

用厨房打比方，三个东西是这样的：

工具＝厨具（锅铲、烤箱）——能干一件具体的事。
MCP＝插座标准——让任何厨具都能插进任何厨房，不用配转接头。
Skill＝菜谱——教你"做这一类菜"的完整做法，包括火候和翻车怎么救。

1. 先看问题：自己写工具，写到什么时候是个头？

上一课你已经体会到：工具是一个个手写的。这在只有三五个工具时没问题。但——

  • 你想用别人写好的（天气、搜索、读数据库、发邮件……），每家的调用格式都不一样；
  • 你想让 agent 会做某类事（比如"报天气顺便给穿衣建议"），光有工具不够，还得教它怎么做。

这两件事，性质不同，所以长出了两个不同的东西。

2. MCP：给工具定一个统一的插口

MCP（Model Context Protocol，模型上下文协议）是一套开放标准：让"提供工具的一方"和"用工具的一方"说同一种话。

类比：插座标准。以前每台电器配一个专用插头，现在统一成国标，任何厨房都能插任何电器。

三个角色

  • MCP server（提供方）：把你的能力（工具、数据）按标准公布出去；
  • MCP client / host（使用方）：你的 agent 或 IDE，按标准接入；
  • 协议本身：双方都遵守的那套说辞。

关键是"能被发现"

以前你要把工具硬编码进 prompt；有了 MCP，client 可以先问一句：

client → server：  你能干什么？
server → client：  我有这些：get_weather、list_cities、send_email …
                    每个都带名字、说明、参数

这就叫发现（discovery）。工具可以被找到，不用你一个个写死。

术语

MCP＝Model Context Protocol，一套开放标准。MCP server＝按这套标准公布能力的一方。发现（discovery）＝先问"你能干什么"，再决定用哪个。

server 一般公布三样东西：工具（tools）、资源（resources）、提示词模板（prompts）。

好处：写一次，到处能用；工具可以被搜到；整个生态可以共享——你不用为每家 API 重写一遍适配。

3. Skill：把「怎么做这类事」打包

Skill（技能）不是"一个函数"，是"做某一类事的完整做法"：一个目录，里面装着指令 + 可能的脚本 + 参考资料。

类比：菜谱。厨具（工具）告诉你"能切能炒"，菜谱（skill）告诉你"红烧肉该怎么做、什么时候放糖、糊了怎么办"。

一个 skill 长这样：

weather-dress/
  SKILL.md         ← 正文：什么时候用我 / 怎么做 / 翻车怎么救
  reference.md     ← 补充资料，用到才打开

SKILL.md 的第一行最关键

---
name: weather-dress
description: 查天气并给出穿衣建议。当用户问「今天穿什么」
             「要不要带伞」这类跟天气有关的出门问题时使用。
---

这段叫 frontmatter。其中 description 是模型决定"要不要用这个 skill"的唯一依据——写得含糊，它就用不起来。

关键设计：渐进式加载

skill 不是一股脑塞进 prompt 的。它分三层：

  1. 平时：只有 description 那一句话进上下文；
  2. 模型觉得用得上：才打开 SKILL.md 正文；
  3. 正文里提到某个文件：再按需打开那个文件。
为什么非要这样？

因为上下文是稀缺资源——LLM 底层第 3 课讲过：进上下文的东西都要花钱、占位置、还会互相干扰。
把所有东西一次性塞进去，又贵又慢还容易跑偏。渐进式加载就是"不看不用的，连打开都不打开"。

（这跟 RAG 是同一个思想：按需取资料，而不是把整份文档塞进去。见 RAG · 第 1 课。）

4. 三样东西，一张表看清

工具 MCP Skill
是什么 一个函数 一套接口标准 一个"做法包"
解决什么 让模型能动手 让工具能被任何应用接上 让 agent 会做某类事
里面有什么 代码 协议 + 描述 指令 + 脚本 + 资料
怎么被发现 你写在 prompt 里 自动发现 按需加载
类比 厨具 插座标准 菜谱

5. 动手：写你自己的第一个 skill

不调 API，纯离线。脚本生成一个 skill 骨架，并且自检你写得好不好：

python exercises/agent/0005-make-a-skill.py

它会在当前目录下生成 my-first-skill/，并且打印：

[自检] 这几条最容易翻车，逐条看：
  OK  名字小写字母+连字符、1~64 字符：weather-dress
  OK  description 长度 20~1024 字符（现在 61）
  OK  description 里说了「什么时候用」——光说功能不够
  OK  description 里最好写清适用场景

重点看那句"什么时候用"：description 不只是"这个 skill 是干嘛的"，更要写"什么情况下该用我"。模型全靠这句做判断。

6. 三个必须记住的画面

① 工具是"能干什么"，Skill 是"该怎么做"

工具给能力，skill 给判断。光有工具，agent 会做但不会判断该不该做、怎么做才对。

② MCP 解决"接"，不解决"做"

MCP 让工具好接，但接上之后怎么用得好，是 skill 的事。两者互补，不互相替代。

③ 一切按需加载，因为上下文是稀缺资源

MCP 的"发现"、skill 的"渐进式加载"，背后是同一个理由：塞进上下文的东西，都要花钱、占位置、互相干扰。这条从 LLM 底层一路贯到 agent 工程。

8. 下一步

工具这条线到这儿就成体系了。接下来两个方向：

  • 工具设计：名字、描述、参数怎么写，模型才调得准——上面 description 那一课就是它的缩影；
  • 怎么知道它变好了：怎么评估一个 agent（这块资料还缺，是公认的难点）。
这节课的一手资料：
Model Context Protocol — 官方文档：MCP 是"把 AI 应用连到外部系统的开放标准"；server 公布 tools / resources / prompts。
Anthropic — Equipping agents for the real world with Agent Skills：Skill 的设计理念，渐进式加载（progressive disclosure）是核心——"像一本组织良好的手册"。
